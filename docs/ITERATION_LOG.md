## 2026-08-12 - 0.1.1 附件身份占位与数字噪声修复

### 目标

修复文本简历中“手机号：未提取 + 唯一匹配邮箱”仍被判定为多个身份的问题，并把附件身份规则、版本和验收状态同步到维护文档。

### 范围与完成项

- 确认根因有两层：PDF/DOCX 文本层可能拆开“手机/邮箱”标签；通用标签扫描器还会把“项目邮箱：…”等正文短语识别为第二个身份字段，标签值段又可能吞入后续正文邮箱，最终触发多身份
- 使用现场 PDF 的隔离源文件重放后确认另一条根因：真实字段使用“移动电话”，旧规则未识别该标签，全文兜底又把知乎链接中的 11 位文章编号当作第二个中国手机号；现已识别“移动电话”和 PDF 行内分隔身份标签，只读取标签字段值
- 修复批次恢复状态：待确认项引用的短期预览已过期、取消、失败或丢失时，启动恢复会将其转成明确失败并要求重新上传，不再继续展示不可提交的旧匹配结论
- 在服务端附件身份规范化边界过滤 `null`、空字符串、纯空白和精确的“未提取”；手机号与邮箱分别格式验证、规范化、去重后再统计唯一值
- 区分“身份标签存在但值缺失”和“文档没有该身份标签”：前者保持缺失，后者才执行受限全文兜底；无标签手机号兜底只接受中国大陆手机号或显式国际号码。标签值在同一行遇到下一个字段冒号时截断
- 中文身份标签允许 PDF/DOCX 提取造成的内部空格/换行；行内标签要求明确字段边界，并限制可嵌入识别的完整标签，避免从“项目邮箱”等正文短语中间命中
- UI 继续只根据空 API 值展示“未提取”，不把占位文案写回身份字段；API 公共记录不暴露内部候选值数组
- 增加 UTF-8 TXT 单文件和批量附件支持；保留 PDF、DOCX、XLSX、XLSM、BIFF8 XLS、UTF-8 CSV、安全校验、确认事务、一次性令牌与 SHA-256 幂等行为
- 应用版本更新为 `0.1.1`；不新增 schema 迁移，不批量覆盖真实数据库历史原始数据

## 2026-08-04 - 北森分批增量导入与 BIFF8 XLS

## 第十二轮：响应式适配与导航表面隔离（已完成，2026-09-16）

### 背景

用户反馈「模块太大、不适配电脑屏幕」「AI 助手跟导入候选人不是独立的，有时候甚至点不开」。2026-09-15 先在匿名预览库（4398 + Vite 4400）用 Playwright 做了一轮 15 档视口实操审计，确认三类缺陷并写成规范与计划；随后按计划完成阶段 0–6 的实现、回归与文档收尾。

### 审计结论（实测）

- **尺度不随分辨率变化**：1024×768 到 3840×2160 共 15 档视口下，主标题恒 `34px`、侧栏导航 `16px`、表头 `16px`、数据行 ≈`72px`、列表头像 `52px`，一档未变。`721–1439px` 区间（最常见的笔记本区间）没有任何尺度规则；只有 `≤720px` 把 `h1` 降到 20px。
- **常见分辨率下列被裁**：1024×768 / 1152×864 下 `标签`、`更新时间`、`操作` 三列完全不可见，`地点/学历` 被切一半；1366×768 首屏仅 5 行且标签列换行成三行高；768×1024 侧栏固定 208px、内容区仅 560px。
- **导航表面不互斥**：助手与导入页可同时渲染（实测导入页 y=19、拾才助手 y=692 同屏堆叠）；点「导入候选人」后再点「候选人库」会出现「地址栏与侧栏高亮都变了、屏幕还是导入页」的假死；叠加状态下重复点击入口无任何视觉变化。根因是 `src/App.tsx` 的 `importOpen` / `assistantOpen` 并列布尔量与 `:1354` 的 `hidden` 组合，导航动作不清除状态。
- **顺带确认**：履历检索自由文本条件不生效（无关词仍返回全库 48 人并全部标注「部分匹配」，根因 `server/hybrid-search.js:782-795` 的分页补齐 + `:809` 伪分数）；职位操作列按钮竖排；详情抽屉「显示」按钮溢出卡片 21px；导出菜单与模态框无法用 Esc/点击外部关闭；分组名截断无提示；名称与统计口径不一致。

### 方案

- 设计规范：[响应式尺度与导航状态隔离](superpowers/specs/2026-09-15-responsive-scale-and-surface-isolation-design.md)，含断点分档表（XL/L/M/S/XS/平板/手机）、列优先级表、并排抽屉分级、`Surface` 联合类型状态机、D1–D10 修法、G1–G6 验收门禁。

- 目标版本 `0.3.0`，数据库保持 `V13`，无新增迁移。

## 第十三轮：检索性能、索引维护与稳定性（已完成，2026-09-17）

### 起点

正式库达到 140,381 位候选人 / 455,744 份来源文档后，用户在正式服务上观察到「测试搜索功能有很大的问题」——`/api/resume-search` 每次以 `search_timeout`（504）结束，随后又出现「一次查询花了四分钟」。两者都发生在正式服务、正式库上，不是测试环境的特例。

### 定位

- 逐阶段计时：规划 2.1s、向量化 0.25s、重排 0.34s 正常，**267s 全在本地检索**。
- `self_docs` 是覆盖全量来源文档的 CTE，被同一条检索的多条语句反复引用，SQLite 每次都要完整物化：单次 38.8s，即便只查一位候选人也要 13.7s。
- 向量 worker 每次启动都要对 2.68GB 索引 + 4.10GB 向量库做 SHA-256，13.7–15.9s；而查询预算从启动时开始计时，超时又会回收 worker，形成「永远冷启动」的循环。
- 维护任务每 5 分钟触发一轮全量重扫，单轮 498–1003s，几乎不间断占用磁盘 I/O。
- 前端在目标页不在游标缓存中时逐页请求（上限 30 次），在单次检索数秒的情况下放大成约 4 分钟。
- 另有一次正式实例在连续超时后进程退出，stderr 只留下与超时同源的堆栈。

### 实施与验证

- `self_docs` 改为按倒排索引收窄候选域后再物化（收窄集是原谓词的超集，语义等价），并在单次请求内只物化一次到带索引的临时表，供 `count`/`ranked`/`qualification`/向量校验/分页补齐共享；未解析自由文本的本地召回走同一路径。
- `readSearchDocuments` 的来源连接改为 `CROSS JOIN` 强制以主键驱动：原计划从 `candidates` 全表驱动，单页 400 行 10,154ms，修复后 75ms。
- worker 启动与查询预算分离；向量代际只在首次做全量哈希校验，之后按 `.verified.json` 的文件戳判断（复开 0.24s）；文件型只读连接不再设置 `PRAGMA query_only`（`readOnly` 已阻止主库写入）以允许临时表；服务内部 Promise 增加兜底，避免迟到结算终止进程。
- 向量维护改为增量：先做一次「修订值」扫描（身份、`updated_at`、正文长度、候选人归档状态，不读正文，455,744 行约 7.8s），仅对修订值变化的文档读取正文并比对内容哈希；修订值写入向量代际内 `documents` 表的 `revision` 列；移除每轮写入 45 万行 `seen` 表的记账；不可索引文档由「取不到正文即移出索引」处理。
- 维护调度改为每个开机周期一次（开机标记取整到分钟），子进程 BelowNormal 优先级；`SEARCH_VECTOR_MAINTENANCE_INTERVAL_MS` 不再参与调度。
- 前端页码跳转改为：命中游标缓存则沿用快照，否则直接请求目标页（一次请求）。
- 结果集未改变（产品经理 5,419、后端 8,684、Unity 8,505、Java 9,975、数值策划 783，与修复前一致）；单次检索 267s → 约 6–10s；维护单轮 498–1003s → 19–20s；维护运行期间并发检索 6.5–10.1s 全部成功。
- `npx tsc --noEmit`、`npm run build` 通过；`npm test` 730 项、715 通过、8 个既有失败、7 跳过，失败集合与改动前完全一致，无新增失败。
