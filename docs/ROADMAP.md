# 迭代路线图

## 原则

- 先用匿名或脱敏样本完成 PoC，再处理真实候选人数据。
- 迁移必须可预览、可重复、可审计；禁止仅凭姓名合并。
- 结构化查询使用业务 API 工具，简历等非结构化内容才考虑全文检索或 RAG。
- 从个人版升级到多人版必须先补身份、权限、审计和集中运维能力。

## 0.1 个人可用 MVP（已完成）

范围：本机单用户、SQLite、本地 Web 界面。

- 候选人 CRUD、搜索筛选、阶段流转、备注和活动记录
- 软归档与恢复
- UTF-8 CSV、XLSX、XLSM 导入预览、映射、校验、去重和提交
- CSV/XLSX 导出
- OpenAI-compatible 只读 Agent，可不配置
- 本机回环地址强制限制、Agent PII 最小化、CSV 公式注入防护
- 自动化后端测试和桌面/移动端浏览器验收

退出条件：个人可以在空数据库中启动，使用匿名样本完成一轮增删改查、导入、导出和恢复。

## 0.1.x 候选人库与职位工作台（已完成）

目标：把招聘职位提升为候选人的一级筛选和分组对象，同时继续保持个人本机、非完整 ATS 的产品边界。

已实现：

- 独立职位 CRUD、状态、搜索筛选、软归档和恢复
- 候选人与职位多对多关系，复合主键防重复
- 1 至 100 条事务式批量关联和批量解除，支持幂等重放
- 候选人按职位、未分配职位筛选和分组
- 职位详情中的已有候选人关联、新建后关联、解除和按职位导出
- 工作台职位统计和候选人最近 7 天更新数
- 加法式建表；旧候选人不改写，默认未分配
- 历史版本中的三个 Agent 工具保持只读，职位和关系当时不进入模型；该范围已由 V6 全字段按需只读取代

验证：原有 13 项后端回归、生产构建、依赖审计、Playwright 核心流程、1440x900 与 390x844 截图和浏览器控制台检查均通过。

退出条件：候选人、职位和关系核心流程在隔离测试数据库通过；正式数据库升级前备份可用；正式数据库不被测试数据污染。

## 0.2 人才库 V2（历史基线，已实现并验收）

目标：依据三份北森旧版 `.xls` 的真实字段和 `1A/2A/3A/4A/5C/6 全保留/7A/8A` 决策，把默认产品语义从招聘流程调整为长期人才资料管理。

已实现：

- 496 个物理列全部形成处理结论和字段映射基线，不在文档中记录候选人值
- `schema_migrations` V1/V2 和八张人才库领域表；旧候选人及历史 `stage` 不被改写
- 人才库独立实体、候选人多对多关系、归档恢复和组合筛选
- 候选人档案分区、求职偏好、来源历史、历史评估、授权和职位来源记录
- 敏感字段完整保留在受保护本地区域，当时默认不搜索、不导出且不进入 Agent；V6 已保留 UI/默认导出隔离，同时按用户问题开放受控全字段只读
- 北森 `应聘者ID` 增量预览和重放安全提交；同 ID 后出现非空标量覆盖、空值保护、姓名纠正、标签并集上限 50，申请/职位和评估来源可选
- 逐输入行计数守恒、唯一候选人计数、申请归属不改绑和失败行候选人/职位/原始载荷隔离
- 未加密 BIFF8 `.xls` 服务端解析、OLE2 文件签名校验和伪扩展名拒绝
- 默认 UI 和普通导入隐藏 legacy stage；V2 Agent 当时也隐藏该字段，V6 Agent 可按需只读；历史面试/测评只作档案，不扩展完整 ATS
- V2 历史 Agent 使用固定的最小只读工具；V6 已升级为 schema 目录驱动的 17 个全字段只读工具
- 后端测试、生产构建、依赖审计和人才库 V2 Playwright 桌面/移动核心流程通过

仍待：带精确 `应聘者ID` 的正式北森文件 dry-run、错误行人工复核，以及公司对高敏数据合法依据、可见范围和留存周期的确认。现有前两份 `.xls` 因缺少该字段不能与第三份自动合并。

退出条件：代码与文档实现已完成；只有正式数据 dry-run 和公司治理决策完成后，才允许把真实候选人批量写入日常使用库。

## 0.2.1 正式北森数据 PoC（下一阶段）

前置材料：北森合法导出且每批第一张工作表均包含精确 `应聘者ID` 的文件。候选人资料可分批提供；需要申请/职位关系的批次另含完整 `申请ID`、`职位编号` 和必要职位信息。现有前两份 `.xls` 缺少候选人稳定 ID，不能直接参与跨文件合并，也不按姓名或行号补造身份。

计划：

- 在隔离数据库执行导入预览，复核候选人、缺失 ID/姓名、可选申请/职位、跳过关系、职位匹配和职位创建数量
- 抽查日期、枚举、薪资、重复表头、来源渠道、人才库、历史评估和授权字段的转换结果
- 人工确认待创建职位及负责人，禁止从 `current_title` 猜测招聘职位
- 复核身份冲突、重复申请、关系信息不足和缺失候选人身份错误，不绕过预览强制提交
- 用相同 ID 的互补字段文件验证后出现非空值覆盖、空值不清除、姓名纠正、标签上限、逐行计数守恒，以及候选人、可选申请/职位和关系不重复创建
- 验证申请 ID 只在职位关系或真实评估需要时参与校验，跨候选人归属不改绑，失败行不污染有效候选人、职位和原始载荷
- 制定批次回退步骤、真实备份恢复演练和异常行修正清单
- 单独评估简历附件迁移、文件校验、恶意文件扫描和留存策略

验收：相同 ID 分批导入符合后出现非空值覆盖与空值保护规则；标签不超过 50；姓名不参与合并；联系方式冲突不自动合并；完全没有职位字段时只跳过关系，显式职位字段无效/歧义/归档冲突时阻断源行；申请归属不改绑；逐行计数守恒；失败行不污染有效数据；职位创建经过人工确认；原始来源可追溯；测试库与正式库隔离。

后续优化：增加内容指纹或逐字段差异检测，使完全相同文件重放不再更新 `updated_at`、`import_batch_id` 或写入导入更新活动。当前版本只保证不重复创建主记录和关系，不是严格状态幂等。

## 0.3 V6 全量只读 Agent、双实体删除和简历附件

已实现：17 个 schema 目录驱动只读工具、独立 SQLite 只读 worker 与 authorizer、查询审计和资源上限；候选人级 FTS5 Top-K；候选人/职位 token 化单条与批量永久删除；六种本地简历附件解析、电话/邮箱定位、差异预览和用户确认写入。Agent 写工具继续关闭，附件确认只能走普通业务 API。

发布门禁已满足：匿名隔离数据库完成全部自动化、构建、依赖审计和桌面/移动 Playwright 后，正式 `data\recruitment.db` 已执行 V6 加法迁移并通过 schema、对象、完整性、外键和不含明文的聚合核对。现有网关未确认 Embedding，`candidate_resume_vectors=0`，向量检索保持关闭且未连接新服务。

后续：建立更大固定评测集和长期性能基线，补充每用户速率/token/费用限制；多人部署前完成认证、RBAC、字段权限、集中审计和敏感文件授权。

## 0.3.1 附件身份识别修复（0.1.1，已完成）

- 将“未提取”、空值和纯空白限制为缺失身份，UI 只根据空 API 值显示占位文案
- 手机号与邮箱分别完成格式验证、规范化、去重后再做唯一性和歧义判断
- 手机号标签明确缺失时不再全文回退；无标签全文兜底排除日期、版本号和项目序号等数字噪声
- 增加 UTF-8 TXT 简历附件支持，并保持确认事务、一次性预览令牌、SHA-256 幂等和候选人匹配规则不变
- 不新增数据库迁移，不改写历史原始数据；既有错误预览需在新版本部署后重新上传

## 0.4 桌面软件封装评估

当前版本通过 `start.cmd` 启动本机服务，不是原生安装包。完成真实数据 PoC 后，再比较 Tauri、Electron 或受控浏览器壳的打包成本，重点验证自动更新、数据库备份、密钥存储和迁移兼容性。

## 1.0 部门多人版（独立项目门槛）

不能在当前个人版上简单修改监听地址后投入多人使用。至少需要：

- 统一身份认证或企业 SSO
- RBAC、字段级权限、操作人身份和不可伪造审计日志
- PostgreSQL 等集中数据库、对象存储和附件病毒扫描
- HTTPS、基于认证会话/token 的完整 CSRF 防护、HSTS/跨源隔离等多人版响应策略、速率限制和会话管理
- 部门/租户数据隔离、备份演练、监控告警和灾难恢复
- 批量写入、合并、删除、敏感字段修改的二次确认
- 中国个人信息保护相关的最小化、留存、导出、更正和删除流程

验收：安全评审、权限矩阵、恢复演练和真实负载测试全部通过后，才允许部门访问。
