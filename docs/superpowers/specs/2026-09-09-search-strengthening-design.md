# 人才检索全面增强设计（待审阅）

日期：2026-09-09。范围：候选人检索 API、全业务 FTS、Agent 检索工具和履历检索页面。
状态：设计草案；尚未实施、迁移或部署。本文以当前工作树为基线，保留已有未提交改动。

## 1. 目标

让用户用关键词、自然语言或岗位要求找到有真实证据支持的候选人。优先保证条件不被误解、遗漏，随后提升召回和排序。搜索结果辅助人工判断，不自动做招聘录用决定。

验收关注：条件正确率、Recall@50、nDCG@10、证据可追溯性、响应耗时、结果完整性和分页稳定性。不得将关键词命中分数显示成能力匹配百分比。

## 2. 已确认问题

2026-09-09 直接调用 normalizeResumeSearch 的只读探针，未连接数据库或模型：

| 上海 游戏策划 战斗系统 | 仅保留“游戏开发、上海” | 保留策划与战斗系统条件；地点含义可查看、调整 |

代码审查还发现：

- business-search 候选人快速路径按 FTS rowid 截取有限文档，再执行候选人条件和交集，存在漏召回风险，尚未实测发生比例。
- 职位描述和人才库描述可通过关系映射到候选人。这适合关系搜索，但不能证明候选人具备职位要求中的技能。
- 页面有真实证据高亮，但没有显示解析条件；直接显示内部表名、字段路径和原始分数。
- 页面初始状态与搜索无结果共用文案；需要区分首次搜索、无匹配、查询未完成和索引未就绪。
- App 向检索组件传递 positions 分页列表，职位筛选选项需要改成独立可检索的完整选项来源。

## 3. 方案选择

1. 只扩充词典：成本低，但不能解决条件逻辑、采样漏召回和证据归属问题。
2. 分层检索（推荐）：统一查询计划，结构化过滤、精确搜索、FTS 召回、候选人聚合与排序；再增加可选的模型理解及向量通道。每层可以单独验证和降级。
3. 立即替换为外部搜索/向量平台：部署、迁移和数据同步成本高，当前未证明必须更换 SQLite。

采用方案2。先交付本地检索正确性，再按相同评测集决定模型与向量通道的实际收益。

## 4. 查询理解契约

新增独立查询计划模块，供 API 和 Agent 复用：

- version、原始查询、解析来源（规则/模型/人工修正）。
- must、should、must_not：有界嵌套条件，支持 AND、OR、精确短语和排除条件；限制节点数量和深度。
- filters：年限区间与边界、当前所在地、意向地点、学历、公司、职位和人才库；已关联招聘职位与当前任职分开表达。
- 每个条件保留原始文本位置与解释，返回 unresolved 列表标出不能确定的内容。
- 中文剩余词不能因为命中词典而被整体丢掉。别名、上位概念与相关词分开：同义词可用于召回，相关词只用于明确标记的扩展。
- “不限年限”、范围、上下限、否定及中英技术词做确定性解析；模糊表达不得静默变成硬过滤。
- 年限未知与零不同；字段未知不能冒充满足条件。排除关键词只证明相应范围中未命中，不能推导现实中从未做过该工作。
- 模型只产出符合 JSON schema 的计划，不能提交 SQL；解析结果接受校验并在界面可见。模型不可用时返回规则结果和未解析项。

兼容既有 q、keywords、phrases、match_mode 和 filters。新计划增加版本标记；显式结构化条件优先，冲突必须可见。不改变原有敏感字段访问策略。

## 5. 召回、完整性与排序

### 本地基础层

- 精确查找支持姓名、编号和已获授权的联系方式，严格遵循现有字段政策。
- 先限定候选人范围，再检索其主档、履历、附件及来源字段；多条件允许在同一候选人的不同记录中成立。
- 将本人经历证据与职位/人才库等关联证据分开。能力条件默认需要本人证据；关系条件允许关联证据。
- 修复先截断原始文档再按候选人过滤的路径。按候选人范围、稀有条件驱动交集等方式控制成本，以执行计划及容量测试选型。
- 完整检索在资源预算内完成；超时返回明确的未完成状态。快速模式返回有界结果并显式标识完整性，不声称覆盖全库。
- 无精确结果时提供放宽建议，只有用户选择后才执行；不得暗中放宽必须或排除条件。

### 排序层

- 先执行硬条件，再按条件覆盖、证据归属、字段相关性、精确短语和 BM25 排序。
- 相同事实在主档、来源快照和附件中的重复出现不应无限加分。
- 新近经历作为可解释信号；导入更新日期不代表经历更新日期。
- 多路召回启用后采用 RRF 融合，候选集合有明确上限。语义相关度不等于候选人资格或能力分。
- 排序参数、查询计划、筛选条件和索引版本绑定游标；分页期间索引改变时提示重新检索，避免静默重复或遗漏。

### 可选语义层

- 对含岗位要求的长查询，模型提取条件；向量召回补充不同措辞的经历；重排只处理有界候选证据。
- 先确认现有网关的 Embedding/重排能力、模型、维度、批量上限、成本和候选人数据外发范围。
- 未确认前不调用外部向量服务、不批量发送简历、不启用全库向量回填。普通聊天可用不能证明支持 Embedding。
- 若网关不支持，另行评估本地模型的硬件占用与收益，不能自动下载大型模型。
- 向量按内容哈希增量维护，版本变化使用新索引，删除与归档行为同步处理。故障时明确回退本地检索。

## 6. 用户界面

- 搜索框支持自然语言和岗位要求，并显示“已理解的条件”：必须、优先、排除、结构化筛选及待确认项；条件可以编辑和移除。
- 结果卡片展示当前任职、关键履历摘要、条件命中/未知状态和原文证据。
- 来源使用“工作经历、项目经历、附件简历、关联职位”等业务名称；技术路径移入展开详情。
- 保留完整/有界/索引处理中等状态。无结果页面解释已执行条件并提供具体放宽选项。
- 条件变化重置分页；取消与请求序号控制避免旧结果覆盖新查询。查询条件和选项来源不依赖当前职位列表页。
- 支持打开候选人档案；复用现有用户确认的分组/职位关联流程。保存视图与收藏可在核心检索验收后补齐。
- 从 AssistantDrawer 中拆出检索面板，减少聊天任务与搜索状态相互耦合；优先使用独立样式，避免继续叠加全局覆盖。

## 7. 验证与交付

阶段A：建立基线与条件解析修复。包含上述6个复现问题、日期/年限歧义、中英混合、OR/NOT、精确短语、未知值及兼容 API 测试。

阶段B：召回与证据正确性。构造超过现有快速窗口的隔离数据，将唯一符合条件的候选人放在窗口之后；加入跨记录交集、关联职位伪技能、重复来源、归档/删除与分页案例。

阶段C：统一查询计划与交互。API、Agent 与界面共享语义；验证条件编辑、错误/空状态、取消、恢复和证据跳转。当前浏览器连接故障需要恢复后完成实际视觉与交互验收。

阶段D：可选语义增强。能力和外发范围确认后，在相同集合对比规则+FTS、增加语义召回、增加重排的增益，再决定启用配置。

评测采用至少60条匿名招聘查询、包含正例和困难负例的固定集合，明确 relevance 标注。解析与硬条件回归、证据归属测试要求全部通过；Recall@50、nDCG@10 先记录当前基线，增强版本不得降低总体指标，重点问题子集必须改善。额外记录零结果率，不能以放宽条件换取虚假改善。

性能在相同机器、隔离数据和冷热缓存下比较，记录 p50/p95、峰值内存和索引体积；覆盖1万及10万候选人。以本地关键词检索 p95 2秒、复杂条件5秒作为初始目标，实测达不到则说明原因和方案，不能报告未测结论。

运行相关 search/Agent/API 回归、完整 npm test、npm run build 和 diff 检查。测试不使用正式库、不自动重启服务。需要新增 schema 或索引时，另列迁移、空间评估和回退步骤后再安排正式部署。

## 8. 本轮待审阅决定

建议批准阶段A至C作为第一批实现：修正语义、保障召回完整性、改进排序和证据交互。阶段D属于完整路线，但其外部能力和数据处理范围尚未确认，不作为基础实现的前置阻塞。
