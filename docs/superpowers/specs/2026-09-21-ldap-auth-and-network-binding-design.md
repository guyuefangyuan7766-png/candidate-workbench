# LDAP 统一认证与受控网络监听：设计规范

适用版本：目标应用版本 `0.6.0`；主库保持 schema `V13`；认证数据使用独立 SQLite 文件，不进入主库迁移账本。

## 1. 背景与当前事实

项目要落到公司本地服务器上供招聘团队使用。当前代码在部署边界上有两个硬约束：

1. `server/index.mjs` 硬编码只允许 `127.0.0.1`、`localhost`、`::1`，非回环 `HOST` 直接抛错退出。
2. 全站没有任何身份概念。`server/app.js` 的业务路由一律直接执行，候选人列表、详情（含 `include_sensitive=true` 的未打码手机号/邮箱/薪资）、导出、附件下载、Agent 会话与全字段只读工具对任何能访问端口的客户端完全开放。

同时全仓 16 份文档都明确写着"没有认证、RBAC、不允许非回环监听"。因此本轮改造不是加一个功能，而是**改变产品的安全边界**，必须同时满足三个条件才算完成：

- 服务端具备真实身份认证，且默认拒绝匿名访问；
- 网络监听范围由配置显式声明，未声明时保持原有的回环限制；
- 全部相关文档同步改写，不再存在"系统没有认证"的过期陈述。

## 2. 目标与非目标

### 2.1 本轮（阶段 1）目标

- 接入公司 LDAP（`ldap.wan5d.com:389`）完成账号登录，账号来源唯一，不在本地维护密码。
- 服务端持久化会话，支持重启后继续使用、主动登出、按用户撤销。
- 允许在**显式配置**下监听内网地址，并在未鉴权时拒绝启动，杜绝"改个 HOST 就裸奔"。
- 业务 API、附件下载、导出、Agent 端点全部纳入鉴权保护；健康检查等极少数端点保持公开。
- 前端提供登录页、当前用户展示和登出。
- 默认关闭。未配置 LDAP 时行为与本轮之前完全一致，既有 741 项测试不需要因为本改造而修改。

### 2.2 明确不在本轮范围

| 项目 | 说明 |
| --- | --- |
| 角色与字段级权限 | 阶段 2。本轮所有登录用户权限相同，**不等价于可以交付部门使用**，见第 9 节准入判断 |
| LDAP 组到角色的映射 | 阶段 2。本轮不读取 `memberOf` 做授权决策 |
| 操作人审计 | 阶段 3。“谁导出了什么、谁删除了谁”当前仍无法回答 |
| 附件病毒扫描、集中对象存储 | 阶段 3 |
| HTTPS / 反向代理 | 由部署侧提供，本轮只提供配置要求与 `Secure` Cookie 开关 |
| 数据库静态加密、按用户留存 | 不在本改造范围 |
| 账号自助管理、密码修改、找回 | LDAP 负责，本应用不实现 |

## 3. 公司 LDAP 配置与现状澄清

用户提供的配置：

```go
LdapConf := ldapConfig{
    Host:   "ldap.wan5d.com",
    Port:   "389",
    BaseDn: "cn=%s,ou=People,dc=wooduan,dc=com",
    Attributes: ldapAttributes{
        UNameKey: "uid",
        NameKey:  "sn",
        EmailKey: "mail",
    },
}
```

映射到本应用的环境变量：

| LDAP 字段 | 值 | 对应环境变量 |
| --- | --- | --- |
| `Host` | `ldap.wan5d.com` | `LDAP_URL`（拼成 `ldap://ldap.wan5d.com:389`） |
| `Port` | `389` | 同上 |
| `BaseDn` | `cn=%s,ou=People,dc=wooduan,dc=com` | `LDAP_USER_DN_TEMPLATE` |
| `UNameKey` | `uid` | `LDAP_UID_ATTRIBUTE` |
| `NameKey` | `sn` | `LDAP_NAME_ATTRIBUTE` |
| `EmailKey` | `mail` | `LDAP_EMAIL_ATTRIBUTE` |

### 3.1 环境确认结论（2026-09-21）

四点由项目方确认如下，设计据此收敛：

| 编号 | 问题 | 确认结论 | 设计影响 |
| --- | --- | --- | --- |
| C1 | `cn=%s` 的 `%s` 是否为登录账号 | **是**。真实 DN 形如 `cn=zhangsan,ou=People,dc=wooduan,dc=com`，登录输入 `zhangsan` | **直接绑定确定为唯一认证路径** |
| C2 | `NameKey = sn` 的取值 | **暂不处理**，不作为登录或授权依据 | 显示名降级为外观问题，不阻塞认证 |
| C3 | 只读服务账号 | **后续再说** | 服务账号搜索模式移出本轮，接口保留但不实现、不启用 |
| C4 | 是否支持 LDAPS/STARTTLS | **没有 LDAPS，直接使用 389** | 明文 LDAP 为本轮既定事实，风险记录为 3.2 的显式例外 |

**由 C1 直接确定的认证路径**：登录标识规范化后替换 `LDAP_USER_DN_TEMPLATE` 的 `%s`，用用户密码对该 DN 执行一次 `bind`。绑定成功即认证通过，绑定失败即拒绝。**本轮不做任何前置搜索**，也不依赖 `LDAP_BIND_DN`。

**由 C2 确定的显示名策略**：认证与 `bind` 都不返回属性，因此在本轮没有服务账号的前提下，**无法可靠取得 `sn`、`cn` 或 `mail`**。设计选择是：

1. 首次登录时做**一次 best-effort 匿名搜索**（`LDAP_ATTRIBUTE_LOOKUP=anonymous|off`，默认 `off`）。仅在目录允许匿名读取时才会成功，成功则缓存显示名与邮箱。
2. 未取得属性时，`display_name` 回退为**登录标识本身**（界面右上角显示 `zhangsan` 而不是「张」）。
3. 属性读取失败**不得影响登录结果**。该路径是纯外观增强，任何异常都被吞掉并降级。

在获得服务账号后（C3），把 `LDAP_ATTRIBUTE_LOOKUP` 升级为 `service` 即可读取真实属性，这是阶段 2 的可选增强，不改变认证流程。

**由 C4 保留的后续项**：账号停用与离职检测在本轮无法实现——直接绑定只返回成功或失败，服务端读不到 `shadowExpire`、`accountStatus` 或组关系。**本轮接受该限制**，并明确：离职账号在 LDAP 侧被删除或禁用后，其登录会自然失败；但已建立的会话在有效期内仍然可用，因此运维必须在人员离职时执行会话撤销（见 4.2 节）。若公司目录的停用方式是"保留账号但禁止绑定"，则登录会被正确拒绝；若停用表现为"仍可绑定但不可登录其他系统"，本轮无法识别，需要在阶段 2 随组映射一并解决。

### 3.2 传输安全

`389` 是明文 LDAP，用户密码以可读形式经过网络。同网段嗅探即可还原凭据。

C4 已确认本轮没有 LDAPS。设计按"已知并接受的例外"处理，而不是假装它是安全的：

**配置**：

- `LDAP_URL=ldap://ldap.wan5d.com:389`，`LDAP_ALLOW_PLAINTEXT=true` 为显式设置项。代码保留对 `ldaps://` 与 STARTTLS 的支持，但本轮不启用，也不作为交付条件。
- 启动时打印一条不含凭据的告警：`LDAP 明文连接已启用`。该告警保留在日志中，作为后续升级加密的提醒，不静默通过。
- 服务端只把密码用于一次绑定，不落盘、不写日志、不进会话表。

**必须同时满足的补偿控制**（写进部署检查清单）：

1. **服务端到 LDAP 的链路必须是受控内网**，不得经过不可信网段或公网。若 `ldap.wan5d.com` 解析到办公网且与服务器同网段，可接受。
2. **浏览器到应用的链路必须 HTTPS**。明文 LDAP 已经让凭据在服务端到目录这一段可读；如果浏览器到服务端也是明文 HTTP，密码会在客户端到服务端这一段再暴露一次，叠加后风险不可接受。因此：明文 LDAP 与 `AUTH_COOKIE_SECURE=false` **不得同时存在**于面向他人开放的部署中。
3. 服务器本身按高敏感主机管理：全盘加密、限定登录账户、机房受控、杀毒白名单按 [部署手册](../../DEPLOYMENT_LOCAL_SERVER.md) 执行。
4. 该例外的有效期与责任人需由信息安全确认，并在获得 LDAPS 或 STARTTLS 能力后立即切换（配置改动即可，无代码改动）。

## 4. 认证流程设计

### 4.1 登录

```text
浏览器                Express                     LDAP                auth.db
  |                     |                          |                    |
  |-- POST /api/auth/login (username, password) -->|                    |
  |                     |-- 规范化 username ------>|                    |
  |                     |-- 拼 DN: cn=<name>,ou=People,dc=wooduan,dc=com  |
  |                     |-- 该 DN + 用户密码 bind ->|                    |
  |                     |<-- 绑定成功/失败 ---------|                    |
  |                     |-- [可选] 匿名读属性 ---->|                    |
  |                     |-- upsert 账号记录 --------------------------->|
  |                     |-- 创建会话(token 哈希) ---------------------->|
  |<-- Set-Cookie + 用户信息 ----------------------|                    |
```

关键规则：

- 绑定失败一律返回统一的 `401 invalid_credentials`，不区分"用户不存在"与"密码错误"，避免账号枚举。
- LDAP 服务不可达、超时、返回异常时返回 `503 auth_backend_unavailable`，与凭据错误区分，便于排障。
- 单次绑定超时默认 8 秒（`LDAP_TIMEOUT_MS`），防连接挂死。
- 登录标识先规范化：去首尾空白、去 `WOODUAN\` 之类域前缀、限长、拒绝空值；规范化结果同时作为 DN 的 `%s` 与账号唯一键。
- DN 拼装前对标识做 RFC 4514 转义，避免特殊字符改变 DN 结构。
- 属性读取（`LDAP_ATTRIBUTE_LOOKUP=anonymous`）是可选增强：失败、超时、目录不允许匿名读取时一律降级为"显示名 = 登录标识"，**不改变登录结果，不返回错误**。
- 绑定成功后按 `auth_users` 唯一键（规范化后的 `uid`）插入或更新账号，记录 `last_login_at`。
- 登录成功后创建会话，写入 Set-Cookie 后立即返回当前用户信息，前端不再多发一次请求。

### 4.2 会话

| 项目 | 设计 | 原因 |
| --- | --- | --- |
| 会话标识 | 32 字节随机数的 hex | 不可预测 |
| 存储 | 只存 `SHA-256(token)` | 数据库或备份泄露不能直接冒充登录 |
| Cookie | `HttpOnly` + `SameSite=Lax` + `Path=/` | 阻断 JS 读取与跨站携带 |
| `Secure` | 由 `AUTH_COOKIE_SECURE` 控制，HTTPS 部署必须为 `true` | 明文 HTTP 下无法使用 Secure |
| 空闲期限 | 默认 12 小时，命中时滑动续期 | 工作日体验与安全平衡 |
| 绝对期限 | 默认 30 天（`AUTH_SESSION_ABSOLUTE_TTL_MS`） | 限制长期有效凭据 |
| 登出 | 撤销当前会话行 | 立即生效 |
| 撤销全部 | `AUTH_SESSION_REVOKE_ALL` 启动开关，撤销指定用户全部会话 | 应急 |
| 清理 | 启动时与每小时清理过期行 | 避免表无限增长 |
| CSRF | `SameSite=Lax` + 对写请求校验 `Origin`/`Referer` 与请求 Host 同源 | 不引入额外 token 复杂度 |

会话保存在 `auth.db`，服务重启不影响登录状态。

**LDAP 不可用时的行为**：LDAP 只参与登录。目录不可达时新登录返回 `503`，**已建立且未过期的会话继续可用**，候选人管理、检索与导入导出不受影响。这一取舍避免目录抖动导致业务整体中断；代价是撤销权限只能在会话到期或主动撤销后生效，因此人员离职必须执行撤销操作。

### 4.3 鉴权边界

| 路径 | 是否鉴权 | 说明 |
| --- | --- | --- |
| `GET /api/health` | 公开 | 仅返回存活状态和版本，供负载均衡与监控探测 |
| `POST /api/auth/login` | 公开 | 登录入口，自身按 IP 限流 |
| `POST /api/auth/logout` | 需要会话 | |
| `GET /api/auth/session` | 需要会话 | 未登录返回 401，前端据此渲染登录页 |
| `GET /api/auth/me` | 需要会话 | 当前用户信息 |
| `GET /api/*`（其余全部） | 需要会话 | 缺少或失效会话返回 401 `authentication_required` |
| 静态资源与 SPA 回退 | 公开 | 前端自身不承载数据，登录页由前端渲染 |
| 非 `/api` 路径 | 公开 | 同上 |

鉴权以**路由前缀白名单**实现（默认保护 `/api`，开放显式列出的少数端点），而不是逐条路由添加中间件。这样新增业务 API 时默认是受保护的，漏加中间件的风险更低。

### 4.3.1 账号白名单（2026-09-21 补充确认）

2026-09-21 确认采用**账号白名单**：只有显式列出的账号可以使用本系统。这条把"任何持 LDAP 账号者都能看全部数据"的敞口收窄为"仅被授权的账号可访问"，是本轮唯一的一层授权控制。

**配置载体是文件，不是环境变量。** 这一点在 2026-09-21 的设计复核中被修正：Node 的 `process.env` 在进程启动后不会跟随系统环境变量变化，`setx` 修改的内容对**已经在运行**的服务不可见。因此"改环境变量后 30 秒生效"在技术上无法成立，只能重启。白名单又是需要随人员入转调离频繁变更的数据，不应该每次都重启服务。

改为：

| 载体 | 用途 |
| --- | --- |
| `data/auth-allowlist.txt`（路径由 `AUTH_ALLOWLIST_FILE` 指定） | **正式名单**。一行一个登录名，`#` 开头为注释，忽略空行与 BOM，大小写不敏感。服务端每 30 秒重新读取，无需重启 |
| `AUTH_ALLOWED_USERS`（环境变量） | 可选的启动引导值，逗号分隔。仅在名单文件不存在时生效，便于首次启动 |

| 取值 | 行为 |
| --- | --- |
| 文件不存在且环境变量为空 | 不启用白名单，所有通过 LDAP 认证的账号均可登录（**默认行为，兼容无白名单部署**） |
| 文件存在且非空 | 只有列入的登录名可通过；其余即使凭据正确也被拒绝 |
| 文件存在但为空（或只有注释） | **拒绝所有登录**，并打印明确告警。空名单按"谁都不能进"处理，避免因误删内容而意外放开 |
| 文件读取失败（权限、被占用） | 保留上一次成功读取的名单继续生效，打印告警。不静默退化为"允许所有人" |

**判定顺序与错误码**（顺序不能颠倒）：

1. 先完成凭据校验。LDAP 绑定失败 → `401 invalid_credentials`，不因白名单而改变，避免泄露账号是否存在。
2. 绑定成功后检查白名单。不在名单内 → `403 account_not_authorized`，提示"账号未获授权使用该系统"。
3. 白名单通过但 `auth_users.is_active = 0` → `403 account_disabled`。

先验证凭据再判白名单的顺序是刻意的：调用方只有在已经证明自己持有该账号密码的前提下，才能得知"账号存在但未获授权"。这既提供了可理解的失败原因，也不构成未认证的账号枚举。

**有效性检查贯穿会话生命周期，而不只在登录时**：每次请求解析会话时都重新判定白名单与 `is_active`。因此从白名单中移除某人后，**其已建立的会话在下次请求即失效（401）**，不需要等他登出或会话过期。这弥补了"LDAP 侧停用无法识别"留下的缺口——离职或转岗时，从白名单移除是即时生效的动作。

**实现要点**：

- 由定时器每 **30 秒** 重新读取名单文件。变更后**无需重启服务，最迟 30 秒生效**；这是对运维的明确承诺，实施时以该数值为准。
- 名单变更流程对维护者只有一个动作：编辑 `data/auth-allowlist.txt`。文件需与数据库同样纳入权限保护（限定服务账户与管理员读写）。
- 登录成功时把这次判定结果写入会话；每次请求仍按上述规则重新判定，不缓存"曾通过"。
- **不需要重启服务、不需要修改代码或数据库。**

**与阶段 2 的关系**：白名单是"谁能进"，RBAC 是"进来后能看哪些字段"。白名单不能替代字段级权限——名单内的 15 人仍然都能看到全部敏感字段。阶段 2 应把白名单平滑升级为基于 LDAP 组的角色映射，届时该名单文件机制作为紧急兜底继续保留。

### 4.4 登录限流

**分两层，阈值不同。** 来源网段不做限制、且公司内网机器普遍不启用系统防火墙的情况下，如果只按 IP 计数，同一出口 NAT 后的多人会互相拖累：一个人输错 5 次就会把整个部门锁在门外。因此：

| 维度 | 阈值 | 窗口 | 作用 |
| --- | --- | --- | --- |
| 账号（`username`） | 5 次失败 | 5 分钟 | 主防线，阻止针对单个账号的暴力破解 |
| 来源地址（`client_ip`） | 30 次失败 | 1 分钟 | 次级防线，只拦截明显异常的高频尝试，不因正常输入失误误伤 |

计数保存在内存，重启即清空，不写数据库。超过阈值返回 `429 auth_rate_limited` 与 `Retry-After`。成功登录只清空该账号的计数，不重置同一来源地址下其他账号的计数。

反向代理部署时，`client_ip` 取自 `X-Forwarded-For` 中最左侧的可信地址（见 5.4）；未启用 `AUTH_TRUST_PROXY` 时该字段恒为 `127.0.0.1`，IP 层限流会退化为全局限流，这也是 5.4 要求该开关与代理解析配对的原因。

## 5. 监听边界改造

### 5.1 现状

```js
const loopbackHosts = new Set(['127.0.0.1', 'localhost', '::1'])
if (!loopbackHosts.has(host.toLowerCase())) {
  throw new Error('个人版仅允许监听本机地址')
}
```

### 5.2 新规则

绑定地址分两种模式，由配置决定，**默认仍是回环**：

| 模式 | 触发条件 | 行为 |
| --- | --- | --- |
| 个人模式（默认） | 未设置 `AUTH_ENABLED` | 只允许回环地址，与本轮之前完全一致 |
| 受控网络模式 | `AUTH_ENABLED=true` | 允许 `AUTH_BIND_HOSTS` 白名单内的地址，默认白名单为 `127.0.0.1,::1` |

启动校验顺序（任一不满足即拒绝启动并打印原因）：

1. `HOST` 必须是字面 IP（不接受主机名，避免 DNS 解析带来的不确定性）。
2. 回环地址始终允许。
3. 非回环地址必须同时满足：`AUTH_ENABLED=true`、位于 `AUTH_BIND_HOSTS` 白名单、配置了 LDAP、`AUTH_ALLOW_NON_LOOPBACK=true`。
4. 非回环且 `AUTH_COOKIE_SECURE=false` 时打印显著告警。

**任何单个开关都不足以放开监听**，避免误配置直接暴露。

### 5.3 CORS 同源调整

现有 `setCors` 只放行回环来源，局域网访问会被拒绝。改为：请求 `Origin` 与请求自身 `Host` 同源时允许；其余跨站来源仍需显式配置 `CORS_ORIGIN`。这一改动同时构成 CSRF 的第一层防护。

### 5.4 本次部署形态：反向代理 + 回环绑定（2026-09-21 确认）

运维侧提供 HTTPS。这带来一个比"放开监听"更好的结果：**应用本身仍然只绑 `127.0.0.1:4173`，由反向代理终止 TLS 并转发**。

```text
浏览器  --HTTPS-->  反向代理（公司证书）  --HTTP/回环-->  127.0.0.1:4173  Express
```

由此确定的部署要求：

1. **`AUTH_ALLOW_NON_LOOPBACK` 保持 `false`，`AUTH_BIND_HOSTS` 保持默认**。受控网络模式的实现仍然要做（防御"以后图省事直接绑内网 IP"），但本次部署不启用它。这比直接暴露端口少一整类风险。
2. **`AUTH_COOKIE_SECURE=true` 必填**。浏览器侧已经是 HTTPS，会话 Cookie 必须带 `Secure`。
3. **必须正确解析代理转发头**。否则服务端会把所有请求的来源都看成 `127.0.0.1`，导致登录限流把 15 个人算成同一个人、`client_ip` 记录全部相同、后续审计失真。
   - 新增 `AUTH_TRUST_PROXY`（默认 `false`）：置 `true` 时启用 Express `trust proxy`，只信任来自回环/代理地址的 `X-Forwarded-For` 与 `X-Forwarded-Proto`。
   - 该开关在无反代场景下**不得开启**，否则客户端可伪造来源 IP 绕过限流。
4. 反向代理需转发 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto`，并对 `/api/attachments/:id/download` 与导出接口关闭缓冲或放宽超时（导出最大 64 MB，默认代理超时可能不足以覆盖大文件与长检索）。
5. 仍然只支持单实例：会话与限流计数是单进程/单库状态，多实例部署需要共享存储，当前明确不支持。

### 5.5 并发规模与容量基线（15 人）

2026-09-21 确认目标为 **15 名并发使用者**。按 15 人分摊在不同操作上估算峰值：

| 操作 | 占比估计 | 说明 |
| --- | --- | --- |
| 列表浏览、筛选、翻页 | 多数 | 单次 < 1 秒，SQLite 只读，压力小 |
| 打开候选人详情（含敏感字段） | 中 | 单次 < 2 秒 |
| 履历检索（混合检索） | 少数但最重 | 单次 5–20 秒，且占用一个检索 worker 与一次模型网关调用 |
| AI 助手提问 | 少数但最重 | 单进程默认只允许 2 个任务同时运行，其余排队 |
| 导入 / 导出 | 低频 | 写入期与检索争用 SQLite |

按最坏情况估算，15 人同时使用时的瞬时并发请求约 3–6 个，其中同时发起重检索约 2–4 个。这个量级不需要改架构，但**需要调整现有的保守默认值**，否则会出现"能用但总在排队"：

| 参数 | 当前默认 | 15 人建议 | 上限 | 说明 |
| --- | --- | --- | --- | --- |
| `AGENT_MAX_CONCURRENT_TASKS` | 2 | 4 | 8 | 每增加一个并发任务会多一个只读 worker 进程，需同步观察内存 |
| `AGENT_MAX_QUEUED_TASKS` | 20 | 30 | 100 | 超出返回 `task_overloaded` |
| `HybridSearchService.maxConcurrent` | 2 | 4 | 8 | 超过后返回 429 `search_busy`，这是 15 人场景最先撞到的限制 |
| `HybridSearchService.maxQueued` | 8 | 16 | 32 | |
| `SEARCH_VECTOR_MAINTENANCE_CONCURRENCY` | 4 | 4 | — | 维护每个开机周期只跑一次，不需要为并发调高 |

调参原则：

1. **先按默认上线，观测一周再调**。上面的建议值是基于 15 人并发估算的上限参考，不是必须一次性写死的配置。
2. 调高 Agent 并发前先确认内存余量：每个并发任务都可能拉起独立的只读 SQLite worker，叠加 39 GB 主库与 6.3 GB 向量索引的页缓存需求。
3. 若 `search_busy` 频繁出现，优先排查模型网关延迟（单次 5–20 秒主要来自网关），而不是继续加大并发——并发越高，排队时间越长。
4. 15 人规模下**单实例足够**，不需要引入队列中间件或多进程；但硬件必须按 [部署手册](../../DEPLOYMENT_LOCAL_SERVER.md) 调整：15 人规格为 16 核 / 64 GB 内存 / 1 TB NVMe，笔记本级 8 核 / 16 GB 不能满足。

### 5.6 来源网段

2026-09-21 确认：**允许所有内网 IP 访问，不设置来源网段白名单**。公司内网 Windows 机器通常不启用系统防火墙，也不按部门做网络层隔离。因此：

- 不需要维护来源 IP 白名单，也不启用 `AUTH_BIND_HOSTS`。
- 应用仍只监听回环，唯一入口是公司反向代理；网络层不构成访问控制。

**这条确认有一个必须写清楚的后果**：访问控制完全落在账号层，而"认证"不等于"授权"。

| 环节 | 现状 |
| --- | --- |
| 能不能打开这个页面 | 任何能访问公司内网的人都可以 |
| 能不能登录 | 只有持有有效 LDAP 账号的人可以 |
| 登录后能看到什么 | **全部**。当前没有角色与字段级权限，任何能登录的员工都能查看 14 万份候选人档案，包括未打码手机号、邮箱、薪资、评估与简历正文 |

也就是说，**只要拥有公司 LDAP 账号并知道系统地址，就能看到全部候选人敏感数据**，不限于招聘部门。由此产生的操作要求：

1. 系统地址按内部信息管理，不写入对外文档、不投放到公共门户，避免扩大非目标人群的接触面。
2. **本场景不能只靠认证。** 已确认补充账号白名单（见 4.3.1），把"任何持 LDAP 账号者"收窄为"白名单内的账号"；但白名单是"谁能进"，不是"进来能看哪些字段"。阶段 2 的 RBAC 仍然是必需项，只是紧迫度从"上线前必须"降为"扩围前必须"——判断依据见规范 9.3 与 [ROADMAP](../../ROADMAP.md)。
3. 这同时说明为什么不能依赖网络层兜底：既然内网不设防、防火墙默认开放，边界只能建在应用里。

**仍需传达给网络运维的前提**：`ldap.wan5d.com` 必须与服务器同处受控内网。既然本轮使用 `389` 明文，服务器一旦被迁到 DMZ、云主机或任何需要经公网访问目录的位置，凭据即泄露。

**验收补充**：从另一台内网机器直接访问服务器 IP 的 `4173` 端口应当失败（证明应用未直接暴露），只能通过代理地址访问。

### 5.7 域名与访问地址（2026-09-21 提出）

系统需要一个固定的内网访问地址，而不是让使用者记 IP 和端口。域名选择有一条容易忽略但重要的约束。

**域名已确定：`talent.wooduan.com`（2026-09-21）。**

对应的约束是：**该主机名在公网 DNS 上不得解析到任何可达地址**。用已备案的公开域名做内网服务的名字是常见做法，而且能直接复用 `*.wooduan.com` 通配证书（这也正是项目方选择它的理由）；风险不在"用了公开域名"，而在"公网侧留下了可达记录"。

原因是具体的，不是教条：

1. `wooduan.com` 与 `wan5d.com` 都是公开可解析的域名（2026-09-21 实测：`wooduan.com → 47.111.98.111`）。子域名同样可被枚举，猜测 `talent.wooduan.com` 的成本极低。
2. 一旦公网存在指向内网地址的记录，**等同于对外公告"这里存放着 14 万份候选人档案、支持 LDAP 登录"**，即使记录指向的是 RFC1918 地址，记录本身也已经是可被搜索到的事实，并可能被当作探测目标。
3. 若公网侧完全不解析该主机名，则上述问题不存在，用哪个后缀反而是次要的。

推荐做法：

| 项目 | 要求 |
| --- | --- |
| 域名 | **`talent.wooduan.com`** |
| DNS | 只在公司内网 DNS（或内网视图/分裂解析）中解析到反向代理的内网地址；**公网 DNS 不得创建 A/AAAA 记录**，包括指向测试地址的历史记录 |
| 证书 | 复用 `*.wooduan.com` 通配证书，或为 `talent.wooduan.com` 单独签发；**不要用自签名证书**，否则浏览器告警会促使使用者绕过校验 |
| 访问方式 | 使用者一律通过 `https://talent.wooduan.com` 访问；禁止提供"IP 直连"的入口 |
| 80 端口 | 必须 301 跳转到 443，或直接不监听。**明文 HTTP 入口与明文 LDAP 叠加会把密码在两段链路上各暴露一次** |
| 客户端 DNS | 使用者必须走公司内网 DNS；对外网 DNS 有解析记录的终端需确认不会解析到其他地址 |

**配置影响**：应用不需要知道自己的对外域名。前端所有 URL 都基于 `window.location.origin` 生成，服务端不生成绝对链接，因此无需新增 `PUBLIC_BASE_URL`。需要配合的只有两点：

1. `setCors` 的同源判定以请求自身 `Host` 为准，域名更换无需改代码；若代理没有正确转发 `Host`，同源判定会失效，因此 5.4 要求转发 `Host` 是硬条件。必要时可用现有 `CORS_ORIGIN` 显式追加该来源作为兜底。
2. 会话 Cookie 为来源站点作用域，域名一旦确定后应保持稳定。**中途更换域名会使所有已登录会话失效**（Cookie 不带过去），这属于预期行为，但需要安排在变更窗口内。

## 6. 数据模型

### 6.1 为什么使用独立数据库

认证表**不放进主库**，理由是具体的：

1. 主库维护着一套被文档与测试严格断言的 `schema_migrations` 版本链（当前 V1–V13）。新增版本号会与既有断言冲突，需要连带修改多处历史证据描述。
2. `tests/backend/database-migration-idempotence-v9.test.mjs` 断言迁移快照精确等于 `[1..13]`，把认证表塞进主库会污染这一不变量。
3. 认证数据的生命周期与业务数据不同：可以整体清空重建，也可以单独撤销，不需要与候选人数据同步迁移。
4. 备份粒度更清晰：业务库是必须备份的数据资产，`auth.db` 是可重建的会话状态。

代价是备份范围必须包含该文件，已写入 [部署手册](../../DEPLOYMENT_LOCAL_SERVER.md) 的备份清单。

### 6.2 表结构

文件：`data/auth.db`（路径可配置，默认与主库同目录）。

```sql
CREATE TABLE IF NOT EXISTS auth_users (
  id             TEXT PRIMARY KEY,
  username       TEXT NOT NULL UNIQUE,  -- 规范化登录名，LDAP uid
  ldap_dn        TEXT NOT NULL,         -- 登录验证时使用的真实 DN
  display_name   TEXT,                  -- 来自 LDAP_NAME_ATTRIBUTE 候选链
  email          TEXT,
  role           TEXT NOT NULL DEFAULT 'member',  -- 阶段 1 仅记录，不作为授权依据
  is_active      INTEGER NOT NULL DEFAULT 1,
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL,
  last_login_at  TEXT
);

CREATE TABLE IF NOT EXISTS auth_sessions (
  id             TEXT PRIMARY KEY,
  token_hash     TEXT NOT NULL UNIQUE,
  user_id        TEXT NOT NULL REFERENCES auth_users(id) ON DELETE CASCADE,
  created_at     TEXT NOT NULL,
  last_seen_at   TEXT NOT NULL,
  expires_at     TEXT NOT NULL,
  absolute_expires_at TEXT NOT NULL,
  revoked_at     TEXT,
  user_agent     TEXT,
  client_ip      TEXT
);

CREATE INDEX IF NOT EXISTS auth_sessions_user_idx ON auth_sessions(user_id);
CREATE INDEX IF NOT EXISTS auth_sessions_expiry_idx ON auth_sessions(expires_at);
CREATE INDEX IF NOT EXISTS auth_users_username_idx ON auth_users(username);
```

字段说明：

- `token_hash` 存 SHA-256；不存可用的会话明文。
- `role` 本轮固定为 `member`，字段先建好，避免阶段 2 再加迁移。
- `client_ip` 只存用于排障的地址，不解析为地理位置；不在界面展示。
- 不存储任何密码、密码哈希或与 LDAP 凭据相关的派生值。

### 6.3 表结构初始化

不使用主库的迁移框架，改为在 `ServerAuthStore` 构造时执行上面的 `CREATE TABLE IF NOT EXISTS`（幂等），并写入 `auth_meta` 表记录 `schema_version = 1`，供阶段 2 做加法迁移。

启动时打印一行认证摘要：认证开关、DN 模板是否就绪、属性读取模式、加密方式（含明文告警）、是否允许非回环、绑定地址、会话期限。**不打印密码、不打印完整 DN 列表、不打印服务账号、不打印会话密钥**。

## 8. 接口契约

| 方法 | 路径 | 鉴权 | 请求 | 成功响应 |
| --- | --- | --- | --- | --- |
| `GET` | `/api/health` | 否 | — | `{ status, service, timestamp }` |
| `POST` | `/api/auth/login` | 否 | `{ username, password }` | `200` + Set-Cookie + `{ user }` |
| `POST` | `/api/auth/logout` | 是 | — | `204` + 清除 Cookie |
| `GET` | `/api/auth/session` | 是 | — | `{ user, expires_at }` |
| `GET` | `/api/auth/me` | 是 | — | `{ user }` |

用户对象投影（**不含任何 LDAP 属性原文、不含 DN、不含密码相关字段**）：

```json
{
  "id": "uuid",
  "username": "zhangsan",
  "display_name": "张三",
  "email": "zhangsan@wooduan.com",
  "role": "member"
}
```

错误码：

| 场景 | 状态 | 错误码 |
| --- | --- | --- |
| 未登录访问受保护接口 | 401 | `authentication_required` |
| 会话过期或已撤销 | 401 | `session_expired` |
| 凭据错误 | 401 | `invalid_credentials` |
| 凭据正确但不在账号白名单 | 403 | `account_not_authorized` |
| 账号被标记为停用 | 403 | `account_disabled` |
| LDAP 不可达或超时 | 503 | `auth_backend_unavailable` |
| 登录过于频繁 | 429 | `auth_rate_limited` |
| 请求体缺少字段 | 422 | `validation_error` |

前端在任意接口收到上述 401 时统一回到登录页，并保留原始路径以便登录后跳回。

> 关于 `account_disabled`：直接绑定无法从目录侧识别"账号被停用"与"密码错误"，因此 LDAP 返回的失败统一按 `invalid_credentials` 处理，避免泄露账号是否存在。本轮的 `account_disabled` 只由应用侧白名单机制的 `auth_users.is_active = 0` 触发（见 4.3.1），不代表目录状态。

## 9. 安全影响与准入判断

### 9.1 本改造解决的问题

- 匿名访问：解决。所有业务 API、导出、附件下载、Agent 端点都需要有效会话。
- 局域网暴露：受控。必须多个开关同时显式配置才能绑定非回环地址。
- 凭据管理：账号与密码由公司 LDAP 统一管理，应用不维护密码。
- 会话盗用：会话 token 只存哈希，Cookie 设置 HttpOnly 与 SameSite。

### 9.2 本改造**没有**解决的问题

以下缺口在阶段 1 完成后依然存在，**不能因为"有了登录"就认为可以交付部门使用**：

| 缺口 | 后果 |
| --- | --- |
| 没有角色与字段级权限 | **白名单内的每个账号**都能看到全部 14 万份候选人档案，包括未打码手机号、邮箱、薪资、评估和简历正文（白名单解决"谁能进"，不解决"进来能看什么"） |
| 没有操作人审计 | 无法回答"谁导出了什么、谁删除了谁" |
| 数据库与备份仍是明文 | 服务器或备份介质失窃即等同于数据泄露 |
| 没有附件病毒扫描 | 简历附件解析仍是本机单用户假设下的边界 |

> HTTPS 不在缺口清单内：C7 已确认由运维侧反向代理提供，属部署前置条件而非系统缺口。落地要求见 5.4。

### 9.3 可以交付使用的判断标准

| 使用范围 | 阶段 1 之后是否可行 |
| --- | --- |
| 单人在服务器上通过 RDP 使用 | 可行 |
| 少量授权招聘人员在内网使用（本次目标 15 人，已启用账号白名单收窄到具体人），且已接受"白名单内所有账号可看全部字段" | **需要公司信息安全与法务书面确认**，并完成 HTTPS（C7 已具备）与备份加密 |
| 全部门开放 | 不可行，必须先完成阶段 2（RBAC + 字段级权限）与阶段 3（审计 + 加固） |

这条判断必须写入产品文档和部署文档，避免"已经有登录了"被误读为"可以开放了"。

## 10. 前端设计

### 10.1 登录页

- 独立于既有工作台布局的全屏居中卡片，不渲染主导航。
- 字段：账号、密码、登录按钮；Enter 提交；提交中禁用并显示加载状态。
- 错误显示：凭据错误、限流、LDAP 不可达三类文案区分，但不回显账号是否存在。
- 视觉沿用现有 token（冷白表面、`--primary` 蓝色主操作、8px 圆角），不引入新配色体系。
- 顶部显示"使用公司 LDAP 账号登录"，让用户明确账号来源。

### 10.2 会话与登录态

- 应用启动先请求 `/api/auth/session`：通过则渲染工作台，401 则渲染登录页。
- 登录成功后跳回原始路径（含工具页与职位详情路径）。
- 侧栏底部显示当前用户显示名与登出入口；登出后回到登录页并清空前端缓存的业务数据。
- 任意业务请求返回 401 时，统一触发登出流程回到登录页，不静默失败。

### 10.3 不改动的内容

信息架构、导航表面状态机、列表与详情布局、AI 助手会话结构都在本轮保持不变。登录页是唯一新增的顶层表面。

## 11. 迁移、兼容与回滚

| 项目 | 结论 |
| --- | --- |
| 主库 schema | 不变，仍为 `V13` |
| 认证库 | 新建 `data/auth.db`，幂等建表，可删除重建 |

## 12. 阶段划分

| 阶段 | 内容 | 出口条件 |
