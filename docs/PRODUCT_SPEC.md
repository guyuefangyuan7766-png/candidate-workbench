## 产品定位

当前产品是个人使用的“候选人档案 + 人才检索 + 职位关联”人才库，核心对象为：

1. 候选人资料。
2. 人才库分组及候选人与人才库的关联。
3. 招聘职位及候选人与职位的关联。
4. 候选人的履历、偏好、来源、历史评估和授权记录。

人才库用于长期分类和沉淀，职位用于筛选、分组和整理候选人。产品不是完整 ATS，不提供可运行的职位申请、按职位独立招聘阶段、面试排期、评价、Offer 审批或入职流程。北森历史面试和测评数据只作为只读档案记录保留。

`candidates.current_title` 是候选人当前任职；`positions.title` 是本平台管理的招聘职位。二者含义不同，不能互相覆盖。只有文件中显式映射为招聘职位的字段才参与职位匹配、创建和关联。

## 用户与使用场景

当前唯一目标用户是一名在受控 Windows 电脑上整理招聘数据的招聘人员。典型场景包括：

1. 手工建立、查找和维护候选人档案。
2. 从自有表格或北森合法导出的稳定 ID 表格预览并导入候选人，并可按同一 `应聘者ID` 分批补充资料。
3. 创建招聘职位，按状态、部门、地点和负责人维护职位。
4. 建立人才库分组，将候选人加入一个或多个长期人才分类。
5. 将候选人关联到一个或多个招聘职位，并从候选人或职位两侧查看关系。
6. 按人才库、学历、学校、专业、求职状态、职位、来源、负责人、标签和归档状态筛选候选人。
7. 导出当前筛选结果或某一职位下的候选人用于核对。
8. 在明确启用模型网关后，用全量只读 Agent 按需查询 SQLite 任意目录内表和字段，包括未打码敏感字段、完整履历与来源原始数据。
9. 上传本地简历附件，核对手机号/邮箱定位、字段差异和证据后，由用户确认更新并保存附件。

当前版本不是部门共享服务。

## 产品目标

- 候选人和职位数据由使用者控制，不依赖付费招聘 SaaS 才能访问。
- 候选人库是主要工作界面，人才库分组和职位都是一级筛选与关联对象。
- 导入必须先预览，重复和身份冲突必须可见，绝不只按姓名合并。
- 候选人、人才库和职位误操作优先通过软归档与恢复处理。
- 关联和解除只改变关系，不复制或删除候选人、人才库或职位主记录。
- Agent 与业务写连接/API 隔离；数据库可扫描全量记录，但模型只接收当前问题所需的分页、聚合或 Top-K 结果。
- 为以后桌面软件封装和部门多人版保留明确升级边界。

### 界面结构与容器规则

- 一个逻辑内容组默认只保留一个视觉容器。仅用于包裹单个标题、文本或按钮的 border、background、radius 和 padding 应删除；代表独立卡片、独立交互区、滚动区、弹层、空态或错误态的容器可以保留。
- “添加跟进备注”只保留标题、textarea 输入边界和按钮；textarea 是唯一输入框体，外层 section 与 composer 不承担第二层框体。
- AI 助手桌面正文列最大宽度为 `760–880px`；主导航与历史栏不能同时显示，历史入口固定在页面左上角；助手消息不套重边框卡片，用户消息可右对齐并使用克制气泡。执行过程只展示服务端已记录的动作、工具、状态和耗时。
- 输入表单、textarea 与发送按钮共享一个完整输入表面，发送按钮位于表面内部并使用现有 Lucide 图标，禁止输入框、按钮、外层表单和外层卡片形成多层边框。
- 永久无效的隐藏组件必须完成代码引用和浏览器 DOM 审计后才能删除；无障碍隐藏内容、响应式列、交互状态、加载/空态/错误态、确认弹窗和用户可展开区域继续保留。

## 关键业务规则

### 身份与去重

- 候选人身份键为标准化邮箱、标准化电话、`source_system + source_record_id`。
- 姓名只用于显示和搜索，不作为自动合并依据。
- 多个身份键命中不同候选人时返回 `identity_conflict` 并拒绝自动更新。
- 职位关联不参与候选人身份判断；关联同一职位不会创建候选人副本。

### 职位与关联

- 职位状态为 `draft`、`open`、`paused`、`closed`，分别显示为草稿、招聘中、已暂停、已关闭。
- `status=closed` 是业务状态，`archived_at` 是软归档标记；关闭不等于归档。
- 一个候选人可以关联多个职位，一个职位可以关联多个候选人。
- `(candidate_id, position_id)` 唯一；重复关联按幂等重放处理，不重复写活动。
- 单次批量关联最多 100 名候选人。输入先去重，再在一个 SQLite 事务内校验和写入。
- 目标职位、任一候选人不存在，职位已关闭/归档，或待新增关系的候选人已归档时，整批关联失败且不部分写入；暂停职位允许关联。
- 解除关联删除关系行，但不删除候选人或职位，并写入 `position_unlinked` 候选人活动。
- 单次批量解除同样最多 100 名候选人，在一个事务中完成；不存在的关系作为幂等缺席项报告，任一候选人不存在时整批失败。
- “新建候选人并关联职位”仍由两个 API 请求组成，不具备跨请求原子性；关联失败时新候选人可能保留在未分配列表。
- 已有候选人升级后不自动创建职位或关系，因没有关联行自然进入“未分配职位”。
- 关联或解除不改变 `candidates.stage`。该字段仅兼容历史数据，不是职位申请阶段，也不进入默认人才库界面。
- 活动职位批量归档必须提交每个职位的 `expected_updated_at`，单批最多 100 个；服务端在一个 SQLite 事务中重验存在性、活动状态和版本，任一目标异常返回 `409` 且整批不归档。归档职位不删除候选人或既有职位关系。

### 人才库与档案

- 人才库是独立实体，不等同于标签或职位；一个候选人可加入多个分组，同一关系只能存在一次。
- 归档人才库不会归档或删除其中候选人，也不会改变职位关系；恢复后原成员关系继续存在。
- 活动人才库支持单条和最多 100 个批量归档；已归档人才库支持单条和最多 100 个批量恢复或永久删除。V6.1 UI 对单条和批量操作都提交 `expected_updated_at`；服务端对批量操作及永久删除强制版本校验。旧单条归档/恢复为兼容 V6 可省略版本，但仍校验状态并在冲突时返回 `409`。批量操作在单个事务中重验全部分组，任一冲突均整批回滚。
- 人才库永久删除的对象只是“分组容器”：只删除分组主记录并解除 `candidate_talent_pools` 关系，不删除任何候选人、职位、附件、备注、活动、履历或其他候选人资料；活动分组直接永久删除必须返回 `409`。
- 多段履历使用 `candidate_profile_sections` 保存，不强行压缩成候选人主表单一文本。
- 历史面试、考试、测评和 AI 评估写入档案记录，只用于追溯，不形成待办、排期或可运行的招聘流程。
- Offer/录用字段只保留在候选人来源原始载荷，不结构化为历史评估；`自我评价` 写入 `candidates.self_summary`，也不进入历史评估。
- 敏感字段和原始来源载荷按业务确认完整保留；普通列表/详情仍遵守最小投影，但 Agent 已按用户明确决定改为全字段按需只读，可以在问题需要时读取未打码联系方式、薪资、照片地址、备注、活动、完整履历和 `raw_payload`。
- 用户本次明确要求在人才库头像位显示证件照，这是对旧“照片默认不展示”规则的定向变更。普通列表和详情只接收布尔值 `has_photo`，浏览器通过受控头像端点按需加载；原始 `photo_url` 仍是高敏字段。

### 归档与永久删除

- 候选人、职位和人才库分组均使用 `archived_at` 软归档，可恢复。
- 关闭或归档职位保留已有候选人关系和候选人记录，但禁止建立新关联；暂停职位仍可建立关系。
- 归档候选人保留职位关系，但禁止建立新关联。
- 在“全部档案”等混合结果中，权限按候选人自身 `archived_at` 判断；归档记录可选择、查看、恢复或永久删除，但不能与活动候选人混合执行永久删除，也不能编辑、变更阶段、添加备注或调整职位/人才库关系。
- 单条归档直接执行并提供撤销；批量归档要求确认人数，单批 1 至 100 人并在一个 SQLite 事务中全成全败。归档、撤销和恢复写入候选人活动。
- 候选人和职位永久删除均先请求预览：服务端把操作类型、去重后的目标 ID 和各自 `updated_at` 绑定到默认 2 分钟有效的一次性令牌。提交只携带令牌，不再要求输入确认词；提交时重新校验存在性、归档状态和版本，任一目标异常均返回 `409` 且整批不删除，单批最多 100 个。
- 单条兼容提交路径还把 URL 中的候选人/职位 ID 作为期望目标传入服务端；它必须与 token 快照的唯一目标完全一致，批量 token 不能误用到单条 URL。
- 候选人永久删除在一个事务中删除主档、联系方式、照片 URL、备注、活动、职位/人才库关系、履历、偏好、来源、历史评估、授权、职位申请来源、附件元数据、履历/FTS/向量数据，并先把物理附件路径放入可重试清理队列；共享职位、人才库和导入批次保留。
- 职位永久删除只删除职位主记录、职位关系和职位从属记录，不删除候选人、人才库、候选人附件、备注或其他候选人档案；每位受影响候选人获得“关联职位已永久删除”活动。删除后职位不会再出现在搜索、筛选、统计、导出、候选人详情或 Agent 查询结果中，后续来源导入可按正常规则重新创建。
- 人才库分组永久删除不使用候选人/职位的删除预览 token，而使用每个分组的 `expected_updated_at` 完成一次确认后的版本绑定提交。服务端只接受已归档分组并在一个事务中删除全部目标及其成员关系；返回受影响唯一候选人数和解除关系数，候选人档案保持完整。
- 删除审计只保存候选人 ID 的 SHA-256 和删除时间，不能恢复候选人，也不保存姓名、联系方式、照片 URL 或原始载荷。
- 职位删除审计只保存职位 ID 的 SHA-256、受影响候选人数和删除时间，不保存职位正文、来源原始载荷或可恢复快照。
- 永久删除只作用于当前应用数据库，不能删除北森等来源系统中的数据，也不会自动清理既有数据库备份；它不等同于已经完成全链路个人信息删除证明。

### 导入与导出

- 候选人文件必须经过服务端解析、字段映射、标准化和预览后才能提交。
- 预览令牌一次性使用、保存在当前进程内存中，30 分钟后过期。
- 候选人批量导入文件上限由 `CANDIDATE_IMPORT_MAX_BYTES` 配置，默认 64 MiB；不按候选人数或数据行数设置业务硬上限。解析仍受工作表、列、单元格、解压后体积、文本量、内存和 180 秒超时等安全边界约束，预览响应最多返回 20 行。
- 通用和北森导入都可显式映射招聘职位字段。`current_title` 始终是候选人当前任职，绝不自动作为招聘职位。
- 职位匹配依次使用：`source_system + source_record_id/external_code`；标准化后的“职位名称 + 部门 + 地点”；仅名称时唯一未归档同名职位。没有匹配且提供职位名称时预览为新建草稿职位。完全没有招聘职位字段时可跳过关系；显式职位字段无效、缺少新职位名称、匹配歧义或命中归档职位时，该源行标记失败并阻断该行候选人/职位/关系/原始载荷写入，要求人工复核。
- 预览通过 `position_preview` 展示匹配、新建、歧义、无效、归档冲突和拟新增关系；只有确认提交后才创建职位。职位创建和候选人关联与导入提交使用同一事务，重复提交不重复创建职位或关系。
- 北森人才库专用导入以精确 `应聘者ID` 为唯一必需稳定字段；相同 ID 跨批次只用非空值补充或更新，同一文件后出现的非空标量覆盖先出现值，空值不清除，标签按有序并集最多保留 50 个。
- 北森“证件照”映射到 `candidates.photo_url`，只接受协议为 HTTP/HTTPS 且 URL 路径以 `.jpg`、`.jpeg`、`.png` 或 `.webp` 结尾的地址，允许签名查询参数；可按相同 `应聘者ID` 在后续批次用非空值补充或更新，空单元格不清除已有照片。预览只返回 `has_photo`，不返回带签名参数的原始 URL。
- 已有 ID 可省略姓名，新 ID 必须有姓名；电话或邮箱命中另一候选人时返回 `identity_conflict`。
- `申请ID` 和职位信息可选。完全没有招聘职位字段时可只导入候选人并跳过关系；但显式职位字段若无法形成有效确定身份（例如新稳定编号缺职位名称、部门和地点只提供一项、匹配歧义或命中归档职位），受影响源行标记失败，不写入该行候选人、职位、关系或原始载荷，需人工复核。有效申请 ID 已属于另一候选人时阻断且绝不改绑。招聘负责人写职位负责人，候选人负责人默认未分配。
- 提交的导入、更新、跳过、失败行数之和必须等于输入总行数；`candidate_count` 是成功处理的唯一候选人数。失败行不贡献候选人、职位、关系或原始载荷。
- 同文件重放不会重复创建候选人、职位或关系，但仍更新候选人时间、最近导入批次并追加导入更新活动；当前不是严格状态幂等，可能影响最近更新排序。
- 支持未加密的 BIFF8 `.xls`，并拒绝伪装扩展名、加密或非 BIFF8 文件。三份真实文件中的前两份缺少精确 `应聘者ID`，不得按姓名或当前行序与第三份合并。
- `position_id` 只筛选导出候选人行；默认 CSV/XLSX 导出排除 `photo_url`，也不包含关系、备注或活动。
- 候选人库导出使用当前候选人筛选；职位详情导出只使用当前 `position_id`，并包含详情中展示的归档关系，不继承候选人库的残留筛选。

### Agent

- Agent 通过独立文件型 SQLite 只读连接按需查询，不复用业务写连接。连接以 `readOnly` 打开，并启用 `query_only=ON`、`trusted_schema=OFF`、defensive mode，禁用扩展加载。
- 用户已明确允许 Agent 查询服务端业务政策目录内全部允许表、允许字段和全部候选人资料，包括未打码手机号/邮箱、证件照地址、薪资、偏好、备注、活动、完整履历、评估、授权、`raw_payload`、附件正文、归档数据及最小删除审计。
- 业务全字段授权不包含服务端内部状态。`agent_sessions`、`agent_messages`、`agent_session_summaries`、附件更新预览/清理任务、迁移账本、搜索索引表及 FTS shadow 表不进入 Agent schema 目录；`candidate_attachments.storage_path` 和 `candidate_resume_vectors.vector` 也不可通过普通只读 SQL 返回。
- 自由 SQL 只接受一条 `SELECT` 或只读 CTE；服务端先做语句边界检查，再由 SQLite authorizer 按实时 schema 目录校验表、列、函数和操作码。写入、DDL、写 PRAGMA、`ATTACH`/`DETACH`、扩展加载、文件函数和多语句均拒绝。
- 常规查询最多返回 100 行、1 MB，默认 3 秒超时；结构化查询支持 `eq`、`ne`、`contains`、`in`、`gte`、`lte`、`is_null`、关联、排序、分页、聚合和分组。大明细通过受控 CSV 导出，不塞入模型上下文。
- Agent 的 18 个工具覆盖 schema、自由只读 SQL、候选人/备注/活动/来源/评估、职位、人才库、聚合、跨实体全业务字段检索、候选人级履历召回、附件文本和导出。`search_all_records` 面向候选人、职位、人才库、来源、附件和最小删除审计等实体，`search_candidate_resumes` 面向候选人级 Top-K 召回；Agent 没有任何写入、归档、恢复、关联、附件确认或删除能力。
- V8 全业务字段搜索由服务端显式表政策和 `PRAGMA table_xinfo` 动态发现字段；JSON 递归展开为稳定 `field_path`，长值按 4,000 Unicode code point 确定性分段且不截断，中文内容补充二元/三元 token。职位、人才库、阶段和导入批次命中可经关系映射回候选人。
- 业务表写入触发器只登记幂等 dirty 项并把 checkpoint 标为 `pending`；同步器在写事务内删除旧文档、重建相关字段并核验表级/字段级 coverage。索引未达到 `ready` 时检索失败关闭，不静默全表扫描正文。
- 数据库负责扫描全量候选人和聚合，常规工具最多返回 100 行；候选人召回默认 20、Agent 上限 50 位及每人 1 至 5 条必要证据，模型总上下文最多 512 KiB。单个问题不设固定总工具轮次或总执行时间，按真实证据进展持续查询；语义重复、相同结果和连续无进展会被识别并收束，没有成功工具证据的数据问答不得标记完成。默认多概念检索先为召回 Top-20 构建候选人范围内的关系子集，每个概念优先选择真实命中证据；该优化不增加返回候选人数、证据上限或模型上下文。数据内容一律视为不可信，不得把备注、附件、`raw_payload`、历史消息或摘要中的指令当成系统命令。
- SQL/FTS 查询、`business_search_sync`、模型网关等待、Agent 工具执行和响应组装均写入分段运行审计；审计只保存阶段/工具名、读取范围、耗时、行数和错误，不保存用户问题、Agent 回复、工具结果或敏感正文。
- 会话正文以 SQLite 为事实来源：用户消息、Agent 回复、状态、模型、工具名和字节统计写入 `agent_messages`，会话元数据写入 `agent_sessions`，长会话摘要写入 `agent_session_summaries`。最近上下文最多 12 条/96 KiB；超过 12 条或 96 KiB 时异步生成摘要并保留最近 6 条，摘要失败不影响已经完成的回复。
- `localStorage` 仅保存符合 UUID 格式的当前会话 ID，不保存手机号、邮箱、薪资、简历、聊天正文、摘要或历史栏开关。删除会话会级联删除本机 SQLite 中的消息与摘要，且不可恢复。
- 现有网关只确认 Chat Completions，未确认 Embedding。V8 不连接外部向量服务、不安装本地大模型，向量检索保持关闭，FTS5 不可用或 V8 索引未就绪时明确报错而不把全库正文发给模型。

### 简历附件与确认更新

- 单文件最大 15 MB；同时校验扩展名、MIME、PDF/OLE2/ZIP/UTF-8 签名，清洗原名并使用随机内部路径存放在非公开目录。
- PDF/DOCX 默认一文件一候选人；表格每行独立匹配。自动定位只使用现有标准化手机号或小写邮箱精确匹配，姓名、公司、学校、职位和文件名不参与自动合并。双字段冲突、任一字段多候选命中或命中归档档案均阻断；手机号和邮箱均无匹配时允许以解析姓名手动搜索已有候选人，或复用现有新建候选人表单、校验、重复检查和审计创建后继续确认。
- “未提取”仅为 UI 根据 `null`、空数组或空字符串生成的展示占位，不得写回身份业务值。服务端在最早可靠的附件身份边界过滤 `null`、空字符串、纯空白和精确的“未提取”，手机号与邮箱分别经过格式验证、规范化和去重后再统计唯一值；同一真实值重复出现只计一次，两个不同且有效的真实手机号或邮箱仍判定为身份歧义。
- 文本简历存在手机号或邮箱标签时，以该类标签的有效值为身份来源；PDF/DOCX 将中文标签拆成空格或换行时仍识别，行内带空白标签必须具有明确字段边界，不能从“项目邮箱”等普通词中间开始命中。标签值为“未提取”时视为缺失，不回退到整份正文搜集数字；同一行遇到下一个字段冒号即截断，正文中的“项目邮箱”不参与身份判断。无手机号标签时的全文兜底只接受中国大陆手机号或显式带 `+`/`00` 前缀的国际号码，日期、版本号、项目序号等普通数字不得参与身份判断。
- “移动电话”属于明确手机号标签；PDF/DOCX 将“电子邮箱”等身份标签拆成行内字符间空白时仍应识别。标签扫描不得把 URL 路径中的 11 位文章编号作为第二个手机号。
- 解析和建议阶段只写临时预览，不修改候选人。默认只选中当前为空且置信度足够的字段；空解析值不能清除旧值，覆盖非空值需单独选择，标签取去重并集，履历区块默认去重合并，整体替换需额外确认。
- 用户点击“确认更新并保存附件”后，普通业务 API 用短时一次性预览令牌重新校验候选人版本、身份冲突、字段格式与选择项，在事务中写候选人、字段来源、附件、履历索引和活动。相同候选人 + SHA-256 + 附件类型幂等，重复提交不会重复写入。
- 生产入口可把最多 120,000 字符、100 条预览记录交给现有 Agent 模型网关补充字段/履历建议；请求使用 strict JSON Schema且不提供 tools，附件内容明确标记为不可信。网关未配置、不可用或返回无效结果时保留本地规则建议，不阻断预览或扩大写权限。
- 预览进入 `confirmed`、`cancelled` 或 `expired` 后立即清空临时 `extracted_text` 与 `records_json`，只保留最小预览状态；确认后的完整正文只存在正式 `candidate_attachments` 及其履历索引中。
- 批次项不得在所引用预览已过期、取消、失败或丢失后继续保持“待确认”；启动恢复必须将其置为明确失败并引导重新上传。
- `.doc`、非 UTF-8 TXT/CSV、加密文件、扫描版/无文本 PDF、OCR、损坏文件和非 BIFF8 `.xls` 明确失败；不调用 OCR、LibreOffice、云转换、原生可执行程序，不执行宏或访问外部链接/远程资源。
- `0.1.1` 不新增 schema 迁移，也不批量改写历史候选人或来源原始数据。修复前已生成的错误预览保持原状态，部署新版本后必须重新上传附件才能使用新身份规则。

## 非功能要求

- 默认数据库为 `data/recruitment.db`，可用 `APP_DATA_DIR` 或 `DB_PATH` 指定。
- 个人版仅允许 `127.0.0.1`、`localhost` 或 `::1`。
- 依赖已安装且锁文件未变化时，除远程头像和远程 Agent 外的候选人、人才库和职位管理可离线启动使用。
- 当前北森证件照来源是带签名查询参数的远程明文 HTTP URL。头像不是离线附件；个人回环模式下只有在浏览器按需显示头像时才访问该远程地址。
- 使用远程 Agent 网关需要网络；用户消息和最近历史不会自动脱敏。
- SQLite 启用外键、WAL 和 5 秒忙等待。
- 数据库使用 `schema_migrations` 记录 V1-V13；V6-V13 均为加法迁移。升级前必须停止服务并备份 `.db`、`-wal`、`-shm` 文件集；当前没有自动 down migration。V11/V12 不重建候选人表、不清空历史值、不从旧 `stage` 或求职偏好回填。
- Agent 会话正文、摘要、查询结果导出和搜索索引均属于本机敏感数据；浏览器持久层只保存不透明会话 ID 与界面偏好，SQLite 才是聊天内容事实来源。

## 升级为部门版的准入条件

部门版不能只取消回环监听限制。身份认证或企业 SSO、RBAC 和字段级权限，以及把远程签名照片迁入受控本地/内部附件存储，是头像功能进入部门部署的硬门槛；同时还需要可靠操作者审计、集中数据库、HTTPS、CSRF 防护、速率限制、备份恢复演练、监控告警、附件安全、隐私留存和删除流程。完整清单见 `ROADMAP.md`。
