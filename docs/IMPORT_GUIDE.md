# 候选人导入与导出指南

## 版本边界

当前服务端提供两种文件导入轮廓：

1. **通用候选人导入**：兼容现有 CSV/Excel 映射、预览和候选人主表写入；显式映射招聘职位字段时，同时预览并提交职位匹配/草稿创建和候选人关系。
2. **北森人才库导入**：以精确 `应聘者ID` 为候选人稳定键，支持同一候选人分文件、分批次补充不同字段；申请和职位信息可用时按唯一键更新职位、多职位关系和申请血缘。

批量候选人导入只读本地上传文件，不在导入过程中连接北森或其他外部服务。该流程保存必要的原始行 JSON，但不保存原始上传文件本身；导入后的证件照仍是远程 URL，实际显示时会按需联网。V6 的“简历附件”是独立流程：用户确认后会把原文件保存在非公开本地目录，不应与批量导入混淆。

北森历史面试、测评和背调可结构化为高敏历史评估，授权字段可结构化为授权记录。Offer/录用只保留在候选人来源 `raw_payload`，不进入 `candidate_assessments`；`自我评价` 写入 `candidates.self_summary`，也不属于历史评估。上述数据都不会创建可执行的面试、审批、Offer 或入职流程。本系统仍是人才库，不是完整 ATS。

## 支持格式与限制

| 项目 | 当前行为 |
| --- | --- |
| `.xlsx` | 支持，只读第一个工作表 |
| `.xlsm` | 支持数据读取，不执行宏，只读第一个工作表 |
| `.csv` | 支持 UTF-8；不自动识别 GBK/GB2312 |
| `.xls` | 支持未加密 Excel 97-2003 BIFF8；先校验 OLE2 文件签名 |
| 批量导入文件 | 每次 1 个；由 `CANDIDATE_IMPORT_MAX_BYTES` 配置，默认 `67108864` bytes（64 MiB） |
| 候选人/数据行 | 不设置候选人数或源行数业务上限；由文件大小、单元格、列数、字符总量、解压体积、解析时限等资源安全限制约束 |
| 表头/工作表 | 第 1 行是表头；只读第 1 个工作表 |
| 预览 | 汇总全部行，响应最多返回前 20 行明细 |
| 预览令牌 | 30 分钟有效，成功提交后一次性失效 |

`GET /api/candidates/import/config`（兼容路径 `/api/import/config`）返回当前实例实际生效的 `max_file_size_bytes`、`preview_row_limit`、允许扩展名和解析资源限制。调整 `CANDIDATE_IMPORT_MAX_BYTES` 只改变候选人批量导入的上传字节上限；它不改变 V6 简历附件独立的 15 MiB 上限，也不能关闭解析安全限制。

批量导入上传使用磁盘临时文件和随机内部名，不由 Multer 在业务进程内保留第二份完整内存 Buffer；预览完成或失败后清理临时文件。解析器可以扫描并校验文件中的全部源行，但 API 和页面不会把全部明细一次性返回或挂载到 DOM。预览响应固定最多 20 行代表性明细，其余内容通过全量汇总表达；候选人约一万条只是性能验收规模，不是拒绝阈值。只有超过配置字节上限时返回 `413`，或触发明确资源/格式安全限制时返回 `422`。

候选人文件解析在独立 Node.js Worker 中运行，父线程在默认 180 秒墙钟时限到达时直接终止 worker；默认 V8 `resourceLimits` 为 old generation 1024 MiB、young generation 128 MiB、code range 64 MiB、stack 8 MiB，这些不是整个 Node 进程的 RSS 硬上限。Excel ZIP 会交叉校验 central/local header 的名称和大小、内部路径、大小写规范化后的重复路径及本地数据范围，拒绝跨卷/分段、加密、ZIP64、符号链接、重叠范围、不支持的 flags 及非 stored/deflate 压缩方法；stored 数据和 deflate 流都按实际输出累计字节、CRC-32、声明长度及 2000 倍压缩比校验，不能只依赖 ZIP 声明值绕过 512 MiB 单条目和 768 MiB 累计解压限制。

当前 OOXML 内容解析使用 ExcelJS 4.4，并在解压后按 OPC 关系与 SpreadsheetML 命名空间解析工作表。常规 Excel/LibreOffice 文件以及合法的 `<x:workbook>`、`<x:worksheet>` 前缀形式均已通过匿名测试；错误命名空间、外层 wrapper 走私、缺失/重复/近似 worksheet target 会返回 `422 import_xlsx_invalid`。系统仍不会猜测损坏或非标准关系。V7 的 48.55 MiB 容量成功基准使用 CSV，不应被解释为所有第三方 OOXML 变体均兼容。

每个服务进程最多同时上传/解析 1 个候选人文件，锁在 Multer 接收文件前取得，忙时返回 `429 import_busy` 和 `Retry-After: 1`，并在成功、错误或连接中断时释放。提交所需的完整结构化预览短期保存在进程内存中，默认 30 分钟失效、最多保留 2 个条目，并周期清理过期内容；容量满时淘汰最旧的非提交中预览，应用关闭时清空。响应仍只含 20 行。通用和北森提交返回的逐行失败详情最多 100 条，同时返回失败总数、已返回数和省略数，避免异常文件生成无上限响应。临时文件删除默认尝试 3 次并以 25 ms 线性退避；仍失败时移除已生成的预览 token 并返回 `500 import_temp_cleanup_failed`，不会假装清理成功。

## 已有三份 `.xls` 的处理

已审计的三份北森 `.xls` 是同一批数据的字段分拆导出。`11_08_39.xls`（85 列）和 `11_09_43.xls`（240 列）没有大小写准确的 `应聘者ID`；只有 `11_10_42.xls`（171 列）包含该字段。因此现有三份文件不能按稳定 ID 自动跨文件合并，禁止改用姓名、行号或当前排序拼接。

正式分批迁移应从北森重新导出每份都带 `应聘者ID` 的文件。新候选人的首次文件还需包含姓名；已有 ID 的后续文件可以只提供需要补充的字段。需要职位关系时，再提供 `职位编号` 以及新职位所需的职位名称；需要申请血缘时，同时提供 `申请ID`。将 ID、编号和电话等列按文本导出，避免前导零和长数字精度丢失。

解析支持不代表三份现有文件具备自动合并条件。不要修改、覆盖或伪装原始 `.xls`；加密、非 BIFF8 或仅改扩展名的文件会被拒绝。

已进入数据库的 57 位候选人不需要为了证件照重新导入。schema v4 `candidate_photo_backfill` 会从既有 `candidate_source_records.raw_payload['证件照']` 读取来源值，只在 `candidates.photo_url` 为空且 URL 校验通过时回填；已有照片不覆盖，活动记录不包含 URL。

## 北森人才库文件契约

专用轮廓在任一支持格式的第一张工作表（CSV 为唯一表）存在大小写准确的 `应聘者ID` 时启用：

| 北森表头 | 语义 | 约束 |
| --- | --- | --- |
| `应聘者ID` | 候选人稳定 ID | **必需**；写入 `candidates.source_record_id`，来源系统固定为 `beisen` |
| `申请ID` | 职位申请或评估来源 ID | 可选；仅在职位关系可建立或存在真实评估载荷时参与重复及归属校验 |
| `职位编号` | 北森职位外部编号 | 可选；有职位名称时创建，或仅凭编号匹配已存在职位 |
| `最后职位类投递的职位id` | 最后一次职位类投递的关联招聘职位 | 可选；表头存在时为整表唯一权威职位键，行空不回退普通 `职位编号`；仅整表缺表头才兼容回退。若值是显示名，必须结合 `最后职位类投递时间` 与该候选人的申请来源历史唯一解析，不能使用 `入职职位` 代替 |
| `最后职位类投递时间` | 关联职位解析辅助时间 | 可选；与上一列成对消解同名职位，不写入 `hire_date` 或 `申请ID` |
| `入职职位` | 候选人入职事实 | 可选；写入 `candidates.hire_position`，最长 300 字符，不建立招聘职位关系 |
| `入职状态` / `入职情况` | 候选人入职状态 | 可选；写入 `candidates.hire_status`，最长 200 字符；日期有值而状态为空时自动为 `不确定` |
| `入职日期` / `入职时间` | 候选人入职日期 | 可选；真实日期规范化为 `YYYY-MM-DD`，允许未来日期 |
| `证件照` | 候选人证件照 URL | 可选；只接受不超过 2048 字符、协议为 HTTP/HTTPS 且路径以 `.jpg`、`.jpeg`、`.png` 或 `.webp` 结尾的 URL，允许签名查询参数；映射到高敏 `candidates.photo_url` |
| `性别` | 候选人规范性别 | 可选；规范化为 `男`、`女`、`其他` 或 `未说明` |
| `出生日期` | 候选人完整出生日期 | 可选；规范化为 `YYYY-MM-DD`，不得晚于当前日期 |
| `年龄` | 来源导入年龄 | 可选；0 至 120 的整数；有完整出生日期时界面优先实时计算年龄 |

`应聘者Id` 与 `应聘者ID` 不是同一字段。已审计数据表明，`应聘者Id` 是 2 至 4 字的姓名类文本。导入器只允许它作为姓名候选列，绝不作为身份 ID。

人才库来源列支持 `应聘者关联人才库`、`所属人才库`、`人才库分类`、`人才库` 和 `最近人才库`。同一行多个列中的名称会合并、去空并去重，再按名称大小写不敏感地匹配或创建独立 `talent_pools`；不会转换成候选人标签。`最近储备时间` 等关系元数据继续保留在受保护原始来源快照中。

创建新职位时必须有可用的职位名称，缺少名称时不会用编号虚构占位职位；如果稳定编号能匹配已有职位，则可直接使用匹配结果。`最后职位类投递的职位id` 是关联职位键：工作簿存在该专用表头时是整表权威来源，单行空值不建立关系且不得回退普通 `职位编号`；只有整表没有该表头时才兼容回退。历史导出把它写成职位显示名时，导入器按候选人 ID + 最后投递时间查询既有 `candidate_position_sources.raw_payload`，唯一命中后回填职位的 canonical 编号；没有唯一历史命中时才以该值作为 draft 回退键，歧义不静默绑定。`入职职位` 只保存入职事实。完全没有招聘职位字段时只跳过职位关系；显式职位字段若无效（例如新稳定编号缺职位名称、部门和地点只提供一项）、匹配歧义或命中归档职位，则该源行失败，不写入候选人、职位、关系或原始载荷，要求人工复核。候选人新记录仍要求姓名；已有稳定 `应聘者ID` 的增量批次可省略姓名。

### 重复表头

重复表头会按物理列顺序唯一化，例如第二个同名表头变成 `字段_2`。整行原始 JSON 保留这些唯一 key，重复列不会在留档中互相覆盖。

结构化摘要只从明确别名中选值，不会把“现从事职业”当成招聘职位，也不会自动混合语义不同的重复列。待人工解释的列仍完整存在 `raw_payload` 中。

## 北森预览

```http
POST /api/candidates/import/preview
Content-Type: multipart/form-data

file=<beisen-talent.xlsx>
```

响应关键字段：

```json
{
  "profile": "beisen_talent",
  "preview_token": "uuid",
  "mapping": {
    "source_record_id": "应聘者ID",
    "source_application_id": "申请ID",
    "position_external_code": "最后职位类投递的职位id"
  },
  "summary": {
    "total_rows": 60,
    "valid_rows": 59,
    "invalid_rows": 1,
    "candidate_records": 59,
    "application_records": 60,
    "position_records": 18,
    "missing_identity_rows": 1
  },
  "position_preview": {
    "create_count": 18,
    "match_count": 0,
    "ambiguous_count": 0,
    "invalid_count": 0,
    "archived_conflict_count": 0,
    "link_count": 59,
    "items": [{ "external_code": "...", "title": "...", "action": "create" }]
  }
}
```

`59/60/18/1` 是已审计三份历史导出的匿名统计，只用于人工核对，不是任意文件的硬编码断言，也不能证明三份文件可自动拼接。现有前两份文件缺少精确 `应聘者ID`，不能进入北森增量轮廓完成跨文件合并。

`candidate_records` 是文件中观察到的唯一候选人 ID 数，可能包含最终校验失败的 ID；`application_records` 只统计可建立职位关系的唯一申请 ID，`position_records` 只统计可处理职位。仅用于评估归属的申请 ID 仍会参与重复和归属校验，但不增加 `application_records` 或提交后的 `application_count`。实际完成数以提交响应为准。

预览检查 `应聘者ID`、姓名、邮箱、电话、工作年限、证件照 URL、入职三字段、可选申请/职位信息、文件内重复申请 ID，以及职位的新建、匹配、歧义、无效和归档冲突状态。已有 ID 可以没有姓名；新 ID 缺少姓名时阻断。`最后职位类投递的职位id` 是关联招聘职位键；当工作簿有该表头时，行空只跳过关系，不能回退普通 `职位编号` 或入职职位；仅整表没有该表头时普通编号才可兼容回退。当它是显示名时，预览会用同一候选人的 `最后职位类投递时间` 对齐申请来源历史并展示解析后的职位编号。完全没有招聘职位字段时可跳过职位关系；显式职位字段若无效、匹配歧义或命中归档职位，受影响源行标记失败并阻断该行候选人、职位、关系和原始载荷写入。申请 ID 只有在职位关系可建立或行内有真实评估载荷时才参与重复和既有归属校验；未使用的申请信息只计入跳过统计。

预览先排除失败行，再按候选人 ID 和职位编号合并有效行。相同候选人 ID 的标量字段按文件顺序处理，后出现的非空值覆盖先出现值；空值不覆盖，标签取有序并集并最多保留 50 个。失败行中的候选人字段、职位字段和原始载荷都不能泄漏到同 ID 或同职位编号的有效行。

预览明细不返回整行 `raw_payload`、评估子集、授权子集或原始 `photo_url`，照片只显示为 `has_photo`。预览仍会为人工核对返回已标准化的候选人摘要，可能包含个人信息，不应进入日志、截图或问题单。

前端识别到 `profile=beisen_talent` 后直接展示专用预览，不进入通用字段映射。专用表格只展示状态、候选人稳定 ID、姓名、可选申请 ID 和可选职位编号/名称，不展示电话或邮箱。提交成功后向导保留批次统计，用户点击“完成”后才关闭。

## 北森提交语义

```http
POST /api/candidates/import/commit
Content-Type: application/json

{ "preview_token": "uuid" }
```

北森专用提交总是按稳定 `应聘者ID` 创建或更新，不使用姓名合并。兼容参数 `on_duplicate` 即使传入 `skip|update`，也不改变北森轮廓的稳定 ID upsert 语义。

同一 ID 支持分批补充资料：文件内后出现的非空标量覆盖先出现值；提交到已有候选人时，非空值可补充或更新已存值，包括用非空姓名纠正旧姓名和用合法非空“证件照” URL 更新 `photo_url`。空姓名、空照片、空字符串和空单元格不会清除旧值；标签按首次出现顺序取并集，跨行和跨批次都最多保留 50 个。姓名仍只用于展示和搜索，不参与自动合并。来源、申请、评估和授权的 `raw_payload` 同样只以非空字段递归补充或覆盖，转换失败不能通过空值静默抹除历史原值。

整个提交在一个 SQLite 事务内执行：

1. 创建 `import_batches` 记录。
2. 按 `(beisen, 应聘者ID)` 创建或增量更新候选人；已有 ID 可省略姓名，新 ID 必须有姓名。
3. 将合法“证件照” URL 写入 `candidates.photo_url`；预览和普通响应只派生 `has_photo`，不暴露签名 URL。
4. 同一候选人 ID 在文件内合并候选人资料，只创建一个主记录；后续行的来源、人才库及可选关系仍继续处理。
5. 招聘职位依次按 `(source_system, source_record_id/external_code)`、标准化“职位名称 + 部门 + 地点”、唯一未归档同名匹配；`最后职位类投递的职位id` 作为北森关联职位键，若实际为显示名则按候选人和 `最后职位类投递时间` 对齐申请来源历史，唯一命中后使用 canonical 职位；未匹配且有名称时创建 `draft`。多候选、显式职位字段无效或命中归档职位时，受影响源行失败且不写入候选人、职位、关系或原始载荷，禁止模糊匹配和静默恢复；完全没有职位字段的行只跳过关系。
6. 将北森招聘负责人写入 `positions.owner`；不因导入填充 `candidates.owner`。
7. 职位信息可用时使用唯一约束重放安全地创建 `candidate_positions`；完全缺少职位字段时跳过关系；显式职位字段无效、歧义或归档冲突时该源行已在预览阶段失败，不写入候选人资料。`入职职位` 永远只写 `candidates.hire_position`，不触发这一步。
8. 同时具有 `申请ID` 和可用职位时，按 `(beisen, 申请ID)` upsert `candidate_position_sources`。有真实评估载荷但没有职位关系时，申请 ID 只标识评估来源。两者都不具备时忽略该申请 ID，不做重复或归属阻断。
9. 按名称大小写不敏感地匹配或创建 `talent_pools`，幂等建立人才库关系。
10. 保存原始教育、工作、项目、实习、技能等资料区块。
11. 保存有效来源到 `candidates.source`，并以来源记录保留有效、最初和最后渠道。
12. 归集筛选、面试、考试、测评和背调字段到高敏历史评估记录；Offer/录用仅留在候选人来源 `raw_payload`，`自我评价` 仅写候选人 `self_summary`。
13. 归集授权、协议和同意字段到高敏授权记录。

每个校验通过并成功提交的源行的全部列，包括已确认保留的证件、婚育、家庭、健康、背调、Offer/录用和监控类敏感字段，都存在高敏候选人来源 `raw_payload` 中。校验失败的行不写入数据库，也不贡献候选人、职位、关系或任何原始载荷。这些内容不进入普通候选人列表或默认搜索；候选人详情只有显式 `include_sensitive=true` 才返回，V6 Agent 则可在用户问题确有需要时通过独立只读连接按需查询。

提交响应在通用批次计数之外返回：

`candidate_count`、`application_count`、`position_count`、`positions_created`、`positions_matched`、`links_created`、`pools_created`。

`imported_rows`、`updated_rows`、`skipped_rows`、`failed_rows` 按输入源行计数并严格守恒，其总和等于 `total_rows`。同一新候选人的第一条成功行计入 `imported_rows`，后续成功行计入 `updated_rows`；`candidate_count` 只计算本批成功触达的唯一候选人。`application_count` 只计算已保存的职位申请来源，评估来源不单独计入。

### 100 人验收清单

使用不超过 100 条、带 `应聘者ID` 的真实样本执行预览和提交。当前 V12 有两层结果：20260821 是 `:memory:` 隔离导入（`formal_database_commit=false`）；2026-08-24 对 `北森候选人入职信息导入样本-100人.xlsx`（SHA-256 `7D92DB6C37B892F3237E490E5424CC367CE14C9CAAE3F3584FB3083AD0A6C741`）完成正式 HTTP 预览/提交。预览为 `profile=beisen_talent`、100/100/0、`existing_duplicates=100`，职位映射为专用列，create/match/link/conflict 为 0/32/36/0；提交为 0 导入、100 更新、0 失败/跳过、100 候选人，`positions_created/matched=0/32`、`links_created=0`、`pools_created=0`、`application_count=0`。用户豁免 22GB 全库摘要、逐行字段、完整性/外键后检和恢复演练，不能据此声称后检完成。验收记录至少包含：

- 三个入职字段逐条抽样；`hire_date` 非空且原状态为空的记录必须落为 `hire_status=不确定`，三项全空的候选人不得显示入职信息区块；
- 每一条非空 `最后职位类投递的职位id` 都能在 `candidate_positions` 找到关联；显示名重复时确认按 `最后职位类投递时间` 命中了正确的 canonical 职位，不能以 `入职职位` 代替；
- 每位候选人的 `candidate_talent_pools` 人才库关系，以及有效/最初/最后来源的 `candidate_source_records` 历史至少各抽查一条；
- 预览与提交行数守恒，提交后重放不新增候选人、职位、职位关系、人才库关系或来源记录；
- 在隔离数据库执行 `PRAGMA integrity_check`（应为 `ok`）和 `PRAGMA foreign_key_check`（应返回 0 行），并保留批次 ID、摘要和失败明细。

### 身份冲突

如果文件中的北森候选人 ID 是新值，但其标准化电话或邮箱已属于平台中另一候选人，该行标记为 `identity_conflict` 并失败。系统不会把新北森 ID 静默绑定到旧候选人。

同样，已有北森 ID 的增量文件如果提供了属于另一候选人的电话或邮箱，也会阻断更新。空联系方式不会清空原联系方式，也不会参与冲突判断。

### 申请归属冲突

当 `申请ID` 实际用于职位关系或历史评估时，同一文件内重复会在预览中报错；数据库中已属于另一候选人的申请 ID 返回 `application_identity_conflict`。提交时会重新检查，以阻断预览后发生的归属竞态。系统不会把既有申请、职位来源或评估改绑到另一候选人。未形成职位关系且没有评估载荷的申请 ID 不参与这些校验，只作为跳过信息处理。

### 重放结果与限制

再次预览和提交同一数据时：

- 职位预览从 `create` 变为 `match`。
- 候选人按北森 ID 更新，不新建同名记录；空值不覆盖旧值，标签保持并集。
- 职位按稳定来源键、标准化名称/部门/地点或唯一同名匹配，`positions_created=0`。
- 已有职位关系不重复创建，`links_created=0`。
- 申请原始行、来源、评估和授权按稳定来源键更新。
- 人才库和关系不重复创建。

上述行为保证重放不会重复创建候选人、职位或关系，但不保证数据库状态完全不变。每次重放仍会更新已有候选人的 `updated_at` 和 `import_batch_id`，追加 `candidate_import_updated` 活动，并可能改变“最近更新”排序。当前没有“内容未变化则不写入”的严格状态幂等优化。

## 通用候选人导入

通用轮廓适用于不包含精确 `应聘者ID` 表头的支持格式。它写入候选人主表和导入批次；当用户显式映射招聘职位字段时，还会在同一提交事务中匹配或创建职位并写入 `candidate_positions`。通用轮廓不自动创建人才库。

### V12 入职信息与清理工作簿

通用导入和北森专用导入均可映射 `hire_position`/`hire_status`/`hire_date`。可识别的通用表头别名为 `入职职位`、`入职岗位`、`hire_position`，`入职状态`、`入职情况`、`hire_status`、`hire status`，以及 `入职日期`、`入职时间`、`hire_date`、`hire date`；北森文件优先识别精确中文表头。入职职位只做去首尾空白和长度校验（最多 300 个字符）；入职状态最多 200 个字符且不强制枚举，以免丢失来源系统新增状态。入职日期校验真实日历日期并落库为 `YYYY-MM-DD`，允许未来日期，也允许状态有值但日期为空。工作簿中的数值型日期单元格可按 Excel 1900 日期系统转换；CSV 数字文本、REST/结构化 JSON 和附件建议中的数值日期均拒绝。日期有值而状态为空时自动保存 `不确定`；已有明确状态不被覆盖。

同一候选人的增量导入遵循“非空覆盖、空值不清除”：空入职职位、空入职日期不会抹除数据库已有值，空入职状态也不会抹除已有状态。该规则仅针对字段写入，不会把旧 `stage` 或 `candidate_preferences.employment_status` 转换为新字段；系统也不对所有历史导入自动启用状态过滤。档案中三项全空时仅隐藏入职信息区块，不隐藏候选人。

为本次北森批量导入准备清理文件时，空单元格、纯空白文本和精确文本“空”均视为空入职状态，必须删除整行；仅保留 `trim(入职状态)` 非空且不等于“空”的候选人。即使 `入职日期` 为空，状态有效的行仍保留。输出为每个源 `.xls` 对应的 `_已整理.xlsx`，列顺序保持 `入职状态`、`入职日期`、`应聘者ID`，日期/ID 与状态来自同一源行。原始 `.xls` 不修改、不覆盖、不合并。

清理后的工作簿是本轮导入边界；脚本或人工另行筛选不得改用姓名、行号或日期是否为空作为保留条件。

### 预览

```http
POST /api/candidates/import/preview
Content-Type: multipart/form-data

file=<candidates.csv|xlsx|xlsm|xls>
mapping=<optional JSON>
defaults=<optional JSON>
source_system=<optional text>
```

姓名必须能自动或手工映射。默认候选人映射覆盖联系方式、当前经历、地点、性别、出生日期、年龄、工作年限、学历、学校、专业、求职状态、简历更新时间、自我概述、来源、负责人、标签、薪资和来源血缘。

可选招聘职位映射为：`position_title`、`position_external_code`、`position_department`、`position_location`、`position_owner`、`position_source_system` 和 `position_source_record_id`。候选人 `current_title` 只表示当前任职，绝不能作为招聘职位。无显式职位来源系统时使用本次导入 `source_system`，再回退 `excel_import`。

旧 `stage` 表头不再自动映射。为兼容历史整合，调用方仍可通过显式 `mapping` 或 `defaults.stage` 写入旧阶段，但新人才库导入不应使用它。

预览对文件内去重和已有数据冲突做区分，响应含 `valid_rows`、`invalid_rows`、`existing_duplicates` 和 `file_duplicates`。映射职位时还返回 `candidate_mapping`、`position_mapping` 和 `position_preview`；后者汇总 `create_count`、`match_count`、`ambiguous_count`、`invalid_count`、`archived_conflict_count`、`link_count`，并最多给出 100 个处理条目。预览阶段不写数据库。

### 提交

```json
{
  "preview_token": "uuid",
  "on_duplicate": "skip"
}
```

`on_duplicate` 只支持 `skip|update`。`update` 只更新已映射且非空字段，不自动修改姓名。提交时重新解析并再次查询候选人和职位身份键，预览后产生的并发冲突仍会被拦截。职位创建、候选人写入和关系建立使用同一 SQLite 事务；失败不留下孤立职位或部分关系。`positions` 稳定键/组合匹配和 `(candidate_id, position_id)` 唯一约束保证重复提交不重复创建职位或关系。

## 标准化与去重

- 邮箱去首尾空白并转小写。
- 中国大陆 11 位手机号转为 `+86` 格式。
- 电话分机后缀移除；其他号码保留 7 至 15 位数字。
- 标签去重，最多 50 个，每个最长 80 字符。
- 性别别名规范化为 `男`、`女`、`其他` 或 `未说明`；无法识别的非空值校验失败。
- 出生日期只接受有效且不晚于当前日期的完整日期，落库为 `YYYY-MM-DD`；年龄只接受 0 至 120 的整数。界面存在出生日期时按当前日期计算年龄，否则回退到导入年龄，不从身份证号码推断。
- 工作年限提取首个数字，允许 0 至 80。
- 通用导入的手工旧阶段值仍使用历史别名归一化。

通用去重键是 `source_system + source_record_id`、标准化邮箱和标准化电话。姓名永远不是自动去重键。多个键命中不同候选人时返回 `identity_conflict`，不会任选一人更新。

兼容接口 `/api/imports/candidates` 在缺少来源 ID 时使用“文件名 + 行号”生成 ID。它只适用于已有前端兼容，不是正式北森迁移方案。

## 简历附件导入与候选人更新

简历附件与上述批量导入使用不同 API 和提交语义。支持文本型 `.pdf`、`.docx`、`.xlsx`、`.xlsm`、未加密 BIFF8 `.xls` 和 UTF-8 `.csv`，单文件最大 15 MB；PDF/DOCX 默认一文件对应一位候选人，表格每个非空数据行独立匹配和确认。

上传流程：

1. `POST /api/attachments/previews` 上传 `file`，可选传 `candidate_id` 作为人工上下文。
2. 服务端清洗文件名，联合校验扩展名、MIME、PDF/OLE2/ZIP/UTF-8 签名，计算 SHA-256，并用随机内部名写入非公开 `quarantine/`。
3. 独立 worker 在 15 秒超时内解析；限制 200 页 PDF、20 个工作表、每表 1000 数据行、200 列、2000 个 ZIP 条目、64 MB 总解压体积、32 MB 单条目和 200 万字符。XLSX/XLSM 只读取第一个工作表，宏不执行。Office ZIP 不只信任目录声明：worker 会复核 central/local entry，实际读取 stored entry 或用 `inflateRawSync` 解压 deflate entry，并要求实际长度等于声明长度；实际单条大小、累计 64 MB 和压缩比任一超限即失败，长度不一致返回 `zip_size_mismatch`，加密、ZIP64 和其他压缩方法不支持。
4. 解析线程使用 V8 Worker `resourceLimits`：old generation 256 MB、young generation 64 MB、code range 32 MB、stack 4 MB，并清空 `execArgv`。这些限制与 15 秒超时共同约束解析工作，但不等于整个 Node.js 进程的硬 RSS 上限。
5. 服务端提取电话/邮箱并复用业务标准化。邮箱去空白/小写后精确匹配，电话按现有规则标准化后精确匹配；姓名、公司、学校、职位和文件名只供人工核对。
6. 预览返回匹配状态、字段当前/建议值、置信度、证据和履历区块。此时不更新候选人，也不保存正式附件。
7. Agent 网关配置完整时，系统可把最多 120,000 字符和 100 条记录作为不可信 JSON 发送给现有模型，用 strict JSON Schema、无 tools 的请求补充建议；网关失败时继续使用本地规则建议。
8. 用户逐字段/区块选择并调用 `/api/attachments/previews/:id/confirm`；业务 API 重新校验一次性 token、候选人 `updated_at`、归档状态、身份冲突和字段格式，在单事务中保存附件、字段来源、履历区块、全文索引和活动。确认、取消或过期后，临时预览正文和建议 JSON 被清空。

身份结果：手机号和邮箱命中同一候选人为高置信；只有一个字段唯一命中可提出匹配但仍需确认；两个字段命中不同候选人返回 `identity_conflict`；任一字段命中多个候选人或命中归档候选人时阻断；没有命中时允许手工选择已有活动候选人，但不自动创建。

合并规则：空解析值永不清除旧值；默认只选当前为空且非低置信字段；覆盖已有非空字段需显式勾选；电话/邮箱更新再次全库查冲突；标签取去重并集；履历默认按“类型 + 标题 + 正文”内容签名去重合并，整体替换需 `merge_mode=replace` 和额外确认。同一候选人 + SHA-256 + `resume` 唯一，重复文件不会重复建立附件、更新字段或写活动。

`.doc`、加密/带密码文件、扫描或无文本 PDF、OCR、损坏文件、非 BIFF8 XLS、GBK CSV和超限内容会明确失败。解析器不调用 LibreOffice、OCR、云转换、原生可执行程序，不执行 Office 宏，不访问 DOCX 外部文件或 PDF 远程资源。取消、失败、过期和确认后的隔离文件会清理；删除候选人后的正式附件清理失败进入 `attachment_cleanup_jobs` 重试。

## 敏感数据查看

北森提交后，默认候选人详情只返回来源、评估、授权和申请的安全元数据，并使用 `raw_payload_available` 表示原始数据存在。

```text
GET /api/candidates/:id?include_sensitive=true
```

该显式开关才返回电话、邮箱、原始 `photo_url`、薪资、高敏资料区块和已解析的 `raw_payload`。旧招聘阶段使用独立开关 `include_legacy_stage=true`，不随敏感开关自动返回。普通列表、普通详情和北森预览只返回 `has_photo`。

头像通过 `GET /api/candidates/:id/avatar` 显示：服务端重新校验 URL，仅允许 HTTP/HTTPS 协议且路径以 `.jpg`、`.jpeg`、`.png` 或 `.webp` 结尾，签名查询参数可保留；通过后以带 private cache 和 no-referrer 的 `302` 跳转。当前真实来源是带签名参数的明文 HTTP 地址，系统不下载图片，离线时前端回退姓名首字母。

当前没有认证和字段权限，因此这两个查询开关只是响应投影，不是多用户安全控制。Agent 的全字段能力也不是 RBAC。不能在未增加认证、RBAC 和审计前向部门网络暴露 API。

## 导出

```text
GET /api/candidates/export?format=xlsx
GET /api/candidates/export?format=csv
```

兼容路径为 `/api/export`。导出应用与候选人查询相同的服务端筛选，包括职位、人才库、学历、学校、性别、专业和求职状态，并且不分页。V7 页面筛选区移除“专业”并增加“性别”；`major` 参数仍为旧客户端和导出的兼容能力，专业数据、详情、导入和导出没有删除。
