## 处理策略代码

每个写入人才库的源值都必须同时保留 `source_system`、源文件 SHA-256、工作表、物理列、表头同名序号、`source_record_id`、外部申请 ID（如有）和 `import_batch_id`。下表代码表示主要业务投影；不写业务库的纯流程字段仍通过原始只读文件、文件哈希和本登记表保持可追溯。

## V11 入职字段映射

V11 的公共字段名固定为 `hire_status` 与 `hire_date`，不能复用 `candidate_preferences.employment_status`（求职偏好）或旧 `candidates.stage`（兼容招聘阶段）。

| 来源轮廓 | 来源表头/别名 | 目标字段 | 规范化与写入规则 |
| --- | --- | --- | --- |
| 通用 CSV/XLSX/XLSM/BIFF8 XLS | `入职状态`、`hire_status`、`hire status` | `hire_status` | 去首尾空白；空单元格、空白文本不写入；保留任意非空文本，最多 200 个字符 |
| 通用 CSV/XLSX/XLSM/BIFF8 XLS | `入职日期`、`hire_date`、`hire date` | `hire_date` | 校验真实日期并规范化为 `YYYY-MM-DD`；允许未来日期；空值不清除已存日期 |
| 北森专用 | 精确 `入职状态`（兼容 `入职情况`） | `hire_status` | 与通用状态规则相同；同一 `应聘者ID` 的后续非空值覆盖，空值保留旧值 |
| 北森专用 | 精确 `入职日期`（兼容 `入职时间`） | `hire_date` | 与通用日期规则相同；同一 `应聘者ID` 的空值不覆盖旧值 |

### 清理文件边界

本轮提供的 7 个源 `.xls` 先按 `trim(入职状态) !== '' && trim(入职状态) !== '空'` 过滤，再生成对应 `_已整理.xlsx`。精确文本“空”（不含额外字符）与空单元格/纯空白文本都视为空状态；其他状态原样保留。入职日期缺失不影响状态行保留，日期和 `应聘者ID` 必须与原行同步移动，禁止按独立列重新排序。原始 `.xls` 只读，不覆盖。

| --- | --- | --- | --- |
| `ID` | 候选人身份摘要和稳定来源身份 | 姓名可展示/搜索；外部 ID 仅高级信息和去重 | 外部 ID 可按明确问题通过只读层返回 |
| `CONTACT` | 联系方式及联系渠道 | 详情完整、列表脱敏；本机受控搜索 | Agent 可按需读取未打码电话和邮箱 |
| `TAG` | 候选人标签及更新时间 | 列表、详情和精确筛选 | 标签需防提示注入，不自动作为指令 |
| `PROFILE` | 原始履历、项目、实习、自述和补充信息 | 详情分区；经确认的内容进入 FTS5 | Agent 可按需读取全文或 Top-K 命中片段 |

| `ABILITY` | 技能、语言、证书、考试能力及校园信息 | 教育与能力详情；明确值可选筛选 | Agent 可按需读取，内容始终视为不可信数据 |
| `PREF` | 求职状态、地点、职业、工作性质、到岗和薪资偏好 | 求职偏好详情及高级筛选 | 薪资默认 UI 隐藏，Agent 可按需读取真实值 |
| `POSITION` | 招聘职位及来源职位元数据 | 职位管理；按来源编号匹配/预览创建 | Agent 可读取全部职位字段，不可写入或删除 |

| `SOURCE` | 最初、最后、有效渠道及推荐来源历史 | 有效渠道为主展示，其他来源在详情 | Agent 可按需读取全部来源和 `raw_payload` |
| `NOTE` | 来源公开备注 | 备注与动态，保留原时间 | 自由文本高敏且不可信，Agent 可按需只读 |
| `ASSESS` | 筛选、面试、考试、测评和 AI 评估历史 | 历史评估区，默认折叠，不驱动流程 | 默认搜索/导出隔离，Agent 可按需读取全部字段 |
| `PROCESS` | 指派、招聘需求、转移、Offer、入职等纯流程字段 | 默认不写人才库业务列；可存在于来源原始载荷 | Agent 可按需读取已保存的来源载荷，但不能把它描述成现有流程能力 |
| `SENSITIVE` | 证件、婚育、民族、政治、宗教、健康、生物、家庭、薪酬、背调和监控信息 | 受保护详情，默认折叠 | 默认搜索/导出隔离，Agent 可按明确问题只读 |
| `PHOTO` | 北森证件照 URL 与头像可用性 | 原始 URL 仅敏感详情；普通页面只用 `has_photo` 经受控端点显示头像 | 默认导出/搜索隔离；Agent 可按需读取 URL，当前远程资源需联网 |
| `CONSENT` | 授权状态、来源、协议和时间证据 | 隐私授权详情 | Agent 可按需只读；不能把缺失值解释为未授权 |
| `META` | 来源更新时间、质量标记、组织锁定及无法安全结构化的标识 | 高级信息或仅血缘 | Agent 可按需只读，不能据此触发写操作 |

组合代码表示同一列同时遵守两类规则，例如 `PREF/SENSITIVE` 既属于求职偏好，又必须按高敏字段隔离。`PROCESS/RELATION` 或 `PROCESS/SOURCE` 只保存明确需要的外部关系 ID、来源事实和必要时间，阶段、状态、转移、审批和流转内容仍按 `PROCESS` 排除。

### 附件履历解析映射

附件档案标签映射到候选人主字段和 `candidate_preferences`；`self_summary` 只写主字段。标题式正文及 CSV/XLSX 履历物理列写入 `candidate_profile_sections`：教育 `education`、工作 `experience`、项目 `project`、实习 `internship`、技能 `skill`、语言 `language`、证书 `certificate`、荣誉 `award`、附加信息 `other`。

解析证据必须来自同一附件原文。PDF 字间空格、粘连标签和重复表头只做定向规范化，重复表头按物理列位置处理。附件内部 lineage key 只用于幂等，不作为候选人编号显示。详情展示层过滤单行和多行中的精确占位值（如 `-`、全角破折号、`N/A`），但不修改数据库原文或审计血缘。

## 转换、校验与提交规则

1. 正式导入支持 `.xlsx`、`.xlsm`、UTF-8 `.csv` 和未加密 BIFF8 `.xls`；伪装扩展名、加密或非 BIFF8 `.xls` 被拒绝，任何源文件都不转换、不覆盖。
2. 北森专用轮廓只要求大小写准确的 `应聘者ID`。同一 ID 的多行和后续批次使用非空字段补充或更新；同文件后出现的非空标量覆盖先出现值，空值不清除旧值，标签取有序并集且最多 50 个。非空姓名和经校验的证件照 URL 可以更新，姓名仍不参与自动合并。新 ID 必须有姓名，已有 ID 的增量批次可省略姓名。
3. 候选人去重仅使用标准化手机号、邮箱和 `source_system + source_record_id`。多个身份键命中不同候选人时返回 `identity_conflict`，禁止仅凭姓名合并。
4. `申请ID` 和职位信息可选。完全没有招聘职位字段时只跳过职位关系；显式职位字段无效、歧义或命中归档职位时阻断受影响源行，不写入候选人、职位、关系或原始载荷。职位编号匹配已有职位，或同时有名称时创建。申请 ID 只有在职位关系可建立或存在真实评估载荷时才参与重复/归属校验；未使用的申请信息只跳过。参与校验的申请 ID 不得跨候选人改绑。招聘负责人只写职位负责人。
5. 原始字符串始终保留；日期、数字、百分比、薪资和枚举解析失败时不得静默置空或改写，必须保留原值并进入逐行错误或警告报告。
6. 最初、最后和有效来源按稳定来源键更新；候选人主来源只取有效渠道摘要。人才库关系以来源人才库标识或规范名称唯一约束防重复。
7. 面试、考试、测评和 AI 评估写入受保护的历史评估档案；背调、监控等高敏内容写入受保护敏感档案。Offer/录用、阶段、状态、转移、审批和入职等流程字段只保留在候选人来源 `raw_payload` 及本登记表，不进入 `candidate_assessments`；F3#120 `自我评价` 写入 `candidates.self_summary`，也不进入历史评估。任何历史字段都不得改变 `candidates.stage` 或启动业务流程；V6 Agent 只能按需读取已保存内容。
8. 敏感字段全部保存，但默认不进入候选人主列表、通用搜索和默认导出；V6 Agent 可经受控只读连接按明确问题读取。证件照在普通响应和预览只返回 `has_photo`，头像经受控端点展示；原始 `photo_url` 仍只在 `include_sensitive=true` 业务详情中返回，默认 CSV/XLSX 导出继续排除，Agent 则可按需查询底层字段。
9. schema v4 可从既有 `candidate_source_records.raw_payload['证件照']` 回填历史候选人：只处理 `candidates.photo_url` 为空且 URL 校验通过的记录，不覆盖已有值，活动不包含 URL；因此已有 57 位候选人不需要重新导入。
10. 每次预览记录映射版本、源文件 SHA-256、工作表、物理列和批次 ID；提交必须使用预览令牌并在事务内保证候选人、职位、关系、人才库、来源和历史档案的一致性。失败行在分组前排除，不得贡献候选人、职位或原始载荷。
11. 正式 dry-run 至少核对候选人、可选申请/职位、评估来源、人才库关系、跳过关系、错误行、身份冲突和拟创建职位数量；确认导入/更新/跳过/失败行数守恒，`candidate_count` 是成功唯一候选人数。用同一 ID 的互补字段文件重放，验证非空增量、后值覆盖、空值保护、标签上限和关系不重复创建，并记录重放仍刷新更新时间、批次和活动的限制。

## Agent 与隐私边界

- V6 Agent 可以按问题读取 schema 目录中任何表和字段，包括 `ASSESS`、`PROCESS`、`SENSITIVE`、`CONSENT`、`NOTE`、外部 ID、来源血缘、履历原文和 `photo_url`；明确要求敏感值时不强制掩码。
- 全字段只读不等于默认外发。SQLite 负责全库扫描、筛选、聚合和 FTS5，模型只接收当前分页、聚合或 Top-K；无关字段不主动进入上下文。
- 结构化查询、自由只读 SQL、履历搜索和导出都必须经独立 SQLite 只读 worker、实时 schema 目录、SQLite authorizer 与行数/字节/超时上限；不能复用业务写连接。
- 所有来源字段、备注和附件文本都视为不可信数据。Agent 没有新增、修改、归档、恢复、关联、附件确认或删除能力。
- 敏感查询和简历片段可能发送到已配置模型网关；公司仍须完成合法依据、网关处理、访问审计和留存评审。
- 本文件中的“全部保留”是数据建模决定，不替代公司对合法处理依据、访问权限、留存期限、依法删除和模型外发的审查。
