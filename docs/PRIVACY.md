# 隐私与数据治理

## 1. 适用范围

本文覆盖 talent-library v2 与 schema V1-V12 中的候选人主档、联系方式、照片 URL、履历、求职偏好、入职状态/日期/职位、来源/评估/授权、人才库、职位、备注、活动、本地简历附件及解析正文、持久附件导入批次、全业务字段索引、Agent 会话/消息/摘要、导入/导出、SQLite 数据库、备份及发送给模型网关的数据。用户提供的北森清理工作簿只作为本地导入准备文件，原始 `.xls` 不被覆盖。

当前版本是个人本机应用。本说明是产品和工程控制基线，不替代公司法务、信息安全或个人信息保护负责人的正式意见。

## 2. 当前安全边界

当前依靠以下边界减少暴露：

- HTTP 服务强制监听回环地址，只允许同一台电脑访问。
- 候选人列表和默认详情使用隐私最小化投影。
- 完整敏感详情需要本机用户在候选人详情中显式加载。
- 普通候选人响应只返回 `has_photo`；头像端点不回传原始 URL 字段，而是校验后按需跳转。
- Agent 使用独立受控 SQLite 全字段只读层；它可以按明确问题接收未打码敏感详情，但不主动发送整库，模型上下文受分页、聚合和 Top-K 限制。
- 简历附件保存在非公开随机路径，上传先进入隔离区；解析失败、取消、过期和候选人删除后的物理清理由可重试队列处理。
- 附件预览确认、取消或过期后清空临时解析正文和建议 JSON；只有正式附件保留业务需要的完整文本。
- 数据库、导出文件和备份不提交版本库。本轮用户明确要求的 7 份 `_已整理.xlsx` 和 100 人验证样本是受控本地交付，仅用于导入准备；`outputs/**/*.xlsx` 已被 Git 忽略，安全测试只使用匿名生成 fixture。不得把真实工作簿当作源码、备份或测试夹具，也不得扩散到共享仓库；应按组织留存/销毁策略单独保管。

必须同时理解当前缺口：

- **没有登录、认证、RBAC、字段级权限或多人隔离。**能登录当前 Windows 账户并访问应用的人，在本机上可以触发敏感详情加载。
- **没有 SQLite 或字段级静态加密。**数据库文件、WAL、备份和导出中的敏感值是明文数据；“界面默认隐藏”不等于“磁盘已加密”。
- 没有不可伪造的操作者审计、自动留存或备份销毁证明；候选人/职位永久删除只覆盖当前应用数据库。
- 当前不支持部门多人部署，也不应通过修改 `HOST`、反向代理、端口转发、共享 Windows 会话或共享数据目录绕过限制。
- 当前照片来源是带签名参数的远程明文 HTTP URL，图片内容和签名仍会离开本机并经过来源网络链路；`no-referrer` 只能减少引用页泄露，不能提供传输加密或来源可用性保证。

因此操作系统账户权限、全盘加密、自动锁屏、受控备份目录和设备管理是当前主要访问控制。

## 3. 数据责任

- 只能导入公司有权处理、且从北森或其他来源合法导出的候选人数据。
- 使用者应确认处理目的、授权范围、告知同意、第三方处理、跨境和留存要求。
- 当前按业务确认会保留完整历史评估、流程来源和敏感原始字段，这扩大了数据风险；上线真实数据前必须由公司确认必要性、访问范围和留存期限。
- 原始来源文件应放在项目目录之外的受控只读位置，不能作为日常共享文件。
- 自动化、浏览器测试和截图不得使用真实候选人数据。

## 4. 数据分类

| 级别 | 示例 | 当前处理要求 |
| --- | --- | --- |
| 高敏感 | 手机、邮箱、薪资、证件、婚育、健康、家庭、照片及 `photo_url`、背调、AI 监控/作弊字段、完整备注、历史评估、附件原文件/解析正文和各表 `raw_payload` | 原始值默认不进入普通列表、默认搜索和普通导出；Agent 可按明确问题读取并发送必要字段到已配置模型网关。数据库、附件目录、Agent 导出和备份按最高级别保护。 |
| 敏感 | 姓名、出生信息、教育经历、工作履历、求职偏好、人才库归属、职位关联、申请来源和授权状态 | 仅用于明确人才管理目的；限制导出和二次传播。 |
| 内部 | 职位、部门、计划人数、标签、负责人、来源系统、来源记录 ID、导入批次、活动元数据 | 用于业务管理和数据血缘；不得公开传播。 |
| 内部配置 | `AGENT_BASE_URL`、模型名、数据库路径 | 只在受控设备和运维文档中使用。 |
| 机密凭据 | `AGENT_API_KEY` 和其他 token | 只保存在受控环境变量或本机 `.env`；禁止进入代码、日志、截图、导出和文档。 |

自由文本和原始载荷的实际敏感级别可能高于字段名称表现。简历附件保存在数据库同域的非公开私有目录，不由静态服务器暴露；不得另把附件复制进 `public/`、`dist/`、日志、问题单或截图目录。

## 5. 默认投影与显式敏感加载

### 5.1 默认候选人响应

候选人列表和默认 `GET /api/candidates/:id` 不返回：

- 手机和邮箱。
- 原始 `photo_url`；仅返回不含地址信息的 `has_photo`。
- 期望薪资。
- 来源记录 ID 和导入批次内部标识。
- legacy 招聘阶段。
- 来源、评估、授权、申请和求职偏好的 `raw_payload`。

默认详情可以返回经过裁剪的人才库、职位、履历和历史元数据，用于构建人才档案，但不把原始敏感载荷展开。

### 5.2 本机显式加载

用户选择“查看敏感资料”或明确进入候选人编辑时，前端调用：

```text
GET /api/candidates/:id?include_sensitive=true
```

该响应可以包含完整联系方式、原始 `photo_url`、薪资、来源标识和原始载荷。前端只把它放进当前候选人详情会话：

- 不合并回全局候选人列表。
- 不进入默认搜索或筛选索引。
- 不进入工作台统计。
- 普通详情状态不会自动发送给 Agent；Agent 若因用户问题需要敏感字段，会从独立只读连接按需重新查询。
- 关闭详情后不作为列表状态继续展示。

这是界面数据最小化措施，不是访问控制。当前没有用户身份可用于判断谁有权点击该操作。

### 5.3 头像定向展示

用户本次明确要求把北森“证件照”用于候选人头像，这是对旧“照片默认不展示”决策的定向变更，而不是照片敏感级别下降：

- 普通列表、普通详情和导入预览只返回 `has_photo`，不返回远程主机、路径或签名参数。
- `GET /api/candidates/:id/avatar` 仅接受数据库中再次校验通过的 URL：协议必须为 HTTP/HTTPS，路径必须以 `.jpg`、`.jpeg`、`.png` 或 `.webp` 结尾，允许签名查询参数；以 `302` 跳转并设置 `Cache-Control: private`、`Referrer-Policy: no-referrer`。
- 默认 CSV/XLSX 导出和普通搜索排除 `photo_url`；Agent 可在用户明确问题需要时读取原始地址。
- 前端加载失败时回退首字母，不把错误 URL 输出到界面或日志。
- 当前实现不代理、不下载、不生成本地缩略图，因此查看远程头像仍是一次对来源服务的联网请求。
- schema v4 仅从既有来源记录为 `photo_url` 为空的候选人回填校验通过的地址，不覆盖已有值；回填活动不记录 URL 或签名参数。

## 6. 北森数据收集与导入

北森专用导入只要求每条候选人记录具有大小写准确的 `应聘者ID`。相同 ID 的后续批次可用非空字段补充或纠正资料，包括姓名和经校验的“证件照” URL；同文件后出现的非空标量覆盖先出现值，空值不清除旧值，标签取并集且最多 50 个。姓名始终不是自动合并键。新 ID 必须有姓名，已有 ID 可以在后续批次省略姓名。预览只暴露 `has_photo`。

`hire_status`、`hire_date`、`hire_position` 是候选人主档的入职事实字段：日期规范为 `YYYY-MM-DD`，有效日期无状态时保存精确值“不确定”；三项全空仅不展示详情区块，不删除候选人。`入职职位` 不作为招聘关系，也不读取求职偏好就业状态。

`申请ID` 和职位信息仅在需要申请血缘、职位关系或历史评估来源时提供。北森字段 `最后职位类投递的职位id` 才能写入 `candidate_positions`；为空时跳过关系，显示名值按候选人 ID + 最后投递时间匹配历史职位，未命中才创建草稿。`入职雇佣关系` 保留在来源 `raw_payload`，人才库关系和来源历史分别写入专用关系/来源表。显式职位字段若无效、匹配歧义或命中归档职位，受影响源行失败且不写入候选人、职位、关系或原始载荷。申请 ID 只有在职位关系可建立或存在真实评估载荷时才参与重复与归属校验；其他未使用信息只跳过。有效申请 ID 已属于另一候选人时阻断且不改绑。导入仍需预览候选人、缺少 ID/姓名、申请/职位跳过、职位匹配和创建数量；申请记录数和源行数都不能作为唯一候选人数展示。手机或邮箱指向另一候选人时阻断并人工复核。

服务端支持未加密 BIFF8 `.xls`，并拒绝伪装扩展名、加密和非 BIFF8 文件。现有三份 `.xls` 中前两份缺少精确 `应聘者ID`，不得仅按姓名、行号或当前排序与第三份静默合并，也不得为了导入覆盖原始文件。

北森导入会把来源血缘、履历、偏好、历史评估、授权和职位申请来源写入专用表。Offer/录用仅保留在候选人来源 `raw_payload`，`自我评价` 进入候选人 `self_summary`，二者都不结构化为历史评估。失败行不写入任何候选人、职位或原始载荷。需要保留完整敏感字段时，原值进入高敏感 `raw_payload`，不得进入默认 UI；V6 Agent 只能在用户问题需要时按需读取。

同一文件重放会新增批次和候选人更新活动，并刷新候选人的最近更新时间。即使没有产生重复主记录，这些新增元数据也属于额外个人信息处理和留存，应纳入批次、活动及日志留存策略。

## 7. Agent 与模型网关

不配置 Agent 时，应用不会主动把候选人数据发送给模型服务。配置模型网关后，用户已明确允许 Agent 按问题读取业务政策目录内任何允许表和字段，包括未打码手机号/邮箱、照片地址、薪资、偏好、备注、活动、完整履历、历史评估、授权、`raw_payload`、附件文本、归档记录及最小删除审计。

扩大字段范围不等于允许整库外发。Agent 使用独立只读连接和 18 个白名单工具；数据库可扫描全量数据，但常规结果最多 100 行/1 MB，履历默认只发送 20、最多 50 位候选人及必要证据，统计只发送 SQLite 聚合结果，完整明细写本地受控 CSV。SQL/FTS、`business_search_sync`、模型网关等待、工具执行和响应组装审计只保存阶段/工具名、表/列/函数范围、耗时、行数和错误，不保存问题、回复、工具结果或敏感正文。

配置远程 `AGENT_BASE_URL` 后，用户问题、最近对话、敏感查询结果和简历片段可能离开本机。工具结果中的备注、附件正文和 `raw_payload` 被标记为不可信数据，但这不会降低其隐私级别。启用前必须确认公司模型网关的日志、存储、训练使用、地域、访问控制和删除政策；使用本机模型也应管理模型日志、缓存和临时文件。

V8 会话正文在本机 SQLite 中明文持久化：`agent_sessions` 保存标题和状态，`agent_messages` 保存用户问题、Agent 回复、模型/工具元数据和字节统计，`agent_session_summaries` 保存长会话摘要。应用没有数据库静态加密；任何能读取数据库、WAL 或备份的人都可能读取聊天中的手机号、邮箱、薪资、备注、简历和查询结论。会话消息不是短暂前端状态，必须纳入数据库访问、备份、留存和删除政策。

浏览器 `localStorage` 只保存符合 UUID 格式的当前活动会话 ID 和历史面板开关，不保存聊天正文、摘要或候选人敏感字段。这一设计减少浏览器持久层副本，但不等于聊天内容未落盘；SQLite 才是事实来源。删除会话会级联删除当前 SQLite 中的消息和摘要，不能清理模型网关日志、本地 Agent 导出、数据库/WAL 旧页、导出副本或历史备份。

长会话达到消息或字节阈值后，服务端可能把最多 256 KiB 的既有摘要和历史消息发送到已配置模型网关生成不超过 16,000 字符的新摘要。摘要请求使用 strict JSON Schema 且无 tools，但仍可能包含敏感事实；摘要、历史消息和工具结果都作为不可信数据，不会因此获得写权限。摘要失败不阻塞已完成问答，也不会自动擦除本地原消息。

V8 全业务字段 FTS 会在同一 SQLite 中为允许业务字段建立可搜索副本。来源 JSON 被展开、长值分段但不截断，因此 `search_documents_v2` 可能包含与候选人主表、备注、活动、来源、职位、人才库、履历和附件正文相同的敏感内容。该表、FTS shadow 表和 coverage 属于内部状态，不进入普通 Agent schema 目录；会话表、附件物理路径和向量 BLOB 也不向 Agent 只读 SQL 暴露。候选人删除和业务更新通过 dirty 同步清理或重建搜索文档，但历史备份仍需独立留存/销毁流程。

Agent 没有任何新增、修改、归档、恢复、关系、附件确认或删除能力。附件解析建议必须由用户在差异预览中选择，再由普通业务 API 重新校验并写入。现有网关未确认 Embedding，V6 未向其他服务发送文本生成向量。

附件 suggestion provider 会在现有网关已配置时发送最多 120,000 字符和 100 条记录，用 strict JSON Schema 且不提供 tools；这仍是一次可能包含敏感简历的模型传输。网关不可用时本地规则建议继续工作，模型输出无论成功与否都不能绕过用户确认 API。

## 8. 数据生命周期

### 8.1 收集和使用

1. 确认数据来源和处理目的合法。
2. 在预览中核对稳定 ID、字段分类、非空增量、申请/职位跳过和缺失身份错误。
3. 用 `source_system`、`source_record_id`、`source_application_id` 和 `import_batch_id` 保留血缘。
4. 禁止只凭姓名合并；身份冲突必须人工复核。
5. 只允许业务必要人员接触原始文件、数据库、备份和导出。

### 8.2 留存

公司需要分别确定以下对象的期限和触发条件：

- 在库和已归档候选人。
- 人才库关系与移出记录。
- 职位及候选人职位关系。
- 历史申请来源、评估、流程原始载荷和隐私授权。
- 备注、活动和导入批次。
- 原始导入文件、错误报告和导出文件。
- 简历附件原文件、隔离预览、解析正文、全文索引、字段来源和清理失败任务。
- 数据库、WAL 和备份。
- Agent 查询审计、本地导出、请求与模型网关日志。
- Agent 会话、消息、长会话摘要及其中可能重复出现的敏感查询结果。
- V8 全业务字段搜索文档、FTS shadow 数据、dirty/checkpoint/coverage 状态。

当前“归档”是可恢复的业务状态，不是依法删除。关系解除也不删除候选人主档。系统提供已归档候选人和职位的单条/批量永久删除，但它只清除当前应用数据库与本地候选人附件；来源系统、导出副本和历史备份的过期/销毁及完整删除证明仍需单独流程。

### 8.3 更正、导出和删除

- 更正：候选人核心字段和求职偏好通过受控 API 修改并写活动记录。
- 导出：候选人筛选和按职位导出都会产生新的个人信息副本。
- 归档：候选人、职位和人才库使用软归档并可恢复。
- 关系解除：只删除人才库关系或职位关系，不删除两端实体。
- 永久删除：候选人和职位均只允许已归档目标。服务端短时一次性 token 绑定目标与并发版本，提交整批重验；候选人删除主档、联系方式、照片 URL、备注、活动、关系、履历、偏好、来源、评估、授权、申请来源、附件元数据和检索索引，并通过清理队列删除物理文件。职位删除只清理职位和关系，候选人档案不变。
- 共享数据：职位、人才库实体和导入批次不随候选人删除。
- 最小审计：保留候选人内部 ID 的 SHA-256 和删除时间，不含姓名、联系方式、照片地址、来源 ID、原始载荷或可恢复快照。当前无认证，因此不具备可靠操作者身份。
- 外部边界：永久删除不连接或修改北森等来源系统，也不自动清理导出文件或历史备份，不能单独作为全链路删除证明。

## 9. 备份、迁移与恢复

- 应在应用停止后备份完整数据库文件集，避免只复制仍在 WAL 状态下的主 `.db`。
- 数据库、`-wal`、`-shm` 和备份都包含高敏感数据，必须限制访问并依赖受控存储或全盘加密保护。
- SQLite 当前没有应用级静态加密，备份复制后也不会自动加密。
- v2 迁移自动化已在系统临时目录的隔离 `legacy.db` 上验证：旧测试行保持不变、v1/v2 各记录一次、八张新表和新列存在、`foreign_key_check=0`。

## 11. 多人版附加要求

当前多人部署仍不支持。部门版至少需要：

- 身份认证、SSO、最小权限 RBAC 和字段级权限。
- 把远程签名照片迁移到受控本地或公司内部附件存储，并为现有简历附件补充逐用户鉴权、恶意软件扫描、集中存储、备份和删除链路；这是附件进入部门版的硬门槛。
- 部门/租户隔离和敏感详情访问授权。
- TLS、共享数据库、并发控制和可靠事务边界。
- 集中且不可伪造的审计、管理员复核和安全告警。
- 数据库与备份静态加密、集中备份和恢复演练。
- 留存自动化、物理删除、备份过期和个人信息请求流程。

认证/RBAC和本地附件迁移两项硬门槛，以及其余能力完成并验收前，不得把个人版暴露给其他用户。
