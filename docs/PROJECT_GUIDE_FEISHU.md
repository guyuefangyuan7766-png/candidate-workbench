# 拾才工作台：项目功能与实现说明

> 编写日期：2026-10-06  
> 面向读者：招聘业务人员、产品负责人、开发与运维人员。  
> 编写依据：当前工作区源码、接口定义、数据库建表与迁移、配置样例及项目内文档；Git HEAD 为 `6c78d5d`。本文介绍代码中已经实现的能力，不代表所有可选能力已在当前运行环境启用，也不代表本次完成了生产部署验收。

## 1. 项目是什么

拾才工作台是一个可自行部署的人才资料管理系统。它把散落在表格、北森导出文件和简历附件中的信息，整理为可检索、可分组、可关联职位的候选人档案，并提供基于真实资料回答问题的 AI 助手。

项目的核心工作链路是：

**资料导入 → 身份去重 → 档案沉淀 → 人才检索 → 人才库分组与职位关联 → 备注跟进与资料导出。**

它采用“本地数据优先”的设计：候选人和业务关系主要保存在本机 SQLite，附件保存在受控目录。日常档案管理不依赖模型服务；启用 AI 助手、远程语义检索或附件模型建议时，对应请求会访问配置的外部模型网关。

项目目录名为“北森”，但产品并非北森官方系统，也不是与北森实时双向同步的连接器。当前北森接入以导出表格的专用导入逻辑为主。

### 1.1 当前能力边界

- 已实现：候选人档案、人才库分组、职位管理与关联、导入导出、附件解析、履历检索、只读 AI 助手、归档恢复、永久删除、可选 LDAP 登录。
- 不属于当前完整能力：招聘申请流程引擎、面试排期、Offer 审批、薪酬人事管理、北森实时同步、完整多租户与角色权限体系。
- 历史 `candidates.stage` 字段为兼容数据保留，不能据此把项目理解为已经具备完整 ATS 招聘流程。

### 1.2 版本口径

当前 `package.json` 的应用版本为 **0.5.0**；README 和部分历史文档提到已发布的 0.2.0；LDAP 增量文档使用 **0.6.0** 的迭代标记，且相关代码已经存在。这些口径尚未完全统一。

主库迁移账本上限为 **V13**。认证使用独立 `auth.db`，与业务主库迁移编号不同。应用版本、数据库迁移版本、历史“人才库领域 V2”不能混为一谈。

因此，本文以源码描述功能，不以某个版本标签推断线上状态。

## 3. 总体架构与技术选型

### 3.1 系统如何组成

系统由浏览器前端、Node.js 后端、本地数据库、附件文件区、检索索引和可选外部服务组成：

```text
浏览器：React + TypeScript
        |
        | 同源 HTTP API
        v
Express 应用服务
  |-- 可选 LDAP 登录与会话守卫
  |-- 候选人 / 职位 / 人才库业务服务
  |-- 导入、附件、AI 异步任务
  |-- SQLite 主库 recruitment.db
  |-- 独立认证库 auth.db
  |-- 私有附件与导入暂存目录
  |-- FTS5 全文检索 + 独立向量索引
  |
  +-- 可选模型网关 / 受控互联网搜索

耗时工作：Worker 或独立子进程
  表格解析、导入提交、附件解析、只读查询、检索及索引维护
```

这里的 Worker 是后台执行单元。把耗时工作移出主请求线程，是为了让一次大文件解析或复杂查询尽量不阻塞其他页面请求。

### 3.3 页面与导航如何实现

`src/App.tsx` 持有主页面和工具页面状态。主页面包括工作台、候选人、人才库分组、职位和职位详情；工具页面包括 AI 助手、履历检索和附件解析。

系统用单一 `Surface` 联合类型表示当前显示的是普通页面、工具还是导入页，并与 URL 同步。这样切换工具时不会同时叠加导入页和其他页面。浏览器前进、后退也会映射回界面状态。

AI 页面另用 `assistantPanel` 控制主导航与历史会话栏互斥。布局和响应式样式集中在 `src/workspace.css`，页面外壳在 `src/views/AppShell.tsx`。

## 4. 工作台与候选人档案

### 4.1 工作台概览

**功能用途：** 显示在库人才数、使用中的人才库分组、招聘中职位数、未分组人才，以及人才库分布、来源分布和最近更新信息。统计项可跳转到相应工作页面。

**实现方式：** 前端 `Overview.tsx` 请求 `GET /api/dashboard`；后端 `server/candidates.js` 的 `dashboard()` 对数据库做统计和聚合。首页数据来自数据库，不由 AI 估算。

### 4.2 候选人列表、搜索与筛选

**功能用途：** 新增、编辑、查看候选人，按来源、负责人、标签、职位、人才库、学历、学校、求职状态、归档状态等条件筛选，并支持排序、分页、多选和按职位组织查看。

**实现方式：**

1. 前端维护筛选条件并调用 `GET /api/candidates`。
2. 后端规范化条件，构建参数化查询。
3. 使用数据库计数与 `LIMIT / OFFSET` 返回当前页。
4. 批量补充当前页候选人的职位和人才库关系。
5. `/api/candidates/facets` 返回筛选项和数量，避免前端从当前页自行推算全库情况。

列表默认采用减少敏感字段的返回投影。联系方式、薪资、照片原始字段等不会简单随列表全量返回；详情通过显式请求加载相应资料。这里是数据最小化机制，并不等同于角色权限。

**代码入口：** `src/views/CandidatesView.tsx`、`CandidatesGroupedView.tsx`、`src/components/CandidateDrawer.tsx`、`CandidateForm.tsx`、`server/candidates.js`、`server/validation.js`。

### 4.3 候选人档案包括哪些信息

候选人不是一行姓名和联系方式，而是一组关联资料：

| 信息类别 | 典型内容 | 主要存储 |
| --- | --- | --- |
| 基本档案 | 姓名、联系方式、当前任职、学校、专业、标签、工作年限 | candidates |
| 求职偏好 | 意向职位、地点、薪资、就业或求职相关偏好 | candidate_preferences |
| 分区履历 | 工作、教育、项目等补充档案 | candidate_profile_sections |
| 来源历史 | 来源系统、来源记录 ID、原始来源快照 | candidate_source_records |
| 历史评估 | 测评、面试等导入结果与原始载荷 | candidate_assessments |
| 授权记录 | 协议、同意状态及相应来源数据 | candidate_consents |
| 招聘关系 | 关联职位及申请来源事实 | candidate_positions、candidate_position_sources |
| 跟进信息 | 备注及业务活动记录 | notes、activities |
| 附件资料 | 文件元数据、提取正文及字段来源 | candidate_attachments、candidate_field_sources |

分区、来源、评估等内容分别保存，便于保留原始事实和后续解释“这条信息从哪里来”。

### 4.4 几个容易混淆的字段

- **当前任职 `current_title`：** 候选人现在担任的工作。
- **招聘职位 `positions`：** 公司正在管理的招聘需求对象。
- **入职职位 `hire_position`：** 来源资料记录的实际入职职位文本。
- **入职状态 / 日期：** `hire_status`、`hire_date` 是独立字段，不自动转换为历史招聘阶段。
- **工作年限：** 同时保存 `years_experience_raw` 原文和 `years_experience` 数值投影。例如“3-5 年”或“经验不详”可以保留原文，数值为 null；明确的 0 仍是 0。展示和导出优先原文，数值筛选只使用可安全解析的数值。
- **仅提供入职日期：** 在状态为空的相应写入场景中，系统使用“不确定”；不会把已有明确状态随意覆盖。

这些区分避免把模糊来源强行变成确定事实，也避免将“曾被关联某职位”误当作“具备该职位要求”。

### 4.5 备注、活动与头像

备注用于人工跟进；活动记录用于保留新增、编辑、导入、关联等真实业务动作。接口包括 `/api/candidates/:id/notes` 和 `/api/candidates/:id/activities`。

头像通过候选人头像接口加载，前端统一使用 `CandidateAvatar`、`TwAvatar`，在可用照片与姓名占位之间切换。照片加载失败时回退占位，而不是让两种内容叠在一起。附件中的头像处理集中在 `server/attachment-avatar.js`。

## 5. 人才库分组与职位管理

### 5.1 人才库分组

**功能用途：** 按业务方向、地区或人才类别组织人员，例如“研发人才储备”“设计人才储备”。一个候选人可以加入多个分组，一个分组可以包含多人。

**实现方式：** `talent_pools` 保存分组定义，`candidate_talent_pools` 保存多对多关系。增加或解除成员只改变关系，不复制候选人主档。

分组支持新增、编辑、归档、恢复，以及相应批量操作和永久删除。部分操作校验 `updated_at`，避免用户对已经变化的记录继续执行旧操作。批量关系更新使用事务。

**代码与接口：** `TalentPoolPage.tsx`、`server/talent.js`；`/api/talent-pools`、`/api/talent-pools/:id/candidates`。

### 5.2 职位管理

**功能用途：** 维护职位名称、部门、地点、负责人、要求等资料，搜索和筛选职位，并管理草稿、招聘中、暂停、关闭四种状态。

**实现方式：** `positions` 保存职位，`candidate_positions` 保存候选人与职位的多对多关联。职位详情展示关联候选人，支持批量关联、解除和按职位导出。关系操作先验证目标存在及状态，再事务性写入。

职位状态与软归档分别表达招聘业务状态和是否仍在日常工作区使用。关闭职位不自动等于删除职位，关联职位也不自动启动面试或 Offer 流程。

**代码与接口：** `PositionsView.tsx`、`PositionDetailPage.tsx`、`PositionFormDrawer.tsx`、`server/positions.js`；`/api/positions`、`/api/positions/:id/candidates`。

## 6. 表格导入与北森增量导入

### 6.1 通用导入流程

用户先选择文件和导入方式，再核对字段映射及预览，确认后提交。支持 UTF-8 CSV、XLSX、XLSM 和未加密的 Excel 97-2003 BIFF8 XLS。

```text
上传文件
  → 检查格式、签名、资源限制
  → 后台解析工作簿
  → 映射到业务字段
  → 校验和身份去重
  → 展示新增 / 更新 / 错误等预览
  → 用户确认
  → 后台提交并返回结果
```

**实现方式：**

- `ImportWizard.tsx` 负责前端步骤、映射、任务进度与结果。
- `import-file.js`、`import-file-worker.js` 检查并解析文件。扩展名和真实文件签名需匹配，不靠改后缀识别格式。
- `import-export.js` 生成预览、执行通用映射和提交。
- `import-tasks.js` 保存任务状态、请求指纹和重试信息。
- `import-commit-worker.js` 执行较重的提交工作。

异步任务经历排队、校验、解析、映射、预览、提交等状态。浏览器轮询任务接口，刷新后可通过已有任务信息恢复查询；中断会被识别并标记，不应理解为任何步骤都能无条件自动续跑。

文件大小之外，系统还约束工作表、列、单元格、解压体积、压缩比和 Worker 时间、内存，防止小压缩文件展开成巨大任务。

### 6.2 去重原则

自动身份定位主要使用标准化手机号、邮箱、来源系统加来源记录 ID。**姓名不是自动合并键。**

例如，手机号指向候选人 A、邮箱却指向候选人 B 时，系统应阻断自动合并并提示核对，不能猜测两者是同一人。

预览和提交分开，给用户检查身份冲突、字段含义和更新范围的机会。请求指纹与幂等机制用于降低网络重试造成重复提交的风险。

### 6.3 北森模式的特殊规则

北森模式由 `server/beisen-import.js` 实现，核心身份是首张工作表中精确名称为 **应聘者ID** 的字段。

| 情况 | 当前处理规则 |
| --- | --- |
| 相同应聘者 ID 跨文件再次出现 | 更新或补充同一候选人 |
| 来源值非空 | 可更新相应字段，包括纠正姓名 |
| 来源单元格为空 | 不据此清空已有字段 |
| 同文件同 ID 有多行 | 后出现的非空标量覆盖先出现值；标签合并 |
| 新 ID 缺少姓名 | 不满足创建新候选人的要求 |
| 手机或邮箱命中另一人 | 阻断并要求人工复核 |
| 只有姓名相同 | 不自动合并 |
| 申请 ID 已属于其他候选人 | 不允许改绑到当前人 |
| 缺少可建立的申请或职位关系 | 相应关系可跳过，不一定阻断候选人主档导入 |

申请 ID 和职位信息是可选补充，不是导入所有候选人的必填前提。申请 ID 在有有效职位关系或真实评估载荷时才参与相应归属校验。

职位关联优先遵循北森专用“最后职位类投递的职位id”语义。如果整份工作簿有该专用表头，某行空值不能自行回退成普通“职位编号”；只有整表缺少专用表头时才使用兼容逻辑。也不能根据“入职职位”猜测招聘职位关系。

**重复导入的准确含义：** 通常不会重复创建同一候选人、职位或关系，但仍可能更新修改时间、导入批次并追加活动，因此是“重放安全”，不是所有数据库状态都完全不变。

## 7. 简历附件解析与批量附件

### 7.1 单份附件能做什么

支持 PDF、DOCX、XLSX、XLSM、BIFF8 XLS、UTF-8 CSV/TXT。用户可以查看解析正文、候选人身份匹配、结构化建议和字段差异，选择更新既有档案或创建新档案。

**核心流程：**

1. 上传并验证文件类型、大小及文件结构。
2. 在 Worker 中提取正文。
3. 识别联系方式等身份线索。
4. 定位可能关联的候选人，并检查冲突。
5. 生成差异预览和字段建议。
6. 用户确认后保存附件及选定的档案更新。
7. 保存字段来源，更新相关检索资料。

上传和模型输出本身不会跳过确认直接修改候选人。

### 7.2 不同文件如何解析

- **PDF：** PDF.js 提取页面文本与坐标，按视觉行重建阅读顺序；只有能确认独立垂直栏时才按栏阅读，以减少表格、时间线中的日期和值被错误拆散。
- **DOCX：** Mammoth 提取正文，再进行字段和段落识别。
- **Excel：** 按工作表、行列提取内容；旧 XLS 由对应 BIFF8 读取器处理。
- **CSV/TXT：** 读取文本并进入后续结构化识别。

解析记录的原始提取正文保留审计依据，公开 section、evidence、suggestion 等投影执行有界清理。正文与模型建议是两种不同数据，模型不能替换原始正文。

默认解析没有 OCR；无文本层的扫描 PDF 不应被宣传为已支持。

### 7.3 文本模型建议和 PDF 视觉建议

代码中实现了可选文本建议通道，以及 `ATTACHMENT_VISUAL_CAPABILITY=image_input` 控制的 PDF 页面视觉建议通道。配置样例默认关闭视觉能力。

模型只负责建议结构化字段，输出需要通过本地 Schema、字段、证据和值检查；视觉输入还有页数、像素、字节量和超时限制。能力关闭、网关异常或输出不合规时会记录降级结果。

视觉建议通道的存在不等于系统已经具备通用扫描件 OCR。启用后页面图像可能发送到模型网关，数据出站范围与仅本地文本解析不同。

**代码入口：** `AttachmentWorkflow.tsx`、`server/attachments.js`、`attachment-parser.js`、`attachment-parser-worker.js`、`attachment-model-contract.js`、`attachment-visual-parser.js`。

### 7.4 批量附件和 ZIP

批量工作流支持多文件和 ZIP，逐项展示解析、匹配、待确认、成功、失败、跳过及取消状态，并提供符合条件的重试操作。确认仍按项目进行，不会因批量上传就全部自动写入。

`attachment_import_batches` 保存批次，`attachment_import_items` 保存每份文件的状态、错误及确认结果。批次令牌以哈希形式保存，确认操作有幂等指纹。

源码默认限制包括：单附件 15 MiB、一次最多 100 个上传文件、ZIP 128 MiB、批次上传总量 256 MiB、解压后最多 256 个文件，后台解析并发为 2。具体限制以服务端配置和校验为准。

`secure-zip.js` 等模块检查路径、条目、解压体积和压缩比，阻止路径穿越和异常压缩包。

**代码入口：** `AttachmentBatchWorkflow.tsx`、`server/attachment-batches.js`、`server/secure-zip.js`。

## 8. 人才检索如何工作

项目存在三种不同查询用途：

| 查询方式 | 适用场景 | 实现重点 |
| --- | --- | --- |
| 候选人列表筛选 | 按姓名、来源、标签、学历、关系等字段找人 | 参数化数据库查询、分页 |
| 全业务字段搜索 | 跨候选人、职位、人才库、来源等资料寻找关键词 | schema 驱动的业务文档与 FTS5 |
| 人才履历混合检索 | 按技能、经历、语义及组合条件寻找候选人 | 查询计划、FTS5、向量、融合、重排及证据 |

### 8.1 混合检索流程

以“找有 Unity 项目经历、至少 3 年经验的人”为示例，系统的处理流程是：

1. **理解问题。** 可用时由模型生成符合固定 Schema 的查询计划；规则解析及概念别名辅助处理。
2. **验证计划。** 检查字段、原文依据、AND / OR / 排除等逻辑。模型不能直接生成任意写库指令。
3. **确定资格范围。** 将可确定的年限、地点、关联关系等约束转为受控 SQL 条件。
4. **关键词召回。** FTS5 从本人资料、履历分区和允许的附件正文中找词语和短语。
5. **语义召回。** 查询向量匹配独立向量索引，补充表达不同但语义接近的材料。
6. **融合和重排。** 用 RRF 按排名融合多路结果，再对受限候选集合执行可选模型重排。
7. **证据回查。** 核对当前候选人、原文来源、归档状态和内容修订，避免使用已经失效的索引事实。
8. **返回结果。** 提供候选人、命中证据、分页，以及完整性和降级信息。

RRF 可以理解为“综合各条检索通道的名次”，不需要直接比较不同通道的原始分数。重排用于进一步判断候选材料与问题的相关程度。

### 8.2 为什么区分“本人证据”和“关联证据”

某人被关联到“需要 Python 的数据岗位”，不能证明他本人会 Python。项目使用 `ownership: self / related` 区分事实归属：

- 本人履历、本人项目或本人简历中的内容可以作为能力证据。
- 职位要求、分组描述和关系信息可以用于关联筛选，但不能直接冒充本人技能。

这是检索质量的重要约束，尤其在职位描述很丰富、个人简历很简略时。

### 8.3 向量索引如何构建和维护

原始材料按规则切片后生成 Embedding，向量与元数据放在独立索引目录，不直接把 HNSW 文件塞进业务主库。索引空间区分模型、维度及切片版本，避免不同空间混用。

查询使用 USearch HNSW；更新采用不可变代际及 manifest 发布机制，保留当前与上一代。新代完整构建后才发布，失败不会把半成品切成当前索引。

增量维护先检查文档修订，只有变化材料再读取正文、计算内容哈希、切片和向量化。维护默认按开机周期触发一次，而不是把配置样例中的旧 interval 值理解为每五分钟全量重建。

出站检索文本通过 `search-data-minimization.js` 遮蔽已知身份值、联系方式、证件号等内容；这是规则型最小化处理，不能保证识别所有敏感信息，也不代表 AI 助手所有工具证据都采用同样策略。

### 8.4 超时、降级与完整性

混合检索由常驻只读 Worker 执行，使用有界排队、查询预算和分页快照。当前实现在线查询预算默认及上限为 30 秒，模型规划、Embedding、重排另有子预算。

向量近似召回和有限重排窗口不保证全量精确排序。系统通过 `completeness`、降级字段等表达结果范围；模型、向量或重排不可用时，应结合返回状态理解结果，不能只看页面上有结果就认定全部通道成功。

**核心代码：** `search-query-plan.js`、`search-query-plan.schema.json`、`search-concepts.js`、`hybrid-search.js`、`hybrid-search-service.js`、`search-model-adapters.js`、`search-vector-store.js`、`search-vector-maintenance*.js`、`business-search.js`。

**主要接口：** `GET/POST /api/resume-search`、`GET /api/resume-search/status`、`GET /api/resume-search/options`。

## 9. 拾才 AI 助手如何工作

### 9.1 用户可以做什么

用户可以用自然语言查找候选人、阅读履历、比较资料、统计人才分布、查询备注和来源、按查询结果生成 CSV；配置允许时还能搜索互联网并读取公开网页。

示例：“统计在库人才的来源分布”“找具有某项项目经历的人并给出依据”。这些是用法示例，不代表本次已执行真实候选人查询。

### 9.2 一次问答的执行链路

```text
用户提问
  → 保存会话消息并创建任务
  → 判断对话 / 数据库 / 互联网 / 混合路径
  → 模型选择本路径允许的工具
  → 服务端校验参数并执行工具
  → 收集数据库或网络证据
  → 模型组织回答
  → 保存回答、任务状态和执行事实
  → 前端显示结果及执行时间线
```

AI 不是直接读整个数据库的聊天框。它通过服务端定义的工具获取有界证据，必要时多轮调用。源码包含重试、取消、超时、无进展检测以及上下文和结果大小约束。

默认允许同时执行 2 个 AI 任务、排队 20 个；实际配置可在代码规定的范围内调整。

### 9.3 20 个工具分别负责什么

| 工具类别 | 工具名称 |
| --- | --- |
| 数据结构与只读 SQL | get_schema_catalog、execute_readonly_query |
| 候选人资料与历史 | query_candidates、get_candidate_full、query_candidate_notes、query_candidate_activities、query_candidate_sources、query_candidate_assessments |
| 职位与分组 | query_positions、get_position_full、query_talent_pools |
| 全库统计 | aggregate_recruitment_data |
| 全文及履历检索 | search_all_records、search_candidate_resumes、get_candidate_resume |
| 附件 | query_candidate_attachments、get_attachment_text |
| 互联网 | search_web、fetch_web_page |
| 文件交付 | export_query_results |

### 9.4 “只读”是如何保证的

数据库查询使用独立只读连接，并通过 SQLite authorizer 校验操作、表、列及函数；只允许受控 SELECT / 只读 CTE，禁止业务写入、DDL、ATTACH、危险 PRAGMA、扩展与文件函数。查询还有时间、行数及结果大小限制。

它不能替用户新增候选人、修改资料、关联职位、归档、恢复、确认附件或删除业务数据。

**只读指业务数据库权限。** 会话记录、任务记录、查询审计和 CSV artifact 仍需要由服务端写入相应存储，因此不是“整个应用绝不写文件”。

### 9.5 会话、任务和界面

`agent_sessions`、`agent_messages`、`agent_session_summaries`、`agent_tasks` 保存会话和执行结果。前端提交后可以收到 202，随后轮询任务，避免把长回答绑在一次浏览器 HTTP 等待上。

系统支持会话管理、任务取消及回答重试。启用认证后，会话和相关任务访问校验当前用户归属；历史无用户会话由兼容逻辑处理。**会话隔离不等于候选人数据隔离。**

执行时间线读取真实任务状态、阶段耗时和已调用工具，不展示模型私有推理，也不会伪造 API 没有提供的单工具耗时。

Markdown 渲染配合链接策略控制危险 URL。互联网回答保留来源链接和访问时间；网页与附件中的指令被当成不可信资料。

### 9.6 数据出站边界

配置远程 `AGENT_BASE_URL` 后，问题、近期对话和工具证据可能发送到该网关。现有 Agent 工具可以返回未打码业务字段，包括联系方式、薪资、备注、评估或来源载荷，不能把“只读”理解为“只发匿名数据”。

**核心代码：** `server/agent.js`、`agent-sessions.js`、`readonly-query.js`、`readonly-query-worker.js`、`web-search.js`；`AssistantDrawer.tsx`、`AssistantExecutionTimeline.tsx`、`AssistantMarkdown.tsx`。

## 10. 导出、归档与永久删除

### 10.1 导出

候选人结果支持 CSV 和 XLSX，并可按职位等条件导出。后端依据筛选条件生成数据，不仅导出浏览器当前显示的几行。

CSV 导出处理公式注入风险，避免来源单元格被表格软件直接当作公式执行。AI 工具还可以将只读 SQL 结果生成本地 CSV artifact，适合不宜全部塞入模型回答的明细。

**代码与接口：** `server/import-export.js`、`server/readonly-query.js`；`/api/export`、`/api/candidates/export`、`/api/agent/exports/:id`。

### 10.2 归档和恢复

归档通过 `archived_at` 等状态将记录移出日常使用范围，保留档案和关系以供恢复。候选人、职位和人才库都有相应能力，部分支持批量操作。

### 10.3 永久删除

候选人和职位永久删除采用预览与提交机制。预览统计影响并生成短期令牌，绑定目标和数据版本；提交时检查令牌、操作类型、有效期及记录是否变化，再执行事务性删除。

默认删除预览令牌有效期为 2 分钟；过期或数据已变化需要重新预览。人才库删除走自己的校验与关系处理逻辑，不应混同为完全相同的令牌协议。

候选人删除涉及关联资料、检索数据、附件清理等生命周期处理，并保留最小删除审计。永久删除的恢复需依赖备份，不能用“恢复归档”按钮撤回。

**代码入口：** `PermanentDeleteDialog.tsx`、`server/deletions.js`、`server/candidates.js`、`server/talent.js`、附件清理相关逻辑。

## 11. LDAP 登录和访问控制

### 11.1 默认个人模式

`AUTH_ENABLED` 默认关闭，应用限制在回环地址运行，不要求登录。浏览器通常访问 `http://127.0.0.1:4173`。

### 11.2 开启认证后的登录流程

1. 前端提交账号和密码。
2. 服务端规范化账号并转义 DN 特殊字符。
3. 用 `LDAP_USER_DN_TEMPLATE` 构造用户 DN。
4. 通过 ldapts 进行绑定认证。
5. 检查账号白名单。
6. 生成随机会话令牌，通过 HttpOnly、SameSite Cookie 传递。
7. 认证库只保存令牌哈希，不保存登录密码。
8. 后续业务 API 经统一会话守卫验证。

公开接口主要是 health、登录和认证状态；其余 API 在认证启用时受统一前缀守卫保护。

会话默认 12 小时空闲过期、30 天绝对过期。登录限流默认以账号 5 分钟 5 次失败、来源地址 1 分钟 30 次失败作为两层限制。

### 11.3 白名单与权限边界

`data/auth-allowlist.txt` 一行一个账号，默认每 30 秒重读。名单更新生效后，被移除账号的后续请求将被拒绝。

- 启动时没有名单文件且未配置引导名单：不实施白名单限制。
- 文件存在但为空：拒绝所有账号。
- 已生效文件后来消失：源码保留上次名单并记录异常，不自动放开。

因此部署时先准备名单，再开启认证。

白名单解决“谁能进入”，不解决“进入后能看哪些候选人”。当前没有完整 RBAC、字段级权限或候选人按负责人隔离。LDAP 直接绑定也不能可靠识别“目录标记停用但仍允许绑定”的特殊状态，账号退出需结合目录及白名单管理。

### 11.4 网络部署

推荐由 HTTPS 反向代理转发到 `127.0.0.1:4173`，应用继续保持回环绑定。代理部署需正确设置 Secure Cookie 和可信代理，并确保来源头由受信代理提供。

直接监听非回环 IP，需要认证开启、显式允许非回环、完整 LDAP 配置及绑定地址白名单等条件同时成立。已有受控监听代码不等于可以直接向整个公司或互联网开放。

**代码入口：** `server/auth/config.js`、`ldap.js`、`allowlist.js`、`store.js`、`middleware.js`、`index.js`；`src/components/LoginPage.tsx`。

## 12. 数据模型和一致性

### 12.1 主要关系

```text
候选人 candidates
  ├─ 多对多 → 职位 positions
  ├─ 多对多 → 人才库 talent_pools
  ├─ 一对多 → 履历分区、来源、评估、授权
  ├─ 一对多 → 备注、活动、附件
  └─ 派生 → 履历检索文档与全文索引

AI 会话 → 消息、摘要、异步任务
附件导入批次 → 每个附件处理项
表格导入任务 → 预览、提交状态与请求指纹

独立 auth.db → 认证用户、会话令牌哈希
独立向量目录 → 索引代际、元数据、向量及缓存
```

### 12.2 一致性保障

- SQLite 开启外键约束；文件数据库使用 WAL，提高读写共存能力。
- 关系变更、关键批量操作等通过事务提交，减少半完成状态。
- 迁移和辅助建表逻辑按可重复执行设计，主迁移账本记录 V1 至 V13。
- 部分删除、分组和批量操作用记录版本或预览快照校验，发现变化时要求重新操作。
- 搜索资料通过同步、脏数据维护及查询时回查尽量保持有效；向量索引与主库不是同一事务，必须区分索引维护状态与主档保存成功。
- 长任务持久化状态和请求指纹，便于识别重复请求和中断。

业务活动日志、删除审计和 Agent 查询审计已存在，但不等于完整的“每个用户在何时读取或导出了哪些敏感字段”的企业审计体系。

## 13. 部署、运行与备份

### 13.1 本地启动

前置环境为 Windows、Node.js 24 或更高版本。双击 `start.cmd`，或运行：

```powershell
.\start.ps1
```

启动脚本检查 Node.js 和依赖锁，在需要时安装依赖，然后构建前端并启动应用。默认访问 `http://127.0.0.1:4173`。

开发与构建命令：

```powershell
npm run dev
npm run build
npm start
```

`npm run dev` 是前端开发服务；API 仍需对应后端运行。生产入口为 `server/index.mjs`。

### 13.2 关键配置

| 配置 | 用途 |
| --- | --- |
| HOST、PORT | 服务监听地址与端口 |
| APP_DATA_DIR、DB_PATH | 业务数据位置；DB_PATH 优先 |
| AGENT_BASE_URL、AGENT_API_KEY、AGENT_MODEL | AI 模型网关 |
| SEARCH_REMOTE_ENABLED | 远程混合检索能力开关 |
| SEARCH_QUERY_MODEL、SEARCH_EMBEDDING_MODEL、SEARCH_RERANK_MODEL | 检索规划、向量和重排模型 |
| SEARCH_VECTOR_DIRECTORY、SEARCH_VECTOR_MAINTENANCE_ENABLED | 向量目录及维护开关 |
| ATTACHMENT_TEXT_*、ATTACHMENT_VISUAL_* | 附件模型建议通道 |
| AUTH_ENABLED、LDAP_URL、LDAP_USER_DN_TEMPLATE | LDAP 认证 |
| AUTH_ALLOWLIST_FILE、AUTH_ALLOWED_USERS | 账号准入 |
| AUTH_COOKIE_SECURE、AUTH_TRUST_PROXY | HTTPS 代理下的会话配置 |
| AUTH_ALLOW_NON_LOOPBACK、AUTH_BIND_HOSTS | 受控网络监听 |

`server/index.mjs` 读取环境配置，并可从 `data/search-runtime.json` 加载允许的检索运行设置；该文件内允许的项目会覆盖相应进程环境设置。排查“改了变量却没生效”时需一起检查启动脚本、环境和运行配置文件。

密钥属于服务端配置，不写入前端代码。示例配置应按环境核对，不直接当作生产启用证明。

### 13.3 备份与恢复

完整备份需要覆盖业务数据库、附件与私有文件、检索向量目录、运行配置，以及启用认证时的认证库和白名单。

最易操作的一致性方案是正常停止服务，再备份整个实际数据目录；自定义数据路径也需要覆盖。不要在服务写入期间只随手复制一个 `.db` 文件，因为 WAL 中可能还有已提交数据。

恢复前先保留当前数据副本，再恢复一致的文件集并核对应用版本。向量索引可重建，但有时间和模型调用成本；备份已有索引有助于缩短恢复时间。认证库包含会话状态，应按敏感配置管理。

运维还需要检查健康接口、认证状态、检索状态、模型网关和索引维护状态。多实例共享会话、统一限流、高可用与完整监控尚不能视为现成能力。

## 14. 常见问题如何定位

| 现象 | 优先核对 |
| --- | --- |
| 同名候选人没有合并 | 是否存在可靠手机号、邮箱或来源 ID；姓名本来就不是合并键 |
| 北森导入拒绝关联 | 应聘者 ID、申请 ID 归属和联系方式是否冲突 |
| 导入后职位关系缺失 | 专用职位 ID 表头和本行值是否有效，是否只提供了入职职位 |
| 工作年限无法按范围筛选 | 是否只有原文而没有可安全解析的数值投影 |
| PDF 无法提取正文 | 是否为扫描件或没有文本层；默认链路不做 OCR |
| 附件上传后档案没变化 | 是否仍处于待确认，是否选中了需要保存的字段 |
| 检索结果与预期不同 | 硬条件、同义词、本人证据、向量状态及降级原因 |
| AI 长时间处理中 | 任务状态、排队、网关超时、工具错误；避免反复重复提交 |
| 登录后又回到登录页 | Cookie Secure、HTTPS、代理头、会话期限和白名单 |
| 新增白名单用户仍不能登录 | 名单路径、刷新周期、LDAP 凭据和登录限流 |
| 修改检索变量不生效 | 启动脚本及 search-runtime.json 是否覆盖相应值 |

## 17. 当前限制与后续建设方向

1. **权限需要进一步细化。** 已有 LDAP 准入和 AI 会话归属，但候选人资料尚无完整角色、字段和组织范围隔离。
2. **审计需要补齐操作人维度。** 当前活动及查询审计不覆盖所有敏感访问与导出责任追踪。
3. **招聘流程不是现成能力。** 如需申请阶段、面试协同、Offer 审批，应作为独立业务模块建设。
4. **扫描简历处理仍有限。** 默认无 OCR，受控视觉建议不能替代完整 OCR 工作流。
5. **多人容量需实测。** SQLite、单实例任务调度、共享网关及只读检索 Worker 的组合，需要按真实并发验证，不能仅根据历史单次耗时承诺容量。
6. **部署治理仍需运维配套。** 反向代理、HTTPS、备份恢复演练、密钥管理、日志监控及告警需要在部署环境落地。
7. **版本和文档应统一。** package 版本、LDAP 迭代标记与历史发布说明目前不完全一致，后续发布应统一更新。
8. **检索质量需持续评估。** 同义概念表、规则回退、模型查询理解和近似向量召回都有边界，应使用带预期结果的匿名样本持续评估。
