# 关键技术决策记录

状态说明：`已采纳` 表示当前实现必须遵守；改变已采纳决策时，应在本文追加新记录，而不是覆盖历史原因。

## ADR-001：先实现轻量个人 MVP

- 日期：2026-08-03
- 状态：已采纳
- 决策：当前阶段不引入完整开源 ATS，先实现可验证的数据整理、导入导出和只读 Agent 基础。
- 原因：尚无真实北森样表，完整平台改造成本高，先验证核心数据工作流能更快暴露字段和迁移问题。
- 后果：面试排期、评价、Offer、附件等完整 ATS 功能暂不在 `0.1` 范围内；开源 ATS 选型保留到部门版决策。

## ADR-002：React、Express 和 SQLite

- 日期：2026-08-03
- 状态：已采纳
- 决策：前端使用 React/TypeScript，业务 API 使用 Express，个人数据使用 Node.js 内置 SQLite。
- 原因：部署依赖少，适合本机单用户，代码边界清晰，未来可以保留 API 层并替换数据库。
- 后果：当前不支持并发多人、集中高可用或跨机器共享。

## ADR-003：个人版只监听回环地址

- 日期：2026-08-03
- 状态：已采纳
- 决策：仅允许 `127.0.0.1`、`localhost` 或 `::1`，非回环 `HOST` 启动失败。
- 原因：该决策建立时 API 没有认证、RBAC、CSRF 防护或速率限制；V6 后续只增加了请求体解析前的 Origin 写保护，完整多人版边界见 ADR-035。
- 后果：不能把当前版本直接部署到局域网或公网；多人版必须独立补齐安全能力。

## ADR-004：服务端解析和导出表格

- 日期：2026-08-03
- 状态：历史决策；格式范围已由 ADR-022 取代
- 决策：使用 ExcelJS 在服务端处理 CSV/XLSX/XLSM，浏览器只负责上传、映射和展示预览。
- 原因：避免把真实表格整体交给浏览器第三方解析链路，统一文件大小、行数、格式和校验规则。
- 后果：当前只读取第一个工作表，不支持旧版 `.xls`，GBK CSV 需先转换为 UTF-8。

## ADR-005：身份键去重，不按姓名合并

- 日期：2026-08-03
- 状态：已采纳
- 决策：候选人重复判断只使用标准化邮箱、手机号或 `source_system + source_record_id`。
- 原因：姓名不是稳定身份标识，同名候选人常见。
- 后果：多个身份键命中不同候选人时返回 `identity_conflict`，必须人工复核；系统禁止自动更新或合并。

## ADR-006：软归档优先

- 日期：2026-08-03
- 状态：历史决策；“界面不提供候选人物理删除”已由 ADR-025 定向取代，软归档优先原则继续有效
- 决策：用户界面不提供物理删除，候选人使用 `archived_at` 软归档并允许恢复。
- 原因：降低误操作和数据丢失风险，保留活动记录。
- 后果：依法删除和留存到期处理尚需在真实数据阶段设计专门流程。

## ADR-007：Agent 只调用受控只读工具

- 日期：2026-08-03
- 状态：历史决策；三工具和禁止 SQL 的结论由 ADR-030 取代，无写能力原则继续有效
- 决策：模型不能直接访问数据库或生成 SQL，只能调用三个由服务端实现的结构化只读工具；RAG 不承担结构化 CRUD。
- 原因：模型输出不可直接作为可信写指令，候选人数据包含个人信息。
- 后果：当前不能通过自然语言修改数据；未来写工具必须经过 JSON Schema、权限、预览确认、事务和审计。

## ADR-008：模型侧默认最小化个人信息

- 日期：2026-08-03
- 状态：历史决策；字段最小投影由 ADR-030 的“全字段按需只读 + Top-K 上下文控制”取代
- 决策：搜索和统计结果不发送联系方式；详情仅发送脱敏电话和邮箱，不发送薪资、备注、活动或内部血缘。
- 原因：模型完成常见招聘查询不需要完整 PII。
- 后果：需要查看完整信息时由用户在本地候选人详情中完成，不能要求 Agent 绕过投影。

## ADR-009：职位是一等实体，候选人与职位使用多对多关系

- 日期：2026-08-04
- 状态：已采纳
- 决策：新增独立 `positions` 表和 `candidate_positions` 关联表；一个候选人可关联多个职位，一个职位可关联多个候选人，复合主键禁止重复关系。
- 原因：招聘职位是候选人筛选和分组的核心依据，不能继续使用候选人的 `current_title` 自由文本替代。
- 后果：`current_title` 继续表示候选人当前任职；解除关系不删除两端主记录；既有候选人不会自动创建职位或关系，默认属于未分配职位。

## ADR-010：候选人阶段继续保持全局，不引入职位申请实体

- 日期：2026-08-04
- 状态：已采纳；默认展示与操作行为由 ADR-014 收窄
- 决策：本迭代不创建 application 表，`candidates.stage` 仍是候选人的唯一全局阶段，`candidate_positions` 只表达关联。
- 原因：当前目标是候选人资料整理和按职位分组，不是完整 ATS；每职位阶段会连带引入申请历史、流程配置、面试和 Offer 等更大领域模型。
- 后果：阶段数据继续以全局字段兼容保存，不具备按职位分别记录阶段的能力；默认 UI 和通用导入不展示或修改阶段，V2 Agent 当时也隐藏该字段，V6 Agent 可按需只读。兼容接口若显式修改阶段，仍会影响该候选人的全部职位关系。

## ADR-011：职位表使用加法式建表，回退依赖升级前备份

- 日期：2026-08-04
- 状态：已采纳
- 决策：启动时通过 `CREATE TABLE IF NOT EXISTS` 新增 `positions`、`candidate_positions` 和索引，不重建或改写 `candidates`；升级前停止服务并备份 SQLite 文件集。
- 原因：当前变更只增加独立表，可在不迁移既有候选人行的前提下完成，并保持个人版部署简单。
- 后果：项目仍没有通用版本迁移和自动 down migration；失败回退必须同时恢复旧代码和升级前数据库备份，不能只回退代码。

## ADR-012：职位关系写入通过业务 API，Agent 保持原三个只读工具

- 日期：2026-08-04
- 状态：部分保留；业务 API 写入原则有效，三工具和最小投影由 ADR-030 取代
- 决策：批量职位关联和批量解除均由业务 API 校验并在 SQLite 事务中执行；Agent 不新增职位、关联或写工具。候选人只读投影仅包含最小化的关联职位 `id`、名称和状态，以及人才库 `id` 和名称；职位描述及其他职位或申请详情不进入模型投影。
- 原因：职位关系属于结构化业务数据和写操作，不应交给模型直接修改；当前 Agent 的数据最小化承诺优先于自然语言覆盖面，同时允许在候选人检索结果中识别必要的职位和人才库归属。
- 后果：批量关联/解除支持 1 至 100 个候选人、幂等重放和全成全败；职位及关联只能在本地界面操作。Agent 可以基于候选人的最小化关系回答关联职位或人才库问题，但没有独立职位查询、职位详情或任何职位写工具。未来扩大投影或工具范围需重新完成隐私与安全评审。

## ADR-013：列表、导出与混合归档视图使用同一业务边界

- 日期：2026-08-04
- 状态：已采纳
- 决策：候选人列表和导出复用服务端查询实现，查询参数在进入 SQLite 前严格校验，标签精确匹配且排序追加稳定 ID；职位详情导出只使用当前职位上下文。前端在包含活跃和归档记录的视图中按每条记录的 `archived_at` 决定操作权限。
- 原因：页面可见结果、导出集合或操作权限若依赖不同筛选实现，会产生漏导、误导和对归档记录的意外写入。
- 后果：非法或重复查询参数返回 `400 invalid_query`；归档候选人可在“已归档”或“全部档案”中选择用于恢复或永久删除，但不能编辑、移动阶段、添加备注或调整职位/人才库关系；活动与归档候选人不得混合执行永久删除。职位详情导出包含详情中展示的归档关系且不继承候选人库筛选。

## ADR-014：人才库成为默认产品语义，招聘阶段仅兼容保留

- 日期：2026-08-04
- 状态：部分保留；默认产品语义和 UI/导入隐藏规则有效，Agent 阶段字段边界与禁止自由 SQL 结论由 ADR-030 取代
- 决策：产品默认工作区围绕候选人资料、人才检索、人才库分组和职位关联组织。现有 `candidates.stage` 与 `stages` 继续保留以兼容历史数据和旧接口，但默认候选人界面、导入映射和 Agent 投影不再以招聘阶段为入口或核心字段。Agent 本身继续保留；被弱化的是阶段数据，而不是 Agent 功能。只有用户明确查询历史招聘阶段且受控只读工具显式允许时，才可以返回对应阶段信息。
- 原因：当前目标是长期人才库，不是围绕筛选、面试、Offer 和入职推进的完整 ATS。直接删除阶段会破坏现有数据和兼容性，而继续默认展示又会让产品语义偏回招聘流程。
- 后果：默认工作台不再依赖阶段漏斗或阶段看板；阶段数据不得在新文件导入时自动映射。V6 Agent 可按明确问题读取阶段字段，并可执行一条经 schema 目录和 SQLite authorizer 验证的只读 SQL；它仍无业务写连接和任何写工具。

## ADR-015：北森正式迁移使用包含稳定 ID 的单一 XLSX

- 日期：2026-08-04
- 状态：历史决策；单文件和三 ID 必需约束已由 ADR-022 取代
- 决策：正式迁移要求从来源系统重新导出一份 `.xlsx`，同一行至少能够追溯候选人 ID、申请 ID 和职位编号。三份旧版 `.xls` 只用于字段审计和映射设计，不直接导入、不转换、不覆盖，也不依赖它们当前的行序完成正式合并。
- 原因：三份审计文件按字段拆分，只有部分文件含稳定候选人 ID；仅按行号、姓名或近似文本拼接无法形成可重复、可审计的身份关系。
- 后果：继续遵守 ADR-004 的服务端解析边界且不增加 `.xls` 解析依赖；继续遵守 ADR-005，候选人只按标准化联系方式或 `source_system + source_record_id` 去重。新 `.xlsx` 缺少稳定 ID 时必须在预览阶段阻断对应关系导入并要求人工修正。

## ADR-016：人才库分类使用独立多对多实体

- 日期：2026-08-04
- 状态：已采纳
- 决策：来源系统中的人才库分类建模为独立 `talent_pools` 及候选人与人才库的关系，而不是转换为普通标签。一个候选人可以进入多个人才库，一个人才库可以包含多个候选人；重复关系必须由唯一约束阻止。
- 原因：人才库具有稳定名称、来源标识、储备时间和分组语义，需要支持可靠筛选、分组、解除和血缘追踪；自由标签不能完整表达这些约束。
- 后果：标签继续用于轻量自由标记，人才库用于正式分组。关联或解除人才库不得删除候选人，也不得改变候选人与招聘职位的关系。

## ADR-017：履历使用来源原文与结构化摘要双轨保存

- 日期：2026-08-04
- 状态：已采纳
- 决策：教育、工作、项目、实习、技能及其他多行履历首先按来源原文完整保存；同时从来源中已有的明确列生成最高学历、学校、专业、当前公司、当前任职等结构化摘要，用于列表、搜索和筛选。自动解析结果不得覆盖来源原文，也不得冒充已人工核验的逐段经历。
- 原因：原文能保证迁移可追溯，结构化摘要能支持人才库高频检索；在没有稳定段落结构时强行拆分会制造错误时间线和字段错位。
- 后果：详情页应同时允许查看来源快照和结构化摘要。本期不要求把所有自然语言履历拆成可独立编辑的教育或工作经历记录；后续若增加解析，必须记录解析版本并保留原文回退依据。

## ADR-018：完整面试和测评历史作为来源档案保留

- 日期：2026-08-04
- 状态：已采纳
- 决策：合法导出的人工筛选、面试、考试、测评和 AI 评估历史完整保留为来源档案，并按候选人及可用的外部申请 ID、职位编号建立血缘。它们不驱动当前平台的排期、审批、状态流转或自动决策。背调等高敏历史是否保留由 ADR-019 约束；Offer/录用只保留在候选人来源原始载荷，审批、入职和其他纯流程字段不因本决策进入人才库业务模型。`自我评价` 属于候选人自述，写入 `self_summary` 而不是历史评估。
- 原因：用户选择保留完整面试和测评历史以便人才判断和来源核对，但当前产品仍不需要重新实现北森的完整招聘流程。
- 后果：评估历史可以在候选人详情的受控区域查看，但不能被描述为可运行的面试、测评、Offer 或入职业务模块。无用流程字段只在原始只读文件和字段登记中保持可追溯，默认不复制进人才库业务库。该决策不取代 ADR-001 和 ADR-010：系统仍没有完整 ATS 流程或每职位独立阶段。

## ADR-019：敏感字段全部本地保留并与默认业务表面隔离

- 日期：2026-08-04
- 状态：部分保留；本地保存、默认 UI/搜索/导出隔离继续有效，Agent 最小投影结论由 ADR-030 取代
- 决策：按业务确认，源文件中的身份、证件、婚育、民族、政治面貌、宗教、健康、生物特征、家庭联系人、薪酬、背调、心理测评、监控及其他敏感字段均保留。这些字段必须进入受保护详情或来源档案，并继续从默认 UI、通用搜索和默认导出中隔离；V6 Agent 可按用户明确问题经全字段只读层读取，不把无关字段主动发送到模型。
- 原因：业务需要完整留存来源事实，同时必须限制高敏数据在高频界面、导出副本和模型网关中的非必要传播。
- 后果：该选择不构成个人信息处理的合法依据，公司仍须确定处理目的、授权、留存期限和删除流程。当前版本没有登录、RBAC、字段级权限或数据库静态加密，只能继续在受控本机单用户边界内使用；多人版完成安全能力前不得开放这些数据。

## ADR-020：职位按来源编号匹配或创建，招聘负责人不写入候选人负责人

- 日期：2026-08-04
- 状态：已采纳
- 决策：来源招聘职位通过 `source_system + source_position_id` 稳定匹配现有职位；确认不存在时才在导入预览中提出创建。不得用候选人的 `current_title` 或仅凭职位名称静默创建关系。来源“招聘负责人”只进入职位负责人，候选人负责人默认保持未分配。
- 原因：职位编号比名称稳定；同名职位可能属于不同部门或批次。职位负责人和候选人维护负责人是不同责任，自动复制会产生错误归属。
- 后果：候选人与职位继续使用 ADR-009 的多对多关系。外部申请 ID 和职位编号只作为关系血缘，不因此引入完整 application 实体；职位匹配、拟创建和关系写入必须先在 dry-run 中显示。

## ADR-021：有效投递渠道作为主来源并保留来源历史

- 日期：2026-08-04
- 状态：已采纳
- 决策：候选人默认展示和筛选使用来源系统导出的“有效投递渠道”；最初、最后和有效获取方式、媒介、渠道、渠道类型及时间分别保存为来源历史。若继续保留 `candidates.source`，它只是当前展示摘要，不是完整来源事实。
- 原因：有效渠道最接近当前业务归因，而最初和最后来源对追溯、渠道分析及争议核对仍有价值，不能互相覆盖。
- 后果：来源记录必须带 `source_system`、外部记录标识和导入批次血缘。重新导入按同一稳定来源键更新，不得通过覆盖摘要丢失最初或最后来源。

## ADR-022：北森按应聘者 ID 分批增量导入并支持 BIFF8 XLS

- 日期：2026-08-04
- 状态：已采纳；取代 ADR-004 的格式限制和 ADR-015 的单文件/三 ID 必需约束
- 决策：北森专用轮廓只由大小写准确的 `应聘者ID` 表头触发，该字段是候选人增量导入唯一必需稳定键。相同 ID 可在同文件或跨批次用非空字段补充、更新或纠正资料，包括姓名；空值不清除旧值，标签取并集，来源原始载荷按非空字段递归合并。姓名始终不参与自动合并；新 ID 必须有姓名，已有 ID 可省略姓名；手机或邮箱属于其他候选人时阻断。`申请ID` 和职位信息可选；完全没有招聘职位字段时只跳过对应关系，但显式职位字段无效、歧义或命中归档职位时阻断受影响源行，不写入候选人、职位、关系或原始载荷。服务端除 `.xlsx`、`.xlsm` 和 UTF-8 `.csv` 外，使用精确锁定的 `xls-reader@0.7.0` 读取未加密 Excel 97-2003 BIFF8 `.xls`，并在解析前校验 OLE2 文件签名。
- 原因：人才资料会按字段分批导出，强制单文件同时携带申请和职位标识会阻断合法的候选人资料补充；`应聘者ID` 已足以提供可重复候选人身份。BIFF8 支持可直接处理来源合法导出的旧格式，减少人为转换，同时仍需防止伪装文件和不受支持格式。
- 后果：伪装扩展名、加密或非 BIFF8 `.xls` 返回 `422`，不会尝试猜测或转换。申请/职位关系只在信息完整时写入，不创建虚构占位记录。已审计三份真实 `.xls` 中前两份没有精确 `应聘者ID`，仍不能按姓名或行号与第三份自动合并，必须重新导出带稳定 ID 的版本。ADR-005 的身份冲突规则继续有效；`start.ps1` 将 `xls-reader` 纳入关键依赖存在性检查。

## ADR-023：北森导入按有效行隔离、申请归属和重放安全处理

- 日期：2026-08-04
- 状态：已采纳；补充 ADR-022，并取代“北森重复提交严格状态幂等”的宽泛表述
- 决策：预览先排除失败行，再按 `应聘者ID` 和职位编号聚合有效数据；失败行不得贡献候选人字段、职位字段、关系或任何 `raw_payload`。同文件同候选人的非空标量以后出现值为准，空值不覆盖，标签按首次出现取并集且最多 50 个。提交的 `imported_rows + updated_rows + skipped_rows + failed_rows` 必须等于输入总行数，`candidate_count` 只计算成功处理的唯一候选人。`申请ID` 只有在职位关系可建立或行内存在真实评估载荷时才参与文件内重复、数据库归属和提交竞态校验；一旦属于另一候选人便阻断，绝不改绑。Offer/录用只保存在候选人来源原始载荷，`自我评价` 写入 `self_summary`，二者都不创建历史评估。
- 原因：分批文件可能包含同 ID 多行、无效行、可选申请信息和重复职位编号。如果在校验前聚合，会让失败行污染有效记录；如果所有出现的申请 ID 都强制唯一，会把未形成任何关系或评估的可选文本误判为冲突。计数必须分别表达源行处理结果和唯一业务实体，才能复核导入是否完整。
- 后果：相同文件可以安全重放而不重复创建候选人、职位或关系，但当前仍会刷新已有候选人的 `updated_at`、`import_batch_id`，追加 `candidate_import_updated` 活动并影响最近更新排序，因此不是严格状态幂等。后续可用内容指纹或逐字段差异检测跳过无变化写入；在此之前，运维和验收不得把“无重复创建”表述为“数据库状态完全不变”。

## ADR-024：证件照定向用于头像，原始 URL 继续按高敏字段隔离

- 日期：2026-08-04
- 状态：部分保留；头像与默认业务投影规则继续有效，Agent 排除照片 URL 的结论由 ADR-030 取代
- 决策：按用户本次明确要求，北森“证件照”映射到 `candidates.photo_url` 并用于候选人头像。schema v3 以加法迁移增加该列；schema v4 `candidate_photo_backfill` 扫描既有 `candidate_source_records.raw_payload['证件照']`，只在候选人 `photo_url` 为空且地址协议为 HTTP/HTTPS、路径以 `.jpg`、`.jpeg`、`.png` 或 `.webp` 结尾时回填，允许签名查询参数；不覆盖已有照片，也不要求重新导入。普通列表、普通详情和导入预览只返回 `has_photo`；原始 `photo_url` 只随 `include_sensitive=true` 返回。头像由 `GET /api/candidates/:id/avatar` 以 private cache、no-referrer 的 `302` 跳转加载，默认 CSV/XLSX 导出排除照片 URL；V6 Agent 可在问题明确需要时经全字段只读层读取。前端所有头像位统一使用 `CandidateAvatar`，加载失败回退姓名首字母。v4 回填活动只记录发生过回填，不记录照片 URL。
- 原因：头像能提高人才库的辨识效率，且现有 57 位候选人的合法来源记录已经包含证件照字段；加法回填可避免重新导入。与此同时，来源 URL 带签名参数并可能直接授予照片访问能力，不能进入高频 JSON、导出、活动日志或模型上下文。
- 后果：当前照片仍是带签名参数的远程明文 HTTP 资源，不是离线附件；个人回环模式只有显示头像时按需联网。`no-referrer` 和最小化投影降低泄露面，但不提供来源传输加密、长期可用性或真正的权限控制。部门部署前，认证/RBAC和把照片迁入受控本地或公司内部附件存储是硬门槛。

## ADR-025：候选人采用“可恢复归档 + 受控单条永久删除”双轨生命周期

- 日期：2026-08-04
- 状态：历史决策；单条确认词协议由 ADR-029 的 token 化单条/批量协议取代，双轨生命周期原则继续有效
- 决策：日常移除继续使用 `archived_at`，单条归档可撤销，批量归档最多 100 人并在单事务中执行。永久删除只对已归档候选人开放，不提供批量入口；前后端都必须校验精确确认词“永久删除”、归档状态和 `expected_updated_at`。删除候选人主行后，通过外键级联清除候选人从属数据，并在同一事务写入只含候选人 ID SHA-256 和删除时间的 `deletion_audits`。
- 原因：归档适合日常误操作恢复，但不能满足用户明确要求的应用内不可恢复删除。确认词、状态门槛、并发版本和最小审计共同降低误删与竞态风险，且不保留可恢复候选人的审计副本。
- 后果：共享职位、人才库和导入批次不随候选人删除。该操作只影响当前 SQLite，不调用北森等来源系统，也不会自动清理历史备份；当前没有认证和 RBAC，因此审计不能证明具体自然人操作者，也不能作为完整个人信息删除证明。

## ADR-026：显式招聘职位字段可在通用与北森导入中匹配或创建职位

- 日期：2026-08-04
- 状态：已采纳；扩展 ADR-020 的匹配策略
- 决策：只有显式映射为招聘职位的字段进入职位处理，候选人 `current_title` 永不参与。匹配顺序为 `source_system + source_record_id/external_code`、标准化“职位名称 + 部门 + 地点”、仅名称时唯一未归档同名。无匹配且名称有效时创建 `draft`；多个候选或命中归档职位时标记歧义/归档冲突并阻断静默处理。预览必须先展示匹配、新建、歧义、无效、归档冲突和拟新增关系，提交时再次解析并在候选人写入、职位创建、关系建立的同一事务中执行。
- 原因：职位是人才分组的正式实体，导入时人工逐一预建职位成本高；稳定来源键和确定性组合可以安全自动化，而模糊匹配或把当前任职当招聘职位会制造错误关系。
- 后果：通用导入不再被描述为“只写候选人”。唯一约束和 `INSERT OR IGNORE` 防止重放产生重复职位关系；职位歧义必须人工修正文件或映射，系统不静默恢复归档职位。

## ADR-027：前端采用飞书公开产品的中性高密度企业工作台方向

## ADR-029：候选人和职位永久删除使用一次性预览令牌

- 日期：2026-08-05
- 状态：已采纳；取代 ADR-025 的确认词和仅单条限制
- 决策：候选人和职位都维持“可恢复归档 + 归档后永久删除”双轨生命周期。单条和批量删除使用同一两步协议：预览 1-100 个已归档目标，把操作类型、规范化 ID 集合和 `updated_at` 快照绑定到默认 2 分钟有效的一次性 token；用户只看一次清晰弹窗，不输入确认词。提交在一个 `BEGIN IMMEDIATE` 事务内重验全部目标的存在性、归档状态和版本，任一异常整批 `409` 回滚，token 过期、跨操作或重放拒绝。单条兼容路由还要求 URL ID 与 token 快照中的唯一目标一致，拒绝批量 token 或其他目标 token。
- 原因：确认词只能防止部分误触，不能解决客户端绕过、批量竞态或预览后状态变化。服务端绑定版本的一次性令牌同时覆盖单条与批量，并让前端确认保持简洁。
- 后果：候选人删除级联清除全部候选人资料、附件元数据和索引，并在事务内把物理附件放入可重试清理队列；共享职位、人才库和导入批次保留。职位删除只清除职位、关系和职位从属记录，为受影响候选人写不含职位正文的活动，绝不删除候选人资料。两类审计只保存 ID 哈希、时间和必要计数；均不影响来源系统、导出副本或历史备份。

## ADR-030：Agent 改为 SQLite 全字段按需只读

- 日期：2026-08-05
- 状态：已采纳；取代 ADR-007/008/012 的三工具和最小字段投影
- 决策：按用户明确授权，Agent 可以查询当前 schema 目录内任何表、字段、归档记录和最小审计，包括未打码联系方式、薪资、照片地址、备注、活动、完整履历、评估、授权、`raw_payload` 和附件正文。访问必须使用与业务写连接隔离的文件型 SQLite 只读 worker，启用 `readOnly`、`query_only=ON`、`trusted_schema=OFF`、defensive mode，关闭扩展加载，并由 SQLite authorizer 校验表、列、函数和操作码。自由 SQL 只允许单条 `SELECT` 或只读 CTE。
- 原因：用户需要跨全部历史和敏感字段完成招聘检索与审计，而静态三工具无法表达。SQLite authorizer、实时 schema 目录、独立只读连接和资源上限能在扩大读取范围时保持不可写边界。
- 后果：结构化工具支持目录驱动字段/关联、`eq|ne|contains|in|gte|lte|is_null`、排序、分页、聚合和分组；常规结果最多 100 行/1 MB/默认 3 秒，大明细通过同一防护的本地 CSV 导出。审计只记录工具、表/列/函数范围、耗时、行数和错误，不记录结果。Agent 继续没有新增、修改、归档、恢复、关联、附件确认、删除、终端、任意文件或 HTTP 能力。

## ADR-031：履历检索以 SQLite FTS5 和 Top-K 为默认

- 日期：2026-08-05
- 状态：已采纳
- 决策：候选人主档摘要、未归档履历区块和已解析附件文本统一进入 `candidate_resume_documents`，由触发器同步到 FTS5。自然语言检索组合结构化字段、同义词/关键词和 FTS5，从全库召回后按候选人去重、排序并返回命中字段、片段和依据；默认 20、Agent 单次最多 50 位候选人进入模型上下文。统计由 SQLite 聚合，完整明细生成本地导出。
- 原因：数据库可以安全扫描全部履历，模型无需也不应接收全库正文。候选人级聚合避免同一人的多个文档占用多个结果槽位。
- 后果：FTS5 不可用时明确报错，禁止静默退化为全库正文外发。现有网关仅确认 Chat Completions，未确认 Embedding；V6 仅预留本地向量元数据表，不连接其他 Embedding 或向量服务，不安装大型本地模型。

## ADR-032：简历附件本地隔离解析且只按电话/邮箱定位

- 日期：2026-08-05
- 状态：已采纳
- 决策：支持文本型 PDF、DOCX、XLSX、XLSM、BIFF8 XLS 和 UTF-8 CSV，单文件 15 MB。上传同时校验扩展名、MIME 和签名/容器，清洗原名并用随机内部路径放入非公开隔离目录；解析在有超时和资源上限的 worker 内完成，不执行宏、脚本、外部链接或子进程。自动定位只使用现有标准化手机号或小写邮箱精确匹配，姓名、公司、学校、职位和文件名只供人工核对。
- 原因：简历是复杂、不可信且可能含敏感数据的文件；仅按扩展名或姓名合并都容易造成安全问题或错档。
- 后果：`.doc`、加密文件、扫描/无文本 PDF、OCR、损坏文件和非 BIFF8 XLS 明确失败，不调用 LibreOffice、OCR、云转换或原生可执行程序。身份字段命中不同候选人、任一字段多候选命中或命中归档档案时阻断；无命中允许手工选择，但不自动创建候选人。

## ADR-033：附件更新必须由用户经业务 API 确认

- 日期：2026-08-05
- 状态：已采纳
- 决策：解析器/Agent 只产生 JSON 结构的字段和履历建议；预览阶段不修改候选人。生产 suggestion provider 复用现有 Agent 网关，最多提交 120,000 字符和 100 条记录，要求 strict JSON Schema 且不提供 tools；网关失败时保留本地规则建议。用户逐字段/区块选择后，普通业务 API 用短时一次性 token 重新校验候选人版本、归档状态、身份冲突、字段格式与合并模式，再在事务中保存附件、字段来源、履历索引和活动。Agent 不得调用确认接口。
- 原因：附件正文、备注和来源载荷都是不可信输入，模型建议不能直接成为写操作。用户可见差异、版本校验和事务是防止错覆盖与重复写入的必要边界。
- 后果：空解析值永不清除旧值，默认只选当前为空且非低置信字段，覆盖非空值需显式选择，标签去重并集，履历按内容签名去重合并，整体替换需额外确认。同一候选人 + SHA-256 + 附件类型幂等；取消、失败、过期和删除后的文件清理失败进入可重试队列。预览进入 `confirmed`、`cancelled` 或 `expired` 后清空临时正文与建议 JSON，只保留正式附件正文和最小预览状态。

## ADR-034：V6 仍是个人回环版

- 日期：2026-08-05
- 状态：已采纳
- 决策：全字段 Agent 和本地附件不改变部署边界。应用仍无认证、RBAC、字段权限、租户隔离或可靠操作者审计，只能监听回环地址并由单个受控 Windows 用户使用。
- 原因：扩大数据读取和新增敏感附件会提高多人暴露风险，不能把功能增加误解为部门部署准备完成。
- 后果：部门版必须另行实现身份/权限、附件鉴权与恶意文件防护、集中审计、TLS、共享存储/数据库、静态加密和备份恢复；不得仅修改 `HOST` 或增加反向代理。

## ADR-035：跨域写请求前置拒绝并按实际解压结果限制附件

- 日期：2026-08-05
- 状态：已采纳
- 决策：Origin 写保护必须位于 JSON 和 multipart 请求体解析之前，不允许的跨域写和预检直接返回 `403 origin_not_allowed`；正常应用响应设置 CSP、禁止 framing、`nosniff`、no-referrer 和受限 Permissions Policy。Office ZIP 不能只信任目录声明，必须实际读取或 inflate 后核对长度、累计体积和压缩比；附件解析同时使用 15 秒超时、空 `execArgv` 和 V8 Worker `resourceLimits`。
- 原因：本地敏感写接口和附件解析都需要在昂贵或危险的内容处理前收紧输入边界；压缩包声明值可能伪造，必须按实际输出执行上限。
- 后果：不允许的 Origin 无法触发 JSON 或附件写入路径；ZIP 长度不一致、加密、ZIP64、未知压缩方法或实际资源超限会明确失败。浏览器响应头和 Origin 校验仍不是认证/RBAC，V8 Worker 限制也不是整个 Node 进程的 RSS 硬上限。

## ADR-037：入职信息使用独立 V11 字段，清理工作簿按状态过滤

- 日期：2026-08-21
- 状态：已采纳
- 决策：候选人主表新增可空 `hire_status` 与 `hire_date`，通过幂等 V11 加法迁移落地，并为两个字段建立查询索引。`hire_status` 是来源系统入职状态的非空原文（去首尾空白、最多 200 个字符、不固定枚举）；`hire_date` 是校验真实日期后统一为 `YYYY-MM-DD` 的日期文本，允许未来日期和状态有值但日期为空。两个字段贯通候选人 CRUD、档案编辑/详情、通用与北森导入以及 CSV/XLSX 导出。
- 原因：实际入职记录与求职偏好 `candidate_preferences.employment_status`、兼容阶段 `candidates.stage` 的语义不同。复用旧字段会混淆查询、导入和历史兼容行为；独立可空字段可以在不改写旧数据的情况下逐步补充来源事实。
- 数据准备边界：本轮提供的 7 个 BIFF8 `.xls` 逐文件生成同名 `_已整理.xlsx`，只保留 `trim(入职状态) !== '' && trim(入职状态) !== '空'` 的行；空日期不影响保留。原始文件只读、不覆盖、不按姓名/行号合并，也不把该过滤规则隐式施加到所有历史导入。
- 后果：V11 不提供入职流程、审批、Offer 或按状态驱动的 ATS 状态机；正式数据库升级仍须停止服务、备份 `.db/-wal/-shm` 文件集并先在可丢弃副本验证。交付工作簿的行数、哈希、公式扫描和复现命令以 `docs/TESTING.md`、`docs/OPERATIONS.md` 及 `outputs/2026-08-21-hire-status-cleaned/cleanup-summary.json` 为准。

## ADR-038：入职事实与招聘关联职位分离（V12）

- 日期：2026-08-21
- 状态：已采纳
- 决策：在 V11 的 `hire_status`/`hire_date` 之上，以幂等 V12 加法迁移增加可空 `candidates.hire_position` 和 `candidates_hire_position_idx`。`hire_position` 只保存“入职职位”事实文本；有效 `hire_date` 没有明确状态时写入精确值 `不确定`。三项入职字段都为空时，详情只隐藏“入职信息”区块，不删除或归档候选人。
- 关系规则：北森 `最后职位类投递的职位id` 才是 `candidate_positions` 的招聘关联键；`入职职位`、`入职雇佣关系` 不能代替它。工作簿存在该专用表头时，行空不创建关系且不得回退普通 `职位编号`；仅整表缺该表头时普通编号才可兼容回退。若专用值是职位名称，按 `应聘者ID + 最后职位类投递时间` 回查历史申请职位，唯一命中则复用正式职位，未命中才创建稳定来源键的草稿职位。人才库和来源历史分别写入 `candidate_talent_pools`、`candidate_source_records`，未建模字段保留在 `raw_payload` 用于追溯。
- 验收边界：真实北森文件先从有入职日期且通过校验的记录中取 100 个唯一候选人；验收分别统计候选人字段、非空关联职位关系、人才库关系、来源历史和 SQLite 完整性，不能把 100 行误报为 100 条职位关系。隔离验收证据见 `docs/evidence/v12-hire-information-import-20260821.json` 且为 `formal_database_commit=false`。2026-08-24 已完成正式入口 HTTP 预览与用户确认提交：100/100/0，0 导入/100 更新/0 失败/跳过，职位 create/match/link/conflict 为 0/32/36/0；脱敏证据为 `docs/evidence/v12-hire-information-formal-import-20260824.json`。用户豁免 22GB 全库摘要、逐行字段、完整性/外键后检及恢复演练，因此未记录这些结论。
- 后果：V12 仍不提供 Offer、审批或入职流程状态机；迁移只加列和索引，不重建或清空旧数据，也不从 `stage` 或求职偏好回填入职字段。

## ADR-039：工作年限保留原文并使用可空数值投影（V13）

- 日期：2026-08-25
- 状态：已采纳；V13 生产部署与样本验收待 Task 7
- 决策：`years_experience` 改为只承载可安全解释的 `number | null` 数值投影，新增 `years_experience_raw TEXT NOT NULL DEFAULT ''` 保存来源原文，响应计算 `years_experience_display`。未知文本、范围、修饰词、负数或溢出值保留原文而不制造数字；只有明确的 `0` 产生数值 `0`。工作年限格式不单独拒绝导入行，手机/邮箱身份冲突保持独立阻断。

- 后果：通用/北森导入、附件确认、API、UI 和 CSV/XLSX 导出都以原文优先并保持数值/原文成对更新；真实空值展示为空白，任何用户可见路径不显示 `null`。`min_years`/`max_years` 的兼容查询输入限制见 API 文档，不是存储或导入上限。迁移登记固定为 `(13, 'candidate_years_experience_raw')`，回滚应用代码时保留列；删除列需单独备份、批准和离线维护。

## ADR-040：头像图片与姓名首字互斥渲染

- 日期：2026-09-17
- 状态：已采纳
- 决策：候选头像只有一个视觉内容分支。`has_photo` 为真且加载未失败时只渲染受保护图片；加载中不渲染姓名首字；无图片或 `onError` 时卸载图片并只渲染首字。两个头像组件共享这一行为约定，页面不得通过叠加、透明首字或页面特殊 CSS 绕开。
- 原因：旧实现无条件输出首字并用绝对定位覆盖图片，导致加载期间 DOM 同时存在两个视觉节点，失败状态和尺寸也难验证。
- 后果：所有列表、详情、选择器和检索结果共享一致回退；图片加载期间只显示容器背景，图片失败后首字稳定出现。头像尺寸、圆角、裁切和调用接口保持不变。

## ADR-041：隐藏节点按证据分类后删除
