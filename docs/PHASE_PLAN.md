# 三阶段方案：简历展示 → 头像同步 → 履历补全

本文是接下来三个阶段的实施方案。每一项的可行性都用实测数据做了验证，
未验证的部分明确标注。

---

## 阶段 1：原始简历内嵌展示

### 目标

每个人的原始简历（`origin`）直接在系统里看，不再只是"下载一个文件"。
档案左边新增简历区块，左右分栏，参考北森/字节的简历查看方式。

### 现状：基础版已完成

- 抽屉详情改为左右两栏：左侧简历、右侧原有五个页签
- 优先展示原始简历，可切换到标准简历
- 服务端新增 `GET /api/attachments/:id/content`，`inline` 返回
- 按真实类型渲染：PDF → iframe、图片 → img、HTML → 沙箱 iframe、
  文本/JSON → `pre`、其余 → 下载入口
- 抽屉宽度在展示简历时放宽到 `min(1360px, 96vw)`，≤1279px 自动改为上下堆叠

### 数据依据（实测）

| 真实类型 | 数量 | 占比 | 渲染方式 |
| --- | --- | --- | --- |
| HTML | 66,061 | 60.6% | 沙箱 iframe |
| PDF | 30,277 | 27.8% | 原生查看器 |
| ZIP | 4,016 | 3.7% | 仅下载 |
| DOC | 2,944 | 2.7% | 仅下载 |
| TXT | 1,995 | 1.8% | `pre` |
| JPEG / PNG | 2,172 | 2.0% | img |
| JSON | 1,494 | 1.4% | `pre` |
| 其他 | 15 | — | 仅下载 |

### 安全设计（已实现）

简历 HTML 是候选人上传的不可信内容，必须按不可信处理：

- 响应加 `X-Frame-Options: SAMEORIGIN`、`frame-ancestors 'self'`，
  允许同源内嵌但仍禁止被第三方站点套壳
- 非 PDF 响应加 `default-src 'none'; sandbox`，**禁脚本、禁外部资源**
- `X-Content-Type-Options: nosniff`
- 前端 iframe 额外带 `sandbox=""` 与 `referrerPolicy="no-referrer"`

副作用：简历 HTML 引用的外部/相对图片会显示为占位符。这是刻意的——
那些资源要么不在资产里，要么来自候选人控制的外部域名。

### 待完善

- 简历 HTML 内联样式较多，长简历滚动体验待优化
- 移动端目前是上下堆叠，需要确认是否符合使用习惯
- 未做：简历全文检索联动（当前简历文本未进索引，见阶段 3）

## 阶段 2：把原始简历里的头像同步到头像框

### 现状

- `candidates.photo_url` **全量为空**，所以所有人头像都是姓名首字
- 29.6% 的档案有 `IDPhoto` 字段，但 100% 是 `dfs://Resume/...` 内部路径
- 资产**没有** `additional/` 目录，照片文件本体不在资产里
- 设计文档 §2 原本规定证件照放 `additional/`，实际未实现

### 已验证的可行路径

证件照被渲染进了 `standard.pdf`。应用自带提取能力，直接复用即可：

- `server/attachment-avatar.js` 的 `extractPdfAvatarCandidates()` + `selectPdfAvatarCandidate()`
- 合格条件：≥96×96、宽高比 0.55–1.35、只扫 PDF 第一页

**实测（8 位档案里标了证件照的候选人）**：

| 候选人 | 提取结果 |
| --- | --- |
| 郜钰 | 314×318 ✅ |
| 宋宇航 | 200×200 ✅ |
| 胡成龙 | 270×268 ✅ |
| 胡泠仪 | 281×281 ✅ |
| 张小文 | 200×204 ✅ |
| 沈祺皓 | 1280×1280 ✅（需转码） |
| 薛岑 | 80×80 ❌ 小于 96 下限 |
| 贺帅 | 未提取到 |

**6 / 8 成功**。引用对象带 `content_type`、`extension`、`byte_length`、
`sha256`、`requires_transcoding`，落盘所需信息齐全。

### 实施方案

1. 新建脚本 `scripts/sync-candidate-avatars.mjs`，遍历有 `resume` 附件的候选人
2. 读 `standard.pdf`（原件若为 PDF 可作为备选），调用
   `extractPdfAvatarCandidates` + `selectPdfAvatarCandidate`
3. 命中后把图片写入 `data/private/attachments/files/`，
   插入 `candidate_attachments`（`attachment_type='avatar'`、`parse_status='parsed'`）
4. 设 `candidates.photo_url = 'attachment-avatar:<avatarAttachmentId>'`
   —— 这是应用既有的本地头像约定，`/api/candidates/:id/avatar` 据此解析文件
5. 幂等：同一候选人已有 avatar 附件则跳过

### 覆盖预估

约 29.6%（有证件照标记）× 75%（提取成功）≈ **全量 22%**。
"未标记但有照片的档案理论上也能提"这一条**已被实测否定**：无 `IDPhoto` 标记的
档案里，`standard.pdf` 内嵌的是同一张 160×160 默认剪影占位图（全库同 sha），
必须用标记做门禁，否则会把占位图当成头像。

### 风险与验收

- **误提**：可能把公司 logo、水印、二维码当头像。缓解：人工抽检；
  需要转码的先转成 JPEG/PNG 再入库（`resolveCandidateAvatar` 只接受
  `image/jpeg` 与 `image/png`）
- **验收**：随机抽 50 人人工核对头像是否正确，并统计提取成功率

### 实施结果（2026-09-24 完成）

- 先导实测：随机 200 位有标记候选人 → 182 张可提取（91%），0 报错。
- 全量：**36,223** 位有 `IDPhoto` 标记的候选人里 **32,258 人**写入了本地头像，
  占有标记者 **89.1%**、占全部 118,918 人的 **27.1%**；落盘 6.4 GiB，
  均 208 KB，最大 4.72 MB。另 3,965 人的证件照小于 96×96 下限或 PDF 内
  没有可用图像，保持姓名首字头像。
- 写入内容：`candidate_attachments`（`attachment_type='avatar'`、
  `parse_status='parsed'`、`source='avatar_sync'`）+ `candidates.photo_url=
  'attachment-avatar:<附件ID>'`。已有 `photo_url` 的候选人一律跳过，不覆盖。
- 误提清洗：重复字节扫描发现 261 个跨候选人重复图组。其中 **136 组（680 人）
  跨不同姓名**——卡通默认头像、产品界面截图、二维码、广告图、宠物照——已删除
  附件行/文件并回滚 `photo_url`，留档 `data/avatar-dedupe-audit.json`；
  另有 125 组（311 人）是同名重复档案的真实照片，保留。
  追加校验：**24 张**颜色多样性 < 2% 的扁平图形（占位剪影、二维码、UI 截图）
  也已清除；同类残留检测未见其他命中。
- 端到端校验：32,258 行头像全部通过「文件存在 / 大小一致 / sha256 一致 /
  可解码」检查；随机 25 人走 `GET /api/candidates/:id/avatar` 全部 200，
  返回字节与库内 sha256 一致。
- **验收口径（2026-09-24 用户确认）**：生活照、毕业照、艺术照都可以，只要
  能看清人脸即可；不需要再收紧“必须是标准证件照”。因此上述非证件照头像
  按通过处理，不做额外过滤。
- 脚本：`scripts/sync-candidate-avatars.mjs`（同步，支持 `--limit`/`--random`/
  `--apply`）、`scripts/dedupe-candidate-avatars.mjs`（清误提，默认 dry-run）。
- 复核材料（含真实头像，仅存本地、已 gitignore）：`data/avatar-audit/`——
  `index.html` 随机 96 张落库头像接触表、`rejected-duplicate-groups.png` 与
  `rejected-low-diversity.png` 被清除的误提拼图、`ui-avatar-verification.png`
  界面取证、`README.json` 汇总。

## 阶段 3：用 Codex 解析原始简历，补齐缺失字段

### 背景（实测）

- 9 类区块全量全空：`skill`、`certificate`、`lang`、`internship`、
  `awards`、`train`、`writings`、`schoolCadre`、`schoolPractice`
- 19,610 人（16.5%）完全没有教育/工作/项目区块
- 极端对比：郜钰结构化 67 字符，原件 171,744 字节
- 结论：**结构化字段来自北森 `GetResume` 的解析结果，本身就不全；
  完整内容只在原始简历里**

### 实施进度（2026-09-24：100 份试点已落库）

**字段口径来自 C 盘旧项目实测**（`C:\Users\cboy\Documents\北森\data\recruitment.db`
的 315,361 条区块），规范字段与同义合并表如下：

| 区块 | 规范字段 |
| --- | --- |
| 实习经历 `internship` | 单位名称、职位名称、开始时间、结束时间、实习地点、实习内容、实习成果、单位介绍、证明人、证明人职务、证明人关系、证明人联系方式 |
| 校园经历 `campus` | 职务名称、实践名称、活动名称、开始时间、结束时间、职务描述、实践描述、活动描述、项目成果、团队规模 |
| 技能 `skill` | 技能名称、掌握程度、技能描述、使用时间总计 |
| 语言能力 `language` | 语言类型、掌握程度、听说、读写 |
| 证书 `certificate` | 证书名称、颁发机构、获得时间、成绩、证书编号、证书种类、有效日期至、证书描述 |
| 培训经历 `training` | 培训机构、课程名称、开始时间、结束时间、培训地点、培训课时数总计、培训描述、获得证书 |
| 奖励与荣誉 `award` | 奖项名称、级别、获得时间、颁发机构、奖项描述 |
| 论文与作品 `publication` | 名称、类型、发表时间、发表载体、作者排序、描述 |
| 管理经历 `management` | 组织、职务、开始时间、结束时间、团队规模、管理内容、管理成果 |
| 附加信息 `other` | 特殊技能、特长、社会活动、宗教信仰、推荐信、专利成果、专业组织、学术专著、兴趣爱好、荣誉、标题、获得荣誉、内容、其他 |

同义字段（如「公司/公司名称/机构」→「单位名称」、「岗位/职务/角色」→
「职位名称」）在落库前按区块作用域合并；**规范字段之外的字段不丢弃**，写入
`structured_data._extra` 并进入报告，确认后再并入规范字段表。

**流水线**（`scripts/parse-origin-resume-sections.mjs`）：

1. 选人：有原始简历正文（`text/html` / `application/pdf` / `text/plain`）、
   九个目标区块全空、且未跑过本解析器 —— 当前符合条件的候选人有 **98,333 位**。
   跨区块目标为四类已有内容的履历（教育/工作/项目）时各类型独立判断，只补空缺。
2. 取正文：HTML 自写去标签（保留换行结构），PDF 走应用既有
   `server/attachment-parser.js`，纯文本直读。
3. 解析：按批（默认 10 份/批）调 `AGENT_BASE_URL` 网关，强制 JSON 输出 +
   规范字段名 + 原文证据；网关调用带 3 次指数退避重试。
4. 本地校验：JSON 结构、区块类型白名单、字段名白名单（含同义合并）、
   证据必须能在原文定位（精确匹配 → 前缀 → 字符二元组重合率 ≥ 45%）。
5. 写库：每个条目一行 `candidate_profile_sections`，`section_type` 用规范类型，
   `title` 为「单位 · 职位」形式，`content` 首行为时间区间、随后是字段行；
   已有该类型区块的候选人整体跳过，不覆盖北森结果。`structured_data` 带
   `parser=origin-section-parse-v1`、`evidence`、`semantic_type`。

**100 份试点结果**：

| 指标 | 值 |
| --- | --- |
| 抽取正文 | 99/100（1 份原件正文过短） |
| 落库区块 | **611 行 / 69 位候选人**（人均 8.9 条） |
| 分布 | 技能 225、奖励 116、证书 74、校园 59、实习 40、管理 35、语言 30、培训 18、论文 14 |
| 质量校验 | 缺规范字段 0、缺证据 0、空标题 0、内容与结构化不一致 0 |
| 证据校验拒绝 | 约 8%（33/265 首轮、3/24 补跑），宁缺勿造 |
| 耗时 | 100 份约 3.5 分钟（10 份/批 ×5 并发），全量 98,333 份外推约 55–60 小时 |

界面排版沿用现有履历抽屉：新增区块按既有分组渲染（实习/管理归入「工作经历」、
校园/培训归入「教育经历」、论文/奖励归入「项目经历」、技能/语言/证书归入
「专业技能」），每条显示时间区间、标题与字段行，可展开结构化字段。

### 目标

用 Codex 解析 109,139 份原始简历，把内容补成 `candidate_profile_sections`，
让界面上履历完整。**只补空缺，不覆盖已有数据。**

### 解析通道（分三层，先确定性后智能）

| 层 | 覆盖 | 做法 |
| --- | --- | --- |
| 1. 应用已有解析器 | 29.6% | PDF / DOCX / XLSX / TXT，直接用 `attachment-parser.js` |
| 2. HTML 文本抽取 | +60.6% | 自写去标签抽取（HTML 不在应用解析器支持范围内） |
| 3. 剩余类型 | 8.5% | DOC 2,944 / 图片 2,172 / ZIP 4,016 单独评估，不假装成功 |

第 1+2 层合计约 **91.5%**（99,827 份），可覆盖绝大多数。

### 字段抽取（Codex 负责的部分）

1. 把第 1、2 层抽出的纯文本按候选人分批（建议 20–50 份/批）
2. 每批交给 Codex，按固定 Schema 输出结构化区块：
   `internship` / `skill` / `certificate` / `awards` / `lang` / `train` /
   `campus` / `publication` / `management`
3. **每条字段必须带原文片段作为证据**，无证据不写
4. 写库前本地校验：Schema 合法性、原文片段能在简历文本里定位、
   不与已有区块重复
5. 写库策略：目标类型已有区块则跳过；空缺才插入，
   `source_record_id` 标记来源（如 `origin-parse:<sha256前8位>`）

### 合规门槛（必须先确认，否则不能开工）

这一步会把 **109,139 份真实简历正文发给模型网关**。开工前需要确认：

- 当前 `AGENT_BASE_URL` 指向的网关是否获批用于候选人简历
- 数据出境/留存边界（网关侧是否留日志）
- 是否需要先脱敏（姓名/手机/邮箱替换），以及脱敏后对解析质量的影响

### 成本与工期（估算）

- 文本量：118,918 份 × 平均约 8 KB ≈ **950 MB**
- 分批：按每批 30 份 ≈ 3,960 批，需限流与断点续传
- 质检：按 1% 抽检 ≈ 1,190 份人工核对

### 风险

- **模型幻觉**：可能编造经历。缓解：强制原文证据 + 本地定位校验 + 抽检
- **错误归类**：把项目经历写进实习经历。缓解：Schema 里给出判定规则 + 抽检
- **覆盖冲突**：原件内容与结构化字段不一致时以谁为准。当前策略是
  **只补空缺**，不覆盖北森已解析出来的内容
- **成本不可控**：需先小批（100 份）跑通并实测单份成本，再外推全量

### 验收

1. 小批 100 份跑通，抽检 20 份，字段准确率与证据可定位率达到可接受水平
2. 全量跑完后统计：新增区块数、覆盖人数、无法解析的档案数
3. 界面上原本空履历的 16.5% 候选人能看到内容
