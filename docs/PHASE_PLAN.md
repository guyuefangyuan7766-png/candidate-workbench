# 三阶段方案：简历展示 → 头像同步 → 履历补全

本文是接下来三个阶段的实施方案。每一项的可行性都用实测数据做了验证，
未验证的部分明确标注。

---

## 阶段 1：原始简历内嵌展示

### 目标

每个人的原始简历（`origin`）直接在系统里看，不再只是"下载一个文件"。
档案左边新增简历区块，左右分栏，参考北森/字节的简历查看方式。

### 现状：基础版已完成

- 抽屉详情改为左右两栏：左侧简历、右侧原有五个页签
- 优先展示原始简历，可切换到标准简历
- 服务端新增 `GET /api/attachments/:id/content`，`inline` 返回
- 按真实类型渲染：PDF → iframe、图片 → img、HTML → 沙箱 iframe、
  文本/JSON → `pre`、其余 → 下载入口
- 抽屉宽度在展示简历时放宽到 `min(1360px, 96vw)`，≤1279px 自动改为上下堆叠

### 数据依据（实测）

| 真实类型 | 数量 | 占比 | 渲染方式 |
| --- | --- | --- | --- |
| HTML | 66,061 | 60.6% | 沙箱 iframe |
| PDF | 30,277 | 27.8% | 原生查看器 |
| ZIP | 4,016 | 3.7% | 仅下载 |
| DOC | 2,944 | 2.7% | 仅下载 |
| TXT | 1,995 | 1.8% | `pre` |
| JPEG / PNG | 2,172 | 2.0% | img |
| JSON | 1,494 | 1.4% | `pre` |
| 其他 | 15 | — | 仅下载 |

### 安全设计（已实现）

简历 HTML 是候选人上传的不可信内容，必须按不可信处理：

- 响应加 `X-Frame-Options: SAMEORIGIN`、`frame-ancestors 'self'`，
  允许同源内嵌但仍禁止被第三方站点套壳
- 非 PDF 响应加 `default-src 'none'; sandbox`，**禁脚本、禁外部资源**
- `X-Content-Type-Options: nosniff`
- 前端 iframe 额外带 `sandbox=""` 与 `referrerPolicy="no-referrer"`

副作用：简历 HTML 引用的外部/相对图片会显示为占位符。这是刻意的——
那些资源要么不在资产里，要么来自候选人控制的外部域名。

### 待完善

- 简历 HTML 内联样式较多，长简历滚动体验待优化
- 移动端目前是上下堆叠，需要确认是否符合使用习惯
- 未做：简历全文检索联动（当前简历文本未进索引，见阶段 3）

## 阶段 2：把原始简历里的头像同步到头像框

### 现状

- `candidates.photo_url` **全量为空**，所以所有人头像都是姓名首字
- 29.6% 的档案有 `IDPhoto` 字段，但 100% 是 `dfs://Resume/...` 内部路径
- 资产**没有** `additional/` 目录，照片文件本体不在资产里
- 设计文档 §2 原本规定证件照放 `additional/`，实际未实现

### 已验证的可行路径

证件照被渲染进了 `standard.pdf`。应用自带提取能力，直接复用即可：

- `server/attachment-avatar.js` 的 `extractPdfAvatarCandidates()` + `selectPdfAvatarCandidate()`
- 合格条件：≥96×96、宽高比 0.55–1.35、只扫 PDF 第一页

**实测（8 位档案里标了证件照的候选人）**：

| 候选人 | 提取结果 |
| --- | --- |
| 郜钰 | 314×318 ✅ |
| 宋宇航 | 200×200 ✅ |
| 胡成龙 | 270×268 ✅ |
| 胡泠仪 | 281×281 ✅ |
| 张小文 | 200×204 ✅ |
| 沈祺皓 | 1280×1280 ✅（需转码） |
| 薛岑 | 80×80 ❌ 小于 96 下限 |
| 贺帅 | 未提取到 |

**6 / 8 成功**。引用对象带 `content_type`、`extension`、`byte_length`、
`sha256`、`requires_transcoding`，落盘所需信息齐全。

### 实施方案

1. 新建脚本 `scripts/sync-candidate-avatars.mjs`，遍历有 `resume` 附件的候选人
2. 读 `standard.pdf`（原件若为 PDF 可作为备选），调用
   `extractPdfAvatarCandidates` + `selectPdfAvatarCandidate`
3. 命中后把图片写入 `data/private/attachments/files/`，
   插入 `candidate_attachments`（`attachment_type='avatar'`、`parse_status='parsed'`）
4. 设 `candidates.photo_url = 'attachment-avatar:<avatarAttachmentId>'`
   —— 这是应用既有的本地头像约定，`/api/candidates/:id/avatar` 据此解析文件
5. 幂等：同一候选人已有 avatar 附件则跳过

### 覆盖预估

约 29.6%（有证件照标记）× 75%（提取成功）≈ **全量 22%**。
未标记但有照片的档案理论上也能提，实施前先随机抽 200 人实测真实覆盖率。

### 风险与验收

- **误提**：可能把公司 logo、水印、二维码当头像。缓解：人工抽检；
  需要转码的先转成 JPEG/PNG 再入库（`resolveCandidateAvatar` 只接受
  `image/jpeg` 与 `image/png`）
- **验收**：随机抽 50 人人工核对头像是否正确，并统计提取成功率

## 阶段 3：用 Codex 解析原始简历，补齐缺失字段

### 背景（实测）

- 9 类区块全量全空：`skill`、`certificate`、`lang`、`internship`、
  `awards`、`train`、`writings`、`schoolCadre`、`schoolPractice`
- 19,610 人（16.5%）完全没有教育/工作/项目区块
- 极端对比：郜钰结构化 67 字符，原件 171,744 字节
- 结论：**结构化字段来自北森 `GetResume` 的解析结果，本身就不全；
  完整内容只在原始简历里**

### 目标

用 Codex 解析 109,139 份原始简历，把内容补成 `candidate_profile_sections`，
让界面上履历完整。**只补空缺，不覆盖已有数据。**

### 解析通道（分三层，先确定性后智能）

| 层 | 覆盖 | 做法 |
| --- | --- | --- |
| 1. 应用已有解析器 | 29.6% | PDF / DOCX / XLSX / TXT，直接用 `attachment-parser.js` |
| 2. HTML 文本抽取 | +60.6% | 自写去标签抽取（HTML 不在应用解析器支持范围内） |
| 3. 剩余类型 | 8.5% | DOC 2,944 / 图片 2,172 / ZIP 4,016 单独评估，不假装成功 |

第 1+2 层合计约 **91.5%**（99,827 份），可覆盖绝大多数。

### 字段抽取（Codex 负责的部分）

1. 把第 1、2 层抽出的纯文本按候选人分批（建议 20–50 份/批）
2. 每批交给 Codex，按固定 Schema 输出结构化区块：
   `internship` / `skill` / `certificate` / `awards` / `lang` / `train` /
   `campus` / `publication` / `management`
3. **每条字段必须带原文片段作为证据**，无证据不写
4. 写库前本地校验：Schema 合法性、原文片段能在简历文本里定位、
   不与已有区块重复
5. 写库策略：目标类型已有区块则跳过；空缺才插入，
   `source_record_id` 标记来源（如 `origin-parse:<sha256前8位>`）

### 合规门槛（必须先确认，否则不能开工）

这一步会把 **109,139 份真实简历正文发给模型网关**。开工前需要确认：

- 当前 `AGENT_BASE_URL` 指向的网关是否获批用于候选人简历
- 数据出境/留存边界（网关侧是否留日志）
- 是否需要先脱敏（姓名/手机/邮箱替换），以及脱敏后对解析质量的影响

### 成本与工期（估算）

- 文本量：118,918 份 × 平均约 8 KB ≈ **950 MB**
- 分批：按每批 30 份 ≈ 3,960 批，需限流与断点续传
- 质检：按 1% 抽检 ≈ 1,190 份人工核对

### 风险

- **模型幻觉**：可能编造经历。缓解：强制原文证据 + 本地定位校验 + 抽检
- **错误归类**：把项目经历写进实习经历。缓解：Schema 里给出判定规则 + 抽检
- **覆盖冲突**：原件内容与结构化字段不一致时以谁为准。当前策略是
  **只补空缺**，不覆盖北森已解析出来的内容
- **成本不可控**：需先小批（100 份）跑通并实测单份成本，再外推全量

### 验收

1. 小批 100 份跑通，抽检 20 份，字段准确率与证据可定位率达到可接受水平
2. 全量跑完后统计：新增区块数、覆盖人数、无法解析的档案数
3. 界面上原本空履历的 16.5% 候选人能看到内容
